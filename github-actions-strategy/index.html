Why we're moving

Three reasons

1

Cost

80% of our CircleCI bill is per active user. We already pay for GitHub seats, so with GitHub Actions we only pay for the compute we use.

2

Claude Code leans to GitHub Actions

When you ask Claude Code to build or fix a pipeline, it reaches for GitHub Actions. We're going with the grain.

3

One place, not two

Code, PRs, checks, releases, changelogs and security alerts all live in GitHub. No more switching to CircleCI to find out why a check failed.

⏱ 2 min. Cost: about 80% of the CircleCI cost is for active users. GitHub doesn't charge per user for Actions, because we already pay for everyone's GitHub seat, so we only pay for the compute we use. That per-user 80% goes away. Claude Code: AI-assisted work on pipelines and releases goes much more smoothly on GitHub Actions and the gh CLI. One place: GitHub's checks UI, the release PR, the changelog and Dependabot all sit next to the code.

Why we're moving

Consolidate, don't just copy across

Our CircleCI setup grew team by team, and it shows:

  • vsp-ci has 35 commands, almost all for .NET. There's one for Python unit tests and none for Node or Java, so those teams build their own
  • It has three image-scan commands, and one of them is a deprecated no-op
  • dynamo-config, which produces our four-part versions, hasn't changed since June 2022

Porting each orb one-for-one would carry all of that forward. Instead, the migration gives us one shared action per capability, for every stack.

⏱ 1.5 min. Checked against the orb sources: vsp-ci src/commands at origin/main 77a8171 (2026-09-25), and dynamo-config at origin/main 66b7b25 (2022-06-20). The deprecated command is docker-scan-image: its Rapid7 scanner is end-of-life, so it only prints a warning. The other two are docker-scan-image-veracode (container scan) and veracode-scan-image (scans the build output). The point: this isn't just a lift-and-shift. We're using the move to fix how fragmented things had become.

The paved road

DevOps maintains the pipeline, so you don't have to

Reusable workflows

  • app-ci: the standard CI. Works out which modules changed, then builds, tests, scans and publishes them, and reports one CI result
  • app-sast: static code security scan
  • helm-validate: lint and render your charts
  • pr-title-lint: the Conventional Commit check
  • release-please workflows coming

Shared actions, by area

docker · test · security · release · packages · helm · git · build

All in VectorLearning/github-actions. One action per job, with a stack: input where only the language changes.

Every action and reusable workflow has unit tests, run in the library's own CI before any release reaches your repo.

⏱ 2 min. Walk the left column. app-ci is the one most teams will use: their ci.yml calls it and nothing else. app-build-publish exists for teams that need extra jobs of their own (the flexible path). Tests: as of origin/main 5527dcd, all 12 actions have test suites, and each of the 5 reusable workflows has its own .bats suite. They run in the library's ci-self-test workflow. Compare that with the CircleCI orbs: a change to a shared pipeline is tested before teams get it.

The paved road

Opinionated on purpose

On the paved road

  • DevOps maintains, upgrades and secures it
  • The same pipeline in every repo, so moving between teams means nothing new to learn
  • Versioning, scanning and tagging are built in
  • Standards are written so Claude Code can follow them

Single repos and monorepos are both supported. Stacks: .NET, Python, Node and Java, rolling out stack by stack. Today you'll see .NET and Python.

What changes in your repo

Branching: mostly the same

Stays the same

  • main is the default branch
  • Developer branches: <category>/<JIRA>-<description>
    feat/DAR-102-add-clear-button · fix/DAR-103-resolve-oom · chore/update-deps
  • Branch builds are tagged with the branch name, now with the run number added: feat-DAR-102-add-clear-button-107

Changes

  • The moving main image tag goes away. Every build gets its own tag
  • Release branches are created automatically, one per minor version: release/1.0.x
  • Fixes on a release branch are forward-ported to main. The release branch is never merged back
  • New: hotfix/X.Y.x, only for plain release-please, only when a production fix can't wait for main

Forward-port: a normal PR into main that copies one fix from a release (or hotfix) branch, so the next version has it too. Only that fix goes across, nothing else on the branch.

⏱ 1.5 min. Compared with the Git Branching @ Vector page on Confluence. Branch names follow the same convention, and branch builds were already tagged with the branch name. What's new for tags is the run number on the end, so each build has its own tag, and the moving main tag going away. The real change is release branches: release-please creates them, named per minor version (the "x" is literal), and fixes flow forward to main instead of the release branch being merged back. Integration branches aren't covered by the new standards yet. If someone asks, they're still allowed, but the branch's builds get a branch-run tag and never a version.

What changes in your repo

Why squash, not merge commits

Merge commit: what lands on main

*   Merge pull request #123 from feat/DAR-102
|\
| * address review comments
| * fix typo
| * wip
| * add clear button
|/

Squash: what lands on main

* feat(search): add clear button (DAR-102) (#123)

DAR-102 links the commit to its Jira ticket. GitHub adds the (#123) PR link itself.

  • The version and changelog are read from commit titles on main. With squash, the only title is the PR title, and the title check makes sure it's right
  • A clean, linear history that's easy to read, bisect and revert, one PR at a time
  • Your branch commits can be as messy as you like. They never reach main
⏱ 1.5 min. With merge commits, "wip" and "fix typo" become commits on main, and versioning would have to make sense of them. Under Continuous versioning, a merge commit in a SemVer module's range since its last tag fails the build. release-please repos are squash-only by standard. The squash setting is in each template's repository-settings.json: squash only, with the PR title as the commit title. Put the Jira key at the end of the PR title, e.g. "(DAR-102)", so the commit on main, and the changelog line, link back to the ticket. GitHub appends the PR number "(#123)" on squash, so you get both links.

What changes in your repo

One PR, one change

A PR becomes one commit with one title and one type. So:

  • One branch = one feature or one fix. Two features in one PR become one changelog line and one version bump, and you can't revert one without the other
  • Don't mix a fix into a feature PR. Under feat:, the fix disappears from the changelog
  • Keep branches small and short-lived. Split unrelated work into separate PRs
  • Start a fresh branch after a merge. Your old branch's commits aren't on main (only the squashed copy is), so carrying on with it brings conflicts
  • ✗feat/DAR-102-search-export-and-oom-fix → one PR, one line, three changes
  • ✓feat/DAR-102-add-clear-button · feat/DAR-110-export-csv · fix/DAR-103-resolve-oom → three PRs, three changelog lines
⏱ 1.5 min. This is the habit change. Teams used to long-lived feature branches that accumulate several pieces of work will feel it most. If work genuinely has to ship together, it can still go in separate PRs that merge back to back. The fresh-branch point catches people out: after a squash merge the remote branch is gone (with the proposed auto-delete), but a local copy still has the original commits. Rebasing or merging main into it brings conflicts with your own squashed change.

What changes in your repo

One set of rules, in every repo

  • main: PR required, at least 1 approval by default (the team can set more), no force push, no deletes, nobody can bypass
  • Required checks: CI / CI result and PR / Lint PR title, accepted only from GitHub Actions
  • Version tags (v*) can't be moved or deleted
  • release-please repos: release/** and hotfix/** are protected too
  • proposed Branches are deleted automatically after merge. This keeps the branch list clean, which matters once Dependabot starts opening PRs

Before, every team had its own rules, or none. Now they're templates in cicd-standards, applied the same way everywhere.

⏱ 1 min. The rulesets are JSON templates in cicd-standards (templates/*/rulesets/), imported with gh api or GitHub's ruleset import. "Nobody can bypass" includes admins: the rule is the rule. Auto-delete is a proposal: GitHub's "Automatically delete head branches" setting (delete_branch_on_merge). It isn't in the repository-settings.json templates yet. Every Dependabot update and every squash-merged PR leaves a branch behind otherwise. A deleted branch can still be restored from the PR page if someone needs it.

What changes in your repo

Where your version lives

Before

dynamo-config

  • Read the version from a file: dynamo-config.yml, a .csproj, package.json or Chart.yaml
  • Bumped it and committed straight to main: "Version auto-update by CircleCi [ci skip]"
  • Then pushed the tag

After

Continuous versioning

  • Git tags only. No file is read or written
  • The image tag carries the version
  • Delete any committed <Version> from your .csproj

After

release-please

  • Files change only in the release PR, which a person approves
  • Services: release-type: simple writes just version.txt and CHANGELOG.md
  • Libraries: the stack's release type updates its package file, e.g. package.json

Either way, no more version-bump commits on main from a bot.

⏱ 1 min. This is what the old cibot commit actually was: dynamo-config's push-version-bumps commits the bumped file and pushes it to the branch with a token, then pushes the tags. Continuous versioning: the version lives in git tags only (cicd-standards, "Where does the version live?"). A package is the exception, because its version is part of the artifact; package versioning is still an open item. release-please: a service MUST use release-type simple, whatever its language. A language type such as node or python would rewrite a file inside the app at every release, which triggers a redundant build, and the app would report a different version from its image tag. A .NET library uses simple and passes the version to dotnet pack -p:Version=.

GitHub hardening that affects you

Which actions you can use

  • ✗uses: some-org/cool-action@main
    not on the approved list, and points at a branch that can change
  • ✗uses: actions/checkout@v4
    a tag can be moved to different code. The SHA-pinning policy rejects it
  • ✓uses: amannn/action-semantic-pull-request@48f2562…0d50 # v6.1.1
    approved, pinned to an exact commit, and the comment tells Dependabot which version it is

DevOps curates and approves general-purpose actions. Need something that isn't on the list? It goes through a security review first.
Actions: SHA. Vector's standard workflows: @v1, so updates reach you without a change. You can pin an exact version if you prefer.

⏱ 1.5 min. Why: a tag or branch can be moved to point at malicious code, and a workflow can hold your secrets and your AWS role. A full SHA can't change. The ✓ example is taken from github-actions' pr-title-lint.yml (SHA shortened here to fit). GitHub's SHA-pinning policy covers actions; reusable workflows are exempt, which is why the standard workflows can use a major-version tag.

Conventional Commits

Your PR title is now your version

PR title starts withVersion bump
feat:minor 1.4.0 → 1.5.0
fix: · perf:patch 1.4.0 → 1.4.1
feat!: or a BREAKING CHANGE: footermajor 1.4.0 → 2.0.0

Also allowed: refactor build ci chore docs style test revert

  • Squash merge means only the PR title counts
  • The required check PR / Lint PR title enforces it
  • Once it's on main it can't be fixed. A wrong title means a wrong version
⏱ 2 min. The old branching page said "always use Conventional Commits" so that one day they could drive versioning. That day is here. Under Continuous versioning, any other type that changes a module's files still ships a patch, so a patch means "a build shipped", not just "a bug was fixed". With release branches, a major version needs Release-As (covered later).

Conventional Commits

Good titles, and an easy way to write them

  • ✓feat(search): add clear button (DAR-102)
  • ✓fix(export): resolve OOM (DAR-103)
  • ✓feat(api)!: remove v1 endpoints (DAR-120)
  • ✓revert: add clear button (DAR-102)
  • ✗Updated stuff
  • ✗DAR-102 add clear button
  • ✗Revert "add clear button"

Let Claude do it

Claude Code writes Conventional Commit titles very reliably. Ask it to:

open a PR for this branch with a Conventional Commit title

It reads your diff, picks feat or fix, and flags anything breaking.

⏱ 2 min. The pattern is type(scope): description (JIRA-KEY), the same as github-actions' own history, e.g. "feat(app-ci): the standard build pipeline as library reusable workflows (COREOPS-4509) (#87)". The scope is free-form: name the area of the code. The Jira key at the end links the commit to its ticket, and GitHub adds the (#PR) on merge. The ✗ "DAR-102 add clear button" fails because the key comes first and there's no type. GitHub's own "Revert …" title isn't conventional, so retitle it revert:. Versioning

Cut is not released

Cut

The git tag is created, for example v1.0.0. A release candidate.

Released

The Promotion Manager promotes that version to production.

1.0.0 fails regression, 1.0.1 passes, and production goes straight to 1.0.1. That's normal. Not every cut version ships.

⏱ 1 min. This holds for all three strategies. "Continuous versioning" is not continuous deployment: nothing goes to production automatically. The Promotion Manager, not the list of tags, is the record of what was released.

release-please

How release branches work

  • Every version cut from main gets release/X.Y.x automatically
  • A regression fix or hotfix goes onto the release branch, and its release PR cuts 1.0.1. The fix is then forward-ported to main
  • main keeps moving: its next version is always the next minor, 1.1.0

CI builds, CD promotes

GitHub Actions stops at the image

  • CI's job ends when the versioned image is in ECR. It never deploys
  • The Promotion Manager records in Git which image each environment runs, and ArgoCD makes the cluster match
  • Promotion to production is a PR to rendered-k8s-manifests, approved by the reviewer CODEOWNERS names
⏱ 2 min. Optional test1–3 and uat environments are left out to keep the picture simple. A team can choose to deploy every main merge to develop automatically, for each service. That's an opt-in for one lower environment only.

CI builds, CD promotes

No more CircleCI approval jobs

Before

SPAs/MFEs and Lambdas deployed from a CircleCI approval step.

After

GitHub Actions builds and packages. Nothing deploys from CI.

  • Lambdas move to AWS ACK: their manifests go in rendered-k8s-manifests and the Promotion Manager promotes them, the same as services
  • SPAs/MFEs follow a similar path being finalized

Why not GitHub's own approvals? Deployment approvals are a GitHub Enterprise feature, and we're on the Team plan. The GitOps PR is the approval, and it's the audit trail too.

Both get their own walkthrough and demo in a later session.

⏱ 1 min. Decided: Lambdas are managed through AWS Controllers for Kubernetes (ACK), so a Lambda is a Kubernetes manifest like any service, and it goes through the same promotion flow. SPAs will be similar; that strategy is still being finalized. Don't go into detail here, because both get a dedicated session. Message to teams: don't build deploy steps into your GitHub Actions workflows.
