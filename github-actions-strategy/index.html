Why we're moving

Three reasons

1

Cost

80% of our CircleCI bill is per active user. We already pay for GitHub seats, so with GitHub Actions we only pay for the compute we use.

2

Claude Code leans to GitHub Actions

When you ask Claude Code to build or fix a pipeline, it reaches for GitHub Actions. We're going with the grain.

3

One place, not two

Code, PRs, checks, releases, changelogs and security alerts all live in GitHub. No more switching to CircleCI to find out why a check failed.

⏱ 2 min. Cost: about 80% of the CircleCI cost is for active users. GitHub doesn't charge per user for Actions, because we already pay for everyone's GitHub seat, so we only pay for the compute we use. That per-user 80% goes away. Claude Code: AI-assisted work on pipelines and releases goes much more smoothly on GitHub Actions and the gh CLI. One place: GitHub's checks UI, the release PR, the changelog and Dependabot all sit next to the code.

Why we're moving

Consolidate, don't just copy across

Our CircleCI setup grew team by team, and it shows:

  • vsp-ci has 35 commands, almost all for .NET. There's one for Python unit tests and none for Node or Java, so those teams build their own
  • It has three image-scan commands, and one of them is a deprecated no-op
  • dynamo-config, which produces our four-part versions, hasn't changed since June 2022

Porting each orb one-for-one would carry all of that forward. Instead, the migration gives us one shared action per capability, for every stack.

⏱ 1.5 min. Checked against the orb sources: vsp-ci src/commands at origin/main 77a8171 (2026-09-25), and dynamo-config at origin/main 66b7b25 (2022-06-20). The deprecated command is docker-scan-image: its Rapid7 scanner is end-of-life, so it only prints a warning. The other two are docker-scan-image-veracode (container scan) and veracode-scan-image (scans the build output). The point: this isn't just a lift-and-shift. We're using the move to fix how fragmented things had become.

The paved road

DevOps maintains the pipeline, so you don't have to

Reusable workflows

  • app-ci: the standard CI. Works out which modules changed, then builds, tests, scans and publishes them, and reports one CI result
  • app-sast: static code security scan
  • helm-validate: lint and render your charts
  • pr-title-lint: the Conventional Commit check
  • release-please workflows coming

Shared actions, by area

docker · test · security · release · packages · helm · git · build

All in VectorLearning/github-actions. One action per job, with a stack: input where only the language changes.

Every action and reusable workflow has unit tests, run in the library's own CI before any release reaches your repo.

⏱ 2 min. Walk the left column. app-ci is the one most teams will use: their ci.yml calls it and nothing else. app-build-publish exists for teams that need extra jobs of their own (the flexible path). Tests: as of origin/main 5527dcd, all 12 actions have test suites, and each of the 5 reusable workflows has its own .bats suite. They run in the library's ci-self-test workflow. Compare that with the CircleCI orbs: a change to a shared pipeline is tested before teams get it.

Point out what's missing: no docker commands, no scan setup, no tagging logic. Opinionated on purpose

What changes in your repo

Branching: mostly the same

Stays the same

  • main is the default branch
  • Developer branches: <category>/<JIRA>-<description>
    feat/DAR-102-add-clear-button · fix/DAR-103-resolve-oom · chore/update-deps
  • Branch builds are tagged with the branch name, now with the run number added: feat-DAR-102-add-clear-button-107

Changes

  • The moving main and latest image tags go away. One tag names one build, and it never moves:
    • main-412: a main build under release-please
    • 1.4.0: a version
⏱ 1 min. Compared with the Git Branching @ Vector page on Confluence. Branch names follow the same convention, and branch builds were already tagged with the branch name. What's new for tags is the run number on the end, so each build has its own tag, and the moving main and latest tags going away. Before, they pointed at whatever image was built most recently; they're removed as part of each repo's migration. Release branches change too, but only under one strategy, so they're covered with release-please. Integration branches aren't covered by the new standards yet. If someone asks, they're still allowed, but the branch's builds get a branch-run tag and never a version.

What changes in your repo

One PR, one change

  • One branch = one feature or one fix. Two features in one PR become one changelog line and one version bump, and you can't revert one without the other
  • Don't mix a fix into a feature PR. Under feat:, the fix disappears from the changelog
  • Keep branches small and short-lived. Split unrelated work into separate PRs
  • Start a fresh branch after a merge. Your old branch's commits aren't on main (only the squashed copy is), so carrying on with it brings conflicts
  • ✗feat/DAR-102-search-export-and-oom-fix → one PR, one line, three changes
  • ✓feat/DAR-102-add-clear-button · feat/DAR-110-export-csv · fix/DAR-103-resolve-oom → three PRs, three changelog lines
⏱ 1.5 min. This is the habit change. Teams used to long-lived feature branches that accumulate several pieces of work will feel it most. If work genuinely has to ship together, it can still go in separate PRs that merge back to back. The fresh-branch point catches people out: after a squash merge the remote branch is gone (with the proposed auto-delete), but a local copy still has the original commits. Rebasing or merging main into it brings conflicts with your own squashed change.

What changes in your repo

One set of rules, in every repo

  • main: PR required, at least 1 approval by default (the team can set more), no force push, no deletes, nobody can bypass
  • Required checks: CI / CI result and PR / Lint PR title, accepted only from GitHub Actions
  • Version tags (v*) can't be moved or deleted
  • release-please repos: release/** and hotfix/** are protected too
  • proposed Branches are deleted automatically after merge. This keeps the branch list clean, which matters once Dependabot starts opening PRs
⏱ 1 min. The rulesets are JSON templates in cicd-standards (templates/*/rulesets/), imported with gh api or GitHub's ruleset import. "Nobody can bypass" includes admins: the rule is the rule. Auto-delete is a proposal: GitHub's "Automatically delete head branches" setting (delete_branch_on_merge). It isn't in the repository-settings.json templates yet. Every Dependabot update and every squash-merged PR leaves a branch behind otherwise. A deleted branch can still be restored from the PR page if someone needs it. Before, every team had its own rules, or none. An org-wide branch protection baseline also lands on Nov 11; the standard rulesets sit on top of it, so teams don't need to do anything.

What changes in your repo

No bot commits on main

Before

cibot and dynamo-config

A machine user with a long-lived token. It read the version from a file, bumped it and committed straight to main: "Version auto-update by CircleCi [ci skip]"

After

The release App, vectorlearning-release

A one-hour token for each job. It opens release PRs and creates v* tags, GitHub Releases and release/** branches. It never commits to main and can't edit workflow files.

Where the version lives

Continuous versioning

Git tags only. No file is read or written. Delete any committed <Version> from your .csproj.

Where the version lives

release-please

Version files change only in the release PR, which a person approves.

Every CI bot account, cibot included, is retired by April 1.

⏱ 1.5 min. Sources: cicd-standards docs/ci/release-github-app.md and "Where does the version live?". The bot, before and after: cibot was a machine user, using a seat and a personal token that lasted months or never expired, and it committed and tagged. The release App is a GitHub App owned by the organization, with a fresh one-hour token for each job; branch rulesets block it from committing to main, and it has no permission to edit workflow files. Nothing lands on main except a reviewed PR, including the App's own release PR. All CI bot accounts, not just cibot, are retired by April 1, 2027, the same date the migration finishes: any pipeline still using one, or its personal token, stops working then. The old version-bump commit was dynamo-config's push-version-bumps: it read the version from dynamo-config.yml, a .csproj, package.json or Chart.yaml, committed the bumped file with a token, then pushed the tags. Under Continuous versioning, a package is the exception, because its version is part of the artifact; package versioning is still an open item. Four-part versions go too: dynamo-config's X.Y.Z.N (e.g. 1.4.0.7284) becomes SemVer X.Y.Z, with git tag v1.4.0 and image tag 1.4.0, one format that people and tools (including the Promotion Manager) can read. The four-part format remains only as a bridge for repos migrating from dynamo-config, and new repos shouldn't use it. For a repo that has to stay four-part for a while, run-number-offset continues the build number from CircleCI's last one, so numbers never go backwards.

Conventional Commits

Squash merge: your PR title is your commit, and your version

Merge commit: what lands on main

*   Merge pull request #123 from feat/DAR-102
|\
| * address review comments
| * fix typo
| * wip
| * add clear button
|/

Squash: what lands on main

* feat(search): add clear button (DAR-102) (#123)
PR title starts withVersion bump
feat:minor 1.4.0 → 1.5.0
fix: · perf:patch 1.4.0 → 1.4.1
feat!: or a BREAKING CHANGE: footermajor 1.4.0 → 2.0.0
  • The PR title check enforces the format
  • Once it's on main it can't be fixed. A wrong title means a wrong version
  • Your branch commits can be as messy as you like. They never reach main
⏱ 2.5 min. With merge commits, "wip" and "fix typo" become commits on main, and versioning would have to make sense of them. With squash, the only title on main is the PR title. It also gives a clean, linear history that's easy to read, bisect and revert, one PR at a time. Under Continuous versioning, a merge commit in a SemVer module's range since its last tag fails the build. release-please repos are squash-only by standard. The squash setting is in each template's repository-settings.json: squash only, with the PR title as the commit title. The old branching page said "always use Conventional Commits" so that one day they could drive versioning. That day is here. Under Continuous versioning, any other type that changes a module's files still ships a patch, so a patch means "a build shipped", not just "a bug was fixed". With release branches, a major version needs Release-As (covered later).

Conventional Commits

Good titles, and an easy way to write them

The pattern is type(scope): description (JIRA-KEY), the same as github-actions' own history, e.g. "feat(app-ci): the standard build pipeline as library reusable workflows (COREOPS-4509) (#87)". Cut

Released

⏱ 2 min. The message: you control your pipeline through these config files, not by editing workflow YAML. Release type: a service MUST use release-type simple, whatever its language, which writes just version.txt and CHANGELOG.md. A library uses its stack's release type, which updates its package file (e.g. package.json); a .NET library uses simple and passes the version to dotnet pack -p:Version=. A release-please repo must not set a version-format other than none in version-config.json, because two tools versioning one repo would disagree. release-please

How release branches work

  • Every version cut from main gets release/X.Y.x automatically
  • A regression fix or hotfix goes onto the release branch, and its release PR cuts 1.0.1. The fix is then forward-ported: a normal PR into main that copies just that fix. The release branch is never merged back
  • Each main commit builds main-10, main-11… Merging the release PR adds the version to the last image
  • main keeps moving: its next version is always the next minor, 1.1.0
Part of the 2.5 min above. The "x" in release/X.Y.x is literal: one branch per minor version. Plain release-please has no release branches; it uses a hotfix/X.Y.x branch only when a production fix can't wait for main. The main-N labels are image tags: every main build is tagged main-<run> (the branch name with / replaced by -), the opposite of Continuous versioning, where the main build itself is tagged with the version. The SemVer tag exists only once a person merges the release PR. The release job checks the image's revision label and adds X.Y.Z to the same image digest, with no rebuild. The release commit itself builds nothing (it only changes CHANGELOG.md, version.txt and the manifest), so v1.0.0 goes onto the image from the commit before it, main-11. Illustrative numbers: real run numbers are shared across branches, so they skip. Several release branches can exist at once: production on 1.0.2 from release/1.0.x while 1.1.0 is in regression. main is set to always-bump-minor, so a major version needs Release-As. An automatic forward-port action is planned (COREOPS-4416). Until it exists, forward-ports are opened by hand.

CI builds, CD promotes

GitHub Actions stops at the image

  • CI's job ends when the versioned image is in ECR. It never deploys
  • Build once, promote many: the image tested in staging is byte-for-byte the image that reaches production
  • Promotion to production is a PR to rendered-k8s-manifests, approved by the reviewer CODEOWNERS names
  • Lambdas (through AWS ACK) and SPAs/MFEs being finalized follow the same path, instead of CircleCI approval jobs. Both get their own session
⏱ 2 min. The Promotion Manager records in Git which image each environment runs, and ArgoCD makes the cluster match. Every image carries the label org.opencontainers.image.revision, set to the full commit SHA, so you can always trace an image back to its commit. Optional test1–3 and uat environments are left out to keep the picture simple. A team can choose to deploy every main merge to develop automatically, for each service. That's an opt-in for one lower environment only. Before, SPAs/MFEs and Lambdas deployed from a CircleCI approval step. Decided: Lambdas are managed through AWS Controllers for Kubernetes (ACK), so a Lambda is a Kubernetes manifest like any service, in rendered-k8s-manifests, and it goes through the same promotion flow. SPAs will be similar; that strategy is still being finalized. Don't go into detail here, because both get a dedicated session with a demo. Message to teams: don't build deploy steps into your GitHub Actions workflows. If someone asks why not GitHub's own approvals: deployment approvals are a GitHub Enterprise feature, and we're on the Team plan. The GitOps PR is the approval, and it's the audit trail too.
