## 3. Three reasons

*Why we're moving*

- **Cost**: **80%** of our CircleCI bill is per active user. We already pay for GitHub seats, so with GitHub Actions **we only pay for the compute we use**.

- **Claude Code leans to GitHub Actions**: When you ask Claude Code to build or fix a pipeline, it reaches for GitHub Actions. We're going with the grain.

- **One place, not two**: Code, PRs, checks, releases, changelogs and security alerts all live in GitHub. No more switching to CircleCI to find out why a check failed.

**Speaker notes:** ⏱ 2 min. Cost: about 80% of the CircleCI cost is for active users. GitHub doesn't charge per user for Actions, because we already pay for everyone's GitHub seat, so we only pay for the compute we use. That per-user 80% goes away. Claude Code: AI-assisted work on pipelines and releases goes much more smoothly on GitHub Actions and the gh CLI. One place: GitHub's checks UI, the release PR, the changelog and Dependabot all sit next to the code.

## 4. Consolidate, don't just copy across

*Why we're moving*

Our CircleCI setup grew team by team, and it shows:

- `vsp-ci` has 35 commands, almost all for .NET. There's one for Python unit tests and **none for Node or Java**, so those teams build their own
- It has **three** image-scan commands, and one of them is a deprecated no-op
- `dynamo-config`, which produces our four-part versions, hasn't changed since **June 2022**

> Porting each orb one-for-one would carry all of that forward. Instead, the migration gives us **one shared action per capability**, for every stack.

**Speaker notes:** ⏱ 1.5 min. Checked against the orb sources: vsp-ci src/commands at origin/main 77a8171 (2026-09-25), and dynamo-config at origin/main 66b7b25 (2022-06-20). The other two are docker-scan-image-veracode (container scan) and veracode-scan-image (scans the build output). The point: this isn't just a lift-and-shift. We're using the move to fix how fragmented things had become.

## 6. Your repo's entire CI

*The paved road*

```
name: build-test-publish
on:
  push:
    branches: ['**']
  workflow_dispatch:
permissions:
  contents: read
jobs:
  ci:
    name: CI
    permissions:
      contents: write   # the release tag
      id-token: write   # AWS through OIDC
    uses: VectorLearning/github-actions/
      .github/workflows/app-ci.yml@v1
    secrets:
      VERACODE_SRCCLR_API_TOKEN: …
```

```
// build-config.json
{
  "image-namespace": "example",
  "modules": {
    "src/Services/Example": {
      "stack": "dotnet"
    }
  }
}
```

*Copy `ci.yml` as-is. What gets built lives in `build-config.json`.*

**Speaker notes:** ⏱ 1.5 min. Trimmed from cicd-standards templates/continuous-versioning/ci.yml (the `uses:` line is split over two lines here to fit; in the file it's one). Point out what's missing: no docker commands, no scan setup, no tagging logic. All of that is DevOps's job now. @v1 is a major-version tag: DevOps ships fixes and improvements under it, and your repo picks them up without a change. A team that wants control can pin an exact version instead. v1.0.0 of github-actions ships mid-November; until then the library is pre-1.0 and the moving tag is @v0.N.

## 7. Opinionated on purpose

*The paved road*

**On the paved road**

- DevOps maintains, upgrades and secures it
- The same pipeline in every repo, so moving between teams means nothing new to learn
- Versioning, scanning and tagging are built in
- Standards are written so Claude Code can follow them

**Off the paved road**

**Single repos and monorepos** are both supported. **Stacks:** .NET, Python, Node and Java, rolling out stack by stack. Today you'll see .NET and Python.

## 9. Before and after

*What changes in your repo*

|  | Before (CircleCI) | After (GitHub Actions) |
|---|---|---|
| Branch protection | Different rules in each team | **One standard set of rulesets** from templates |
| Merging | Merge commits | **Squash only**. The PR title becomes the commit |
| Bot | `cibot` account committed to `main` and tagged | **Release GitHub App**: creates tags and release PRs only, **never commits to `main`** |
| Version format | Four-part `X.Y.Z.N` | **SemVer `X.Y.Z`** |
| Image tags | Moving `latest` / `main` | `<branch>-<run>` or the version. **Tags never move** |
| Dependencies | Updated by hand | **Dependabot** alerts and PRs |
| Actions | Anything, by tag | **Approved list only, pinned by SHA** |
| Release branches | Created by hand, `release/1.0.0` | Created automatically, `release/X.Y.x` |
| Deploys | CircleCI approval jobs | **ArgoCD Promotion Manager**. CI never deploys |

**Speaker notes:** ⏱ 2.5 min. The overview: each row gets its own slide or section next. Don't go into detail here. Tell people "you'll see each of these in a minute".

## 10. Branching: mostly the same

*What changes in your repo*

#### Stays the same

- `main` is the default branch
- Developer branches: `<category>/<JIRA>-<description>` `feat/DAR-102-add-clear-button` · `fix/DAR-103-resolve-oom` · `chore/update-deps`
- Branch builds are tagged with the branch name, now with the run number added: `feat-DAR-102-add-clear-button-107`

#### Changes

- **The moving `main` and `latest` image tags go away.** One tag names one build, and it never moves:
  - `main-412`: a `main` build under release-please
  - `1.4.0`: a version

**Speaker notes:** ⏱ 1 min. Compared with the Git Branching @ Vector page on Confluence. Branch names follow the same convention, and branch builds were already tagged with the branch name. What's new for tags is the run number on the end, so each build has its own tag, and the moving main and latest tags going away. Before, they pointed at whatever image was built most recently; they're removed as part of each repo's migration. Release branches change too, but only under one strategy, so they're covered with release-please. Integration branches aren't covered by the new standards yet. If someone asks, they're still allowed, but the branch's builds get a branch-run tag and never a version.

## 11. One PR, one change

*What changes in your repo*

- **One branch = one feature or one fix.** Two features in one PR become one changelog line and one version bump, and you can't revert one without the other
- **Don't mix a fix into a feature PR.** Under `feat:`, the fix disappears from the changelog
- **Keep branches small and short-lived.** Split unrelated work into separate PRs
- **Start a fresh branch after a merge.** Your old branch's commits aren't on `main` (only the squashed copy is), so carrying on with it brings conflicts

- ✗`feat/DAR-102-search-export-and-oom-fix` → one PR, one line, three changes
- ✓`feat/DAR-102-add-clear-button` · `feat/DAR-110-export-csv` · `fix/DAR-103-resolve-oom` → three PRs, three changelog lines

**Speaker notes:** ⏱ 1.5 min. This is the habit change. Teams used to long-lived feature branches that accumulate several pieces of work will feel it most. If work genuinely has to ship together, it can still go in separate PRs that merge back to back. The fresh-branch point catches people out: after a squash merge the remote branch is gone (with the proposed auto-delete), but a local copy still has the original commits. Rebasing or merging main into it brings conflicts with your own squashed change.

## 12. One set of rules, in every repo

*What changes in your repo*

- `main`: PR required, at least 1 approval by default (the team can set more), no force push, no deletes, **nobody can bypass**
- Required checks: `CI / CI result` and `PR / Lint PR title`, accepted only from GitHub Actions
- Version tags (`v*`) can't be moved or deleted
- release-please repos: `release/**` and `hotfix/**` are protected too
- [proposed] **Branches are deleted automatically after merge**. This keeps the branch list clean, which matters once Dependabot starts opening PRs

**Speaker notes:** ⏱ 1 min. The rulesets are JSON templates in cicd-standards (templates/*/rulesets/), imported with gh api or GitHub's ruleset import. "Nobody can bypass" includes admins: the rule is the rule. Auto-delete is a proposal: GitHub's "Automatically delete head branches" setting (delete_branch_on_merge). It isn't in the repository-settings.json templates yet. Every Dependabot update and every squash-merged PR leaves a branch behind otherwise. A deleted branch can still be restored from the PR page if someone needs it. Before, every team had its own rules, or none. An org-wide branch protection baseline also lands on Nov 11; the standard rulesets sit on top of it, so teams don't need to do anything.

## 13. No bot commits on `main`

*What changes in your repo*

- *Before*: **`cibot` and dynamo-config**: A machine user with a long-lived token. It read the version from a file, bumped it and **committed straight to `main`**: *"Version auto-update by CircleCi [ci skip]"*

- *After*: **The release App, `vectorlearning-release`**: A one-hour token for each job. It opens release PRs and creates `v*` tags, GitHub Releases and `release/**` branches. It **never commits to `main`** and can't edit workflow files.

- *Where the version lives*: **Continuous versioning**: **Git tags only.** No file is read or written. Delete any committed `<Version>` from your `.csproj`.

- *Where the version lives*: **release-please**: Version files change **only in the release PR**, which a person approves.

> Every CI bot account, `cibot` included, is **retired by April 1**.

**Speaker notes:** ⏱ 1.5 min. Sources: cicd-standards docs/ci/release-github-app.md and "Where does the version live?". The bot, before and after: cibot was a machine user, using a seat and a personal token that lasted months or never expired, and it committed and tagged. The release App is a GitHub App owned by the organization, with a fresh one-hour token for each job; branch rulesets block it from committing to main, and it has no permission to edit workflow files. Nothing lands on main except a reviewed PR, including the App's own release PR. All CI bot accounts, not just cibot, are retired by April 1, 2027, the same date the migration finishes: any pipeline still using one, or its personal token, stops working then. The old version-bump commit was dynamo-config's push-version-bumps: it read the version from dynamo-config.yml, a .csproj, package.json or Chart.yaml, committed the bumped file with a token, then pushed the tags. Under Continuous versioning, a package is the exception, because its version is part of the artifact; package versioning is still an open item. Four-part versions go too: dynamo-config's X.Y.Z.N (e.g. 1.4.0.7284) becomes SemVer X.Y.Z, with git tag v1.4.0 and image tag 1.4.0, one format that people and tools (including the Promotion Manager) can read. The four-part format remains only as a bridge for repos migrating from dynamo-config, and new repos shouldn't use it. For a repo that has to stay four-part for a while, run-number-offset continues the build number from CircleCI's last one, so numbers never go backwards.

## 14. What you'll notice, and when

*GitHub hardening that affects you*

| When | Change | What you'll notice | What to do |
|---|---|---|---|
| **End of January** | 2FA enforced org-wide | Members without 2FA are **removed from the org** when it's switched on | **Set up 2FA now** |
| Nov 2 | OIDC to AWS | The static AWS keys in org secrets are deleted | Assume a role through OIDC. It's built into the standard workflows |
| Nov 11 | `GITHUB_TOKEN` read-only by default | A workflow that writes (tags, comments, packages) fails | Declare `permissions:` on each job. The standard workflows already do |
| Nov 11 | Actions can't approve PRs | Bots can't approve their own changes | Nothing, for normal work |
| Nov 11 | SHA pinning required | `@v4` on an action is rejected | Pin `@<full-sha> # v4`. Dependabot keeps it current |
| Nov 11 | Approved actions only | Third-party actions not on the list are blocked | Use the paved road, or request a security review |
| December | Tidy-ups | No new public repos, wikis off, stale repos archived, `claude-review.yml` hardened | Docs go in the repo or Confluence |
| By April 1 | CI bot accounts retired | `cibot` and other bot users, and their tokens, stop working | Move to the standard workflows. The release App tags and releases |
| As repos migrate | Dependabot | Dependabot alerts and PRs appear | Review them like any other PR |

**Speaker notes:** ⏱ 2.5 min. Source: github-security-review remediation backlog (GHSEC-01, 03/10, 04, 05, 06, 08, 09, 11, 12, 15, 17). All of these are committed. OIDC to AWS comes first, on Nov 2: the static keys go then. Most of the rest lands on Nov 11, around the v1.0.0 release. Enforcement is planned for the end of January 2027, so everyone needs to set it up before then. A full SHA can't change; the "# v4" comment tells Dependabot which version it is. GitHub's SHA-pinning policy covers actions, and reusable workflows are exempt, which is why Vector's standard workflows are referenced as @v1: updates reach you without a change, and you can pin an exact version if you prefer. DevOps curates and approves general-purpose actions; anything else goes through a security review first. The org-wide branch protection baseline also lands on Nov 11, with nothing for teams to do.

## 15. Dependabot keeps your dependencies current

*New to us*

#### What it is

- **Alerts**: tells you when a dependency has a known vulnerability
- **Security updates**: a PR that bumps it to the fixed version
- **Version updates**: weekly PRs that keep your packages (NuGet, npm, pip…) and action SHA pins current (`.github/dependabot.yml`, added when your repo migrates)

#### Why it helps

- Hear about vulnerabilities **without going looking**
- The fix is **a PR like any other**: CI runs, you review and merge
- **Small, regular bumps**, not a painful upgrade every few years
- Keeps **SHA pinning** painless, and it's **free** on our plan

![A repository's pull request list showing an open Dependabot PR: ci(deps): Bump actions/setup-node from 7.0.0 to 7.1.0 in the minor-and-patch group, labeled dependencies and github_actions, opened by dependabot\[bot\]](assets/dependabot-pr.png)

**Speaker notes:** ⏱ 1.5 min. Sources: github-security-review GHSEC-04 (alerts, security updates and the dependency graph; free on the Team plan, private repos included) and GHSEC-05; the .NET migration playbook; the pilot repo's .github/dependabot.yml. We haven't used Dependabot before. It's GitHub's built-in dependency bot, with three parts. Alerts come from the dependency graph: GitHub reads your package files (NuGet, npm, pip, and so on), matches them against its advisory database, and raises an alert on the repo's Security tab. Security updates are the PRs it opens for those alerts, bumping the package to the fixed version. Version updates are what dependabot.yml configures. Each migrated repo gets it for its package ecosystem (NuGet, npm, pip, and so on), so packages move to new releases even without a vulnerability, and for github-actions, which keeps the SHA pins current. The pilot so far has only the github-actions part. Settings: weekly, minor and patch bumps grouped into one PR, each major on its own, and a 7-day cooldown so a compromised or broken release can be caught before it reaches us (security updates are never delayed). Its PR titles are Conventional Commits, e.g. "ci(deps): bump ...", so they pass the title check. It's switched on per repo as the repo migrates. Treat its PRs like any other: let CI run, read the release notes for majors, merge. Expect a burst of alerts when it's first turned on. The screenshot shows a Dependabot PR in a repo's PR list: a grouped minor bump of actions/setup-node, with its ci(deps) title and the dependencies label.

## 16. Squash merge: your PR title is your commit, and your version

*Conventional Commits*

#### Merge commit: what lands on `main`

```
*   Merge pull request #123 from feat/DAR-102
|\
| * address review comments
| * fix typo
| * wip
| * add clear button
|/
```

#### Squash: what lands on `main`

```
* feat(search): add clear button (DAR-102) (#123)
```

| PR title starts with | Version bump |
|---|---|
| `feat:` | minor 1.4.0 → 1.5.0 |
| `fix:` · `perf:` | patch 1.4.0 → 1.4.1 |
| `feat!:` or a `BREAKING CHANGE:` footer | major 1.4.0 → 2.0.0 |

- The PR title check enforces the format
- Once it's on `main` it can't be fixed. **A wrong title means a wrong version**
- **Your branch commits can be as messy as you like.** They never reach `main`

**Speaker notes:** ⏱ 2.5 min. With merge commits, "wip" and "fix typo" become commits on main, and versioning would have to make sense of them. With squash, the only title on main is the PR title. It also gives a clean, linear history that's easy to read, bisect and revert, one PR at a time. Under Continuous versioning, a merge commit in a SemVer module's range since its last tag fails the build. release-please repos are squash-only by standard. The squash setting is in each template's repository-settings.json: squash only, with the PR title as the commit title. The old branching page said "always use Conventional Commits" so that one day they could drive versioning. That day is here. Under Continuous versioning, any other type that changes a module's files still ships a patch, so a patch means "a build shipped", not just "a bug was fixed". With release branches, a major version needs Release-As (covered later).

## 17. Good titles, and an easy way to write them

*Conventional Commits*

- ✓`feat(search): add clear button (DAR-102)`
- ✓`fix(export): resolve OOM (DAR-103)`
- ✓`feat(api)!: remove v1 endpoints (DAR-120)`
- ✓`revert: add clear button (DAR-102)`
- ✗`Updated stuff`
- ✗`DAR-102 add clear button`
- ✗`Revert "add clear button"`

- *It reads your diff, picks `feat` or `fix`, and flags anything breaking.*: **Let Claude do it**: Claude Code writes Conventional Commit titles very reliably. Ask it to: `open a PR for this branch with a Conventional Commit title`

*`DAR-102` links the commit to its Jira ticket. GitHub adds the `(#123)` PR link itself. Also allowed: `refactor` `build` `ci` `chore` `docs` `style` `test` `revert`*

**Speaker notes:** ⏱ 2 min. The pattern is type(scope): description (JIRA-KEY), the same as github-actions' own history, e.g. "feat(app-ci): the standard build pipeline as library reusable workflows (COREOPS-4509) (#87)". The scope is free-form: name the area of the code. The ✗ "DAR-102 add clear button" fails because the key comes first and there's no type. GitHub's own "Revert …" title isn't conventional, so retitle it revert:. If you have time, show this live: ask Claude Code to open the PR used in Demo 1.

## 18. Cut is not released

*Versioning*

- **Cut**: The git tag is created, for example `v1.0.0`. A release candidate.

- **Released**: The Promotion Manager promotes that version to **production**.

> `1.0.0` fails regression, `1.0.1` passes, and production goes straight to `1.0.1`. That's normal. Not every cut version ships.

**Speaker notes:** ⏱ 1 min. This holds for all three strategies. "Continuous versioning" is not continuous deployment: nothing goes to production automatically. The Promotion Manager, not the list of tags, is the record of what was released.

## 19. Three ways to version

*Versioning*

|  | Continuous versioning | Plain release-please | release-please with release branches |
|---|---|---|---|
| In short | Every merge to `main` that builds cuts a version | A release PR batches changes, and merging it cuts the version | Same, plus `release/X.Y.x` created for every version |
| Image tag from a `main` build | The version it cuts, `1.4.0` | `main-412`. `1.4.0` is added to that image when the release PR merges | Same as plain. `release/1.4.x` builds are `release-1.4.x-57` |
| Batching | None: one merge, one version | The release PR collects everything since the last version | Same as plain |
| Changelog | None generated | `CHANGELOG.md` + GitHub Release | `CHANGELOG.md` + GitHub Release |
| Regression fails | Fix on `main`. The next merge is the next version | Fix on `main`. Hold other merges to keep it small | Fix on `release/X.Y.x`, forward-port to `main` |
| Hotfix while `main` has unreleased work | Not covered | `hotfix/X.Y.x`, created only when needed | The release branch already exists |
| Keep merging during regression? | Yes, but each merge is a new version | Better to hold merges | Yes |
| Monorepos | Supported | Coming | Coming |

**Speaker notes:** ⏱ 3 min. All three read the version from Conventional Commit titles. They differ in when a version is cut and how a cut version gets fixed. None is the default. A repo uses exactly one, chosen by the workflow it calls (release-please) or version-config.json (Continuous versioning). Monorepo support for release-please is planned. As of 2026-10-27 the release-please standard still says "Monorepos are not covered yet", so a monorepo team that needs release-please now should talk to DevOps.

## 20. Which one fits your team?

*Versioning*

- *You ship each change as it lands*: **Continuous versioning**

- *You ship batches after regression testing, and can pause merges to `main` meanwhile*: **Plain release-please**

- *You keep merging during regression, or must hotfix production without shipping unreleased work*: **release-please with release branches**

## 21. The files that control your pipeline

*Where the rules live*

#### Continuous versioning

| `.github/workflows/ci.yml` | Calls `app-ci`. Copy as-is |
|---|---|
| `.github/workflows/pr-title.yml` | The Conventional Commit check |
| `build-config.json` | **What to build**: modules, stack, image namespace |
| `version-config.json` | **How to version**: `"version-format": "semver"`, each module's folder, first version, extra paths |

#### release-please

| `ci.yml` · `pr-title.yml` | The same build and title check |
|---|---|
| `.github/workflows/release-please.yml` | **Picks the strategy**: calls `app-release-please` or `app-release-please-release-branches` |
| `release-please-config.json` | Release type, `versioning`, `exclude-paths` |
| `.release-please-manifest.json` | The current version |
| `release-please-config.release-branch.json` | Release branches only: patches on `release/X.Y.x` |

*Both strategies also apply `repository-settings.json` (squash only) and the `rulesets/` templates once, during setup.*

**Speaker notes:** ⏱ 2 min. The message: you control your pipeline through these config files, not by editing workflow YAML. Continuous versioning: build-config.json says what to build, and version-config.json says how each module is versioned. release-please: the workflow you call is the strategy choice. release-please-config.json on main uses always-bump-minor with release branches; the release-branch copy is identical except always-bump-patch. Release type: a service MUST use release-type simple, whatever its language, which writes just version.txt and CHANGELOG.md. A language type such as node or python would rewrite a file inside the app at every release, which triggers a redundant build, and the app would report a different version from its image tag. A library uses its stack's release type, which updates its package file (e.g. package.json); a .NET library uses simple and passes the version to dotnet pack -p:Version=. A release-please repo must not set a version-format other than none in version-config.json, because two tools versioning one repo would disagree. In Demo 1, open build-config.json and version-config.json in poc_echo_server_dotnet. In Demo 2, open release-please-config.json and the manifest.

## 24. How release branches work

*release-please*

*Diagram:* Each commit to main builds an image tagged main-10, main-11 and so on. Merging the release PR cuts v1.0.0 and adds 1.0.0 to the main-11 image, and creates release/1.0.x. A fix on release/1.0.x releases 1.0.1 and is forward-ported to main. main later cuts v1.1.0, which creates release/1.1.x.

*Diagram labels:* main · main-10 · main-11 · v1.0.0 · on main-11 · main-12 · forward-port · main-13 · v1.1.0 · on main-13 · main-14 · release/1.0.x · fix · v1.0.1 · release/1.1.x

- Every version cut from `main` gets `release/X.Y.x` **automatically**
- A regression fix or hotfix goes onto the release branch, and its release PR cuts `1.0.1`. The fix is then **forward-ported**: a normal PR into `main` that copies just that fix. The release branch is never merged back
- Each `main` commit builds `main-10`, `main-11`… Merging the release PR adds the version to the last image
- `main` keeps moving: its next version is always the next minor, `1.1.0`

**Speaker notes:** Part of the 2.5 min above. The "x" in release/X.Y.x is literal: one branch per minor version. Plain release-please has no release branches; it uses a hotfix/X.Y.x branch only when a production fix can't wait for main. The main-N labels are image tags: every main build is tagged main-\<run> (the branch name with / replaced by -), the opposite of Continuous versioning, where the main build itself is tagged with the version. The SemVer tag exists only once a person merges the release PR. The release job checks the image's revision label and adds X.Y.Z to the same image digest, with no rebuild. The release commit itself builds nothing (it only changes CHANGELOG.md, version.txt and the manifest), so v1.0.0 goes onto the image from the commit before it, main-11. Illustrative numbers: real run numbers are shared across branches, so they skip. Several release branches can exist at once: production on 1.0.2 from release/1.0.x while 1.1.0 is in regression. main is set to always-bump-minor, so a major version needs Release-As. An automatic forward-port action is planned (COREOPS-4416). Until it exists, forward-ports are opened by hand.

## 28. GitHub Actions stops at the image

*CI builds, CD promotes*

*Diagram:* CI on GitHub Actions builds and publishes an image to ECR. The ArgoCD Promotion Manager then promotes that same image through develop, staging and production.

*Diagram labels:* CI · GitHub Actions · CD · ArgoCD Promotion Manager · lint · test · build · scan · image in ECR · 1.4.0 · develop · staging · production · the same image at every step · production by approved PR

- CI's job ends when the versioned image is in ECR. **It never deploys**
- **Build once, promote many:** the image tested in staging is byte-for-byte the image that reaches production
- Promotion to production is a **PR to `rendered-k8s-manifests`**, approved by the reviewer CODEOWNERS names
- **Lambdas** (through AWS ACK) and **SPAs/MFEs** [being finalized] follow the same path, instead of CircleCI approval jobs. Both get their own session

**Speaker notes:** ⏱ 2 min. The Promotion Manager records in Git which image each environment runs, and ArgoCD makes the cluster match. Every image carries the label org.opencontainers.image.revision, set to the full commit SHA, so you can always trace an image back to its commit. Optional test1–3 and uat environments are left out to keep the picture simple. A team can choose to deploy every main merge to develop automatically, for each service. That's an opt-in for one lower environment only. Before, SPAs/MFEs and Lambdas deployed from a CircleCI approval step. Decided: Lambdas are managed through AWS Controllers for Kubernetes (ACK), so a Lambda is a Kubernetes manifest like any service, in rendered-k8s-manifests, and it goes through the same promotion flow. SPAs will be similar; that strategy is still being finalized. Don't go into detail here, because both get a dedicated session with a demo. Message to teams: don't build deploy steps into your GitHub Actions workflows. If someone asks why not GitHub's own approvals: deployment approvals are a GitHub Enterprise feature, and we're on the Team plan. The GitOps PR is the approval, and it's the audit trail too.
