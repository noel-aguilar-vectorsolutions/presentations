## 3. Three reasons

*Why we're moving*

- **Cost**: **80%** of our CircleCI bill is per active user. We already pay for GitHub seats, so with GitHub Actions **we only pay for the compute we use**.

- **Claude Code leans to GitHub Actions**: When you ask Claude Code to build or fix a pipeline, it reaches for GitHub Actions. We're going with the grain.

- **One place, not two**: Code, PRs, checks, releases, changelogs and security alerts all live in GitHub. No more switching to CircleCI to find out why a check failed.

**Speaker notes:** ⏱ 2 min. Cost: about 80% of the CircleCI cost is for active users. GitHub doesn't charge per user for Actions, because we already pay for everyone's GitHub seat, so we only pay for the compute we use. That per-user 80% goes away. Claude Code: AI-assisted work on pipelines and releases goes much more smoothly on GitHub Actions and the gh CLI. One place: GitHub's checks UI, the release PR, the changelog and Dependabot all sit next to the code.

## 4. Consolidate, don't just copy across

*Why we're moving*

Our CircleCI setup grew team by team, and it shows:

- `vsp-ci` has 35 commands, almost all for .NET. There's one for Python unit tests and **none for Node or Java**, so those teams build their own
- It has **three** image-scan commands, and one of them is a deprecated no-op
- `dynamo-config`, which produces our four-part versions, hasn't changed since **June 2022**

> Porting each orb one-for-one would carry all of that forward. Instead, the migration gives us **one shared action per capability**, for every stack.

**Speaker notes:** ⏱ 1.5 min. Checked against the orb sources: vsp-ci src/commands at origin/main 77a8171 (2026-09-25), and dynamo-config at origin/main 66b7b25 (2022-06-20). The other two are docker-scan-image-veracode (container scan) and veracode-scan-image (scans the build output). The point: this isn't just a lift-and-shift. We're using the move to fix how fragmented things had become.

## 6. Your repo's entire CI

*The paved road*

```
name: build-test-publish
on:
  push:
    branches: ['**']
  workflow_dispatch:
permissions:
  contents: read
jobs:
  ci:
    name: CI
    permissions:
      contents: write   # the release tag
      id-token: write   # AWS through OIDC
    uses: VectorLearning/github-actions/
      .github/workflows/app-ci.yml@v1
    secrets:
      VERACODE_SRCCLR_API_TOKEN: …
```

```
// build-config.json
{
  "image-namespace": "example",
  "modules": {
    "src/Services/Example": {
      "stack": "dotnet"
    }
  }
}
```

*Copy `ci.yml` as-is. What gets built lives in `build-config.json`.*

**Speaker notes:** ⏱ 1.5 min. Trimmed from cicd-standards templates/continuous-versioning/ci.yml (the `uses:` line is split over two lines here to fit; in the file it's one). Point out what's missing: no docker commands, no scan setup, no tagging logic. All of that is DevOps's job now. @v1 is a major-version tag: DevOps ships fixes and improvements under it, and your repo picks them up without a change. A team that wants control can pin an exact version instead. v1.0.0 of github-actions ships mid-November; until then the library is pre-1.0 and the moving tag is @v0.N.

## 11. Branching: mostly the same

*What changes in your repo*

#### Stays the same

- `main` is the default branch
- Developer branches: `<category>/<JIRA>-<description>` `feat/DAR-102-add-clear-button` · `fix/DAR-103-resolve-oom` · `chore/update-deps`
- Branch builds are tagged with the branch name, now with the run number added: `feat-DAR-102-add-clear-button-107`

#### Changes

- **The moving `main` image tag goes away.** Every build gets its own tag
- **Release branches are created automatically**, one per minor version: `release/1.0.x`
- Fixes on a release branch are **forward-ported** to `main`. The release branch is never merged back
- **New:** `hotfix/X.Y.x`, only for plain release-please, only when a production fix can't wait for `main`

> **Forward-port:** a normal PR into `main` that copies one fix from a release (or hotfix) branch, so the next version has it too. Only that fix goes across, nothing else on the branch.

**Speaker notes:** ⏱ 1.5 min. Compared with the Git Branching @ Vector page on Confluence. Branch names follow the same convention, and branch builds were already tagged with the branch name. What's new for tags is the run number on the end, so each build has its own tag, and the moving main tag going away. The real change is release branches: release-please creates them, named per minor version (the "x" is literal), and fixes flow forward to main instead of the release branch being merged back. Integration branches aren't covered by the new standards yet. If someone asks, they're still allowed, but the branch's builds get a branch-run tag and never a version.

## 12. Why squash, not merge commits

*What changes in your repo*

#### Merge commit: what lands on `main`

```
*   Merge pull request #123 from feat/DAR-102
|\
| * address review comments
| * fix typo
| * wip
| * add clear button
|/
```

#### Squash: what lands on `main`

```
* feat(search): add clear button (DAR-102) (#123)
```

*`DAR-102` links the commit to its Jira ticket. GitHub adds the `(#123)` PR link itself.*

- **The version and changelog are read from commit titles on `main`.** With squash, the only title is the PR title, and the title check makes sure it's right
- **A clean, linear history** that's easy to read, bisect and revert, one PR at a time
- **Your branch commits can be as messy as you like.** They never reach `main`

**Speaker notes:** ⏱ 1.5 min. With merge commits, "wip" and "fix typo" become commits on main, and versioning would have to make sense of them. Under Continuous versioning, a merge commit in a SemVer module's range since its last tag fails the build. release-please repos are squash-only by standard. The squash setting is in each template's repository-settings.json: squash only, with the PR title as the commit title. Put the Jira key at the end of the PR title, e.g. "(DAR-102)", so the commit on main, and the changelog line, link back to the ticket. GitHub appends the PR number "(#123)" on squash, so you get both links.

## 13. One PR, one change

*What changes in your repo*

A PR becomes **one commit with one title and one type**. So:

- **One branch = one feature or one fix.** Two features in one PR become one changelog line and one version bump, and you can't revert one without the other
- **Don't mix a fix into a feature PR.** Under `feat:`, the fix disappears from the changelog
- **Keep branches small and short-lived.** Split unrelated work into separate PRs
- **Start a fresh branch after a merge.** Your old branch's commits aren't on `main` (only the squashed copy is), so carrying on with it brings conflicts

- ✗`feat/DAR-102-search-export-and-oom-fix` → one PR, one line, three changes
- ✓`feat/DAR-102-add-clear-button` · `feat/DAR-110-export-csv` · `fix/DAR-103-resolve-oom` → three PRs, three changelog lines

**Speaker notes:** ⏱ 1.5 min. This is the habit change. Teams used to long-lived feature branches that accumulate several pieces of work will feel it most. If work genuinely has to ship together, it can still go in separate PRs that merge back to back. The fresh-branch point catches people out: after a squash merge the remote branch is gone (with the proposed auto-delete), but a local copy still has the original commits. Rebasing or merging main into it brings conflicts with your own squashed change.

## 14. One set of rules, in every repo

*What changes in your repo*

- `main`: PR required, at least 1 approval by default (the team can set more), no force push, no deletes, **nobody can bypass**
- Required checks: `CI / CI result` and `PR / Lint PR title`, accepted only from GitHub Actions
- Version tags (`v*`) can't be moved or deleted
- release-please repos: `release/**` and `hotfix/**` are protected too
- [proposed] **Branches are deleted automatically after merge**. This keeps the branch list clean, which matters once Dependabot starts opening PRs

> Before, every team had its own rules, or none. Now they're templates in `cicd-standards`, applied the same way everywhere.

**Speaker notes:** ⏱ 1 min. The rulesets are JSON templates in cicd-standards (templates/*/rulesets/), imported with gh api or GitHub's ruleset import. "Nobody can bypass" includes admins: the rule is the rule. Auto-delete is a proposal: GitHub's "Automatically delete head branches" setting (delete_branch_on_merge). It isn't in the repository-settings.json templates yet. Every Dependabot update and every squash-merged PR leaves a branch behind otherwise. A deleted branch can still be restored from the PR page if someone needs it.

## 15. No more CI bot accounts

*What changes in your repo*

Every CI bot account, `cibot` included, is **retired by the end of January**. The release App takes over.

|  | `cibot` (before) | `vectorlearning-release[bot]` (after) |
|---|---|---|
| What it is | A machine user, using a seat and a personal token | A GitHub App owned by the organization |
| Token lifetime | Months, or no expiry | One hour, created fresh for each job |
| Commits to `main` | Yes | Never. Branch rulesets block it |
| What it does | Commits and tags | Opens release PRs, creates `v*` tags and GitHub Releases, creates `release/**` branches |
| Can change workflows | Yes | No. It has no permission to edit workflow files |

> **Nothing lands on `main` except a reviewed PR**, and that includes the bot's own release PR.

**Speaker notes:** ⏱ 1.5 min. Source: cicd-standards docs/ci/release-github-app.md. All CI bot accounts, not just cibot, are retired by the end of January 2027: any pipeline still using one, or its personal token, stops working then. With Continuous versioning, the version lives only in git tags. Nothing writes a version into a file, so a committed \<Version> in a .csproj from an old pipeline should be deleted. With release-please, version files change only through the release PR, which a person approves.

## 16. Where your version lives

*What changes in your repo*

*Before*: **dynamo-config**

- Read the version from a file: `dynamo-config.yml`, a `.csproj`, `package.json` or `Chart.yaml`
- Bumped it and **committed straight to `main`**: *"Version auto-update by CircleCi [ci skip]"*
- Then pushed the tag

*After*: **Continuous versioning**

- **Git tags only.** No file is read or written
- The image tag carries the version
- Delete any committed `<Version>` from your `.csproj`

*After*: **release-please**

- Files change **only in the release PR**, which a person approves
- **Services:** `release-type: simple` writes just `version.txt` and `CHANGELOG.md`
- **Libraries:** the stack's release type updates its package file, e.g. `package.json`

> Either way, **no more version-bump commits on `main`** from a bot.

**Speaker notes:** ⏱ 1 min. This is what the old cibot commit actually was: dynamo-config's push-version-bumps commits the bumped file and pushes it to the branch with a token, then pushes the tags. Continuous versioning: the version lives in git tags only (cicd-standards, "Where does the version live?"). A package is the exception, because its version is part of the artifact; package versioning is still an open item. release-please: a service MUST use release-type simple, whatever its language. A language type such as node or python would rewrite a file inside the app at every release, which triggers a redundant build, and the app would report a different version from its image tag. A .NET library uses simple and passes the version to dotnet pack -p:Version=.

## 19. Which actions you can use

*GitHub hardening that affects you*

- ✗`uses: some-org/cool-action@main` not on the approved list, and points at a branch that can change
- ✗`uses: actions/checkout@v4` a tag can be moved to different code. The SHA-pinning policy rejects it
- ✓`uses: amannn/action-semantic-pull-request@48f2562…0d50 # v6.1.1` approved, pinned to an exact commit, and the comment tells Dependabot which version it is

> DevOps **curates and approves general-purpose actions**. Need something that isn't on the list? It goes through a security review first. 
**Actions: SHA. Vector's standard workflows: `@v1`**, so updates reach you without a change. You can pin an exact version if you prefer.

**Speaker notes:** ⏱ 1.5 min. Why: a tag or branch can be moved to point at malicious code, and a workflow can hold your secrets and your AWS role. A full SHA can't change. The ✓ example is taken from github-actions' pr-title-lint.yml (SHA shortened here to fit). GitHub's SHA-pinning policy covers actions; reusable workflows are exempt, which is why the standard workflows can use a major-version tag.

## 20. Your PR title is now your version

*Conventional Commits*

| PR title starts with | Version bump |
|---|---|
| `feat:` | minor 1.4.0 → 1.5.0 |
| `fix:` · `perf:` | patch 1.4.0 → 1.4.1 |
| `feat!:` or a `BREAKING CHANGE:` footer | major 1.4.0 → 2.0.0 |

*Also allowed: `refactor` `build` `ci` `chore` `docs` `style` `test` `revert`*

- Squash merge means **only the PR title counts**
- The required check `PR / Lint PR title` enforces it
- Once it's on `main` it can't be fixed. **A wrong title means a wrong version**

**Speaker notes:** ⏱ 2 min. The old branching page said "always use Conventional Commits" so that one day they could drive versioning. That day is here. Under Continuous versioning, any other type that changes a module's files still ships a patch, so a patch means "a build shipped", not just "a bug was fixed". With release branches, a major version needs Release-As (covered later).

## 21. Good titles, and an easy way to write them

*Conventional Commits*

- ✓`feat(search): add clear button (DAR-102)`
- ✓`fix(export): resolve OOM (DAR-103)`
- ✓`feat(api)!: remove v1 endpoints (DAR-120)`
- ✓`revert: add clear button (DAR-102)`
- ✗`Updated stuff`
- ✗`DAR-102 add clear button`
- ✗`Revert "add clear button"`

- *It reads your diff, picks `feat` or `fix`, and flags anything breaking.*: **Let Claude do it**: Claude Code writes Conventional Commit titles very reliably. Ask it to: `open a PR for this branch with a Conventional Commit title`

**Speaker notes:** ⏱ 2 min. The pattern is type(scope): description (JIRA-KEY), the same as github-actions' own history, e.g. "feat(app-ci): the standard build pipeline as library reusable workflows (COREOPS-4509) (#87)". The scope is free-form: name the area of the code. The Jira key at the end links the commit to its ticket, and GitHub adds the (#PR) on merge. The ✗ "DAR-102 add clear button" fails because the key comes first and there's no type. GitHub's own "Revert …" title isn't conventional, so retitle it revert:. If you have time, show this live: ask Claude Code to open the PR used in Demo 1.

## 22. Cut is not released

*Versioning*

- **Cut**: The git tag is created, for example `v1.0.0`. A release candidate.

- **Released**: The Promotion Manager promotes that version to **production**.

> `1.0.0` fails regression, `1.0.1` passes, and production goes straight to `1.0.1`. That's normal. Not every cut version ships.

**Speaker notes:** ⏱ 1 min. This holds for all three strategies. "Continuous versioning" is not continuous deployment: nothing goes to production automatically. The Promotion Manager, not the list of tags, is the record of what was released.

## 23. Three ways to version

*Versioning*

|  | Continuous versioning | Plain release-please | release-please with release branches |
|---|---|---|---|
| In short | Every merge to `main` that builds cuts a version | A release PR batches changes, and merging it cuts the version | Same, plus `release/X.Y.x` created for every version |
| Image tag from a `main` build | The version it cuts, `1.4.0` | `main-412`. `1.4.0` is added to that image when the release PR merges | Same as plain. `release/1.4.x` builds are `release-1.4.x-57` |
| Batching | None: one merge, one version | The release PR collects everything since the last version | Same as plain |
| Changelog | None generated | `CHANGELOG.md` + GitHub Release | `CHANGELOG.md` + GitHub Release |
| Regression fails | Fix on `main`. The next merge is the next version | Fix on `main`. Hold other merges to keep it small | Fix on `release/X.Y.x`, forward-port to `main` |
| Hotfix while `main` has unreleased work | Not covered | `hotfix/X.Y.x`, created only when needed | The release branch already exists |
| Keep merging during regression? | Yes, but each merge is a new version | Better to hold merges | Yes |
| Monorepos | Supported | Coming | Coming |

**Speaker notes:** ⏱ 3 min. All three read the version from Conventional Commit titles. They differ in when a version is cut and how a cut version gets fixed. None is the default. A repo uses exactly one, chosen by the workflow it calls (release-please) or version-config.json (Continuous versioning). Monorepo support for release-please is planned. As of 2026-10-27 the release-please standard still says "Monorepos are not covered yet", so a monorepo team that needs release-please now should talk to DevOps.

## 24. Which one fits your team?

*Versioning*

- *You ship each change as it lands*: **Continuous versioning**

- *You ship batches after regression testing, and can pause merges to `main` meanwhile*: **Plain release-please**

- *You keep merging during regression, or must hotfix production without shipping unreleased work*: **release-please with release branches**

> **Cutting release branches by hand today?** You move to release-please with release branches. Same idea, now automated.

**Speaker notes:** ⏱ 1.5 min. Ask the room: "Which of these sounds like your team?" Team leads should leave with a first guess. The choice is rarely changed once a repo starts, so it's worth a conversation within the team.

## 26. `VectorLearning/cicd-standards`

*Where the rules live*

- **Standards**: How builds are versioned, tagged and released: Versioning, Continuous versioning, release-please, the release App. `docs/ci/`

- **Templates**: Files you copy into your repo as-is: workflows, config files, repository settings and rulesets. `templates/`

- **How-to guides**: Step by step: set up Continuous versioning, set up release-please, fixes and hotfixes. `docs/how-to/`

## 27. The files that control your pipeline

*Where the rules live*

#### Continuous versioning

| `.github/workflows/ci.yml` | Calls `app-ci`. Copy as-is |
|---|---|
| `.github/workflows/pr-title.yml` | The Conventional Commit check |
| `build-config.json` | **What to build**: modules, stack, image namespace |
| `version-config.json` | **How to version**: `"version-format": "semver"`, each module's folder, first version, extra paths |

#### release-please

| `ci.yml` · `pr-title.yml` | The same build and title check |
|---|---|
| `.github/workflows/release-please.yml` | **Picks the strategy**: calls `app-release-please` or `app-release-please-release-branches` |

| `.release-please-manifest.json` | The current version |

## 30. Why release-please

*release-please*

- **See it before it ships**: A release PR collects every change, with the version it will cut.

- **A changelog for free**: `CHANGELOG.md` and a GitHub Release, written from your PR titles.

- **The version is calculated**: `feat`, `fix` and `!` decide it. `Release-As` overrides it when you need to.

- **You decide when**: Nothing is released until someone merges the release PR.

- **Ship what you tested**: `main` builds are tagged `main-<run>`. Merging the release PR adds `X.Y.Z` to that same image. No rebuild.

- **No bot commits on `main`**: The release PR is reviewed and approved like any other.

*[being finalized] The shared release-please workflows and the demo repo are in progress.*

**Speaker notes:** ⏱ 3 min (with the next slide). Under release-please every build, main included, is tagged \<branch>-\<run> (the branch name with / replaced by -). The SemVer tag exists only once a person merges the release PR: the retag job finds the main build of the commit before the release commit, checks its revision label, and adds X.Y.Z to the same image digest. That's the opposite of Continuous versioning, where the main build itself is tagged with the version. The changelog is the headline benefit: product, QA and support can see exactly what's in a version without asking a developer. Status: the behaviour comes from release-please's docs and source and hasn't yet been checked end to end in a demo repo (COREOPS-4428). The reusable workflows app-release-please.yml and app-release-please-release-branches.yml don't exist yet.

## 31. How release branches work

*release-please*

*Diagram:* Each commit to main builds an image tagged main-10, main-11 and so on. Merging the release PR cuts v1.0.0 and adds 1.0.0 to the main-11 image, and creates release/1.0.x. A fix on release/1.0.x releases 1.0.1 and is forward-ported to main. main later cuts v1.1.0, which creates release/1.1.x.

*Diagram labels:* main · main-10 · main-11 · v1.0.0 · on main-11 · main-12 · forward-port · main-13 · v1.1.0 · on main-13 · main-14 · release/1.0.x · fix · v1.0.1 · release/1.1.x

- Every version cut from `main` gets `release/X.Y.x` **automatically**
- A regression fix or hotfix goes onto the release branch, and its release PR cuts `1.0.1`. The fix is then forward-ported to `main`
- Each `main` commit builds `main-10`, `main-11`… Merging the release PR adds the version to the last image
- `main` keeps moving: its next version is always the next minor, `1.1.0`

**Speaker notes:** Part of the 3 min above. The main-N labels are image tags: every main build is tagged main-\<run>, and the release commit itself builds nothing (it only changes CHANGELOG.md, version.txt and the manifest), so v1.0.0 goes onto the image from the commit before it, main-11. Illustrative numbers: real run numbers are shared across branches, so they skip. Several release branches can exist at once: production on 1.0.2 from release/1.0.x while 1.1.0 is in regression. main is set to always-bump-minor, so a major version needs Release-As. An automatic forward-port action is planned (COREOPS-4416). Until it exists, forward-ports are opened by hand.

## 35. GitHub Actions stops at the image

*CI builds, CD promotes*

*Diagram:* CI on GitHub Actions builds and publishes an image to ECR. The ArgoCD Promotion Manager then promotes that same image through develop, staging and production.

*Diagram labels:* CI · GitHub Actions · CD · ArgoCD Promotion Manager · lint · test · build · scan · image in ECR · 1.4.0 · develop · staging · production · the same image at every step · production by approved PR

- CI's job ends when the versioned image is in ECR. **It never deploys**
- The Promotion Manager records in Git which image each environment runs, and ArgoCD makes the cluster match
- Promotion to production is a **PR to `rendered-k8s-manifests`**, approved by the reviewer CODEOWNERS names

**Speaker notes:** ⏱ 2 min. Optional test1–3 and uat environments are left out to keep the picture simple. A team can choose to deploy every main merge to develop automatically, for each service. That's an opt-in for one lower environment only.

## 36. No more CircleCI approval jobs

*CI builds, CD promotes*

#### Before

*SPAs/MFEs and Lambdas deployed from a CircleCI approval step.*

#### After

GitHub Actions **builds and packages**. Nothing deploys from CI.

- **Lambdas** move to **AWS ACK**: their manifests go in `rendered-k8s-manifests` and the **Promotion Manager** promotes them, the same as services
- **SPAs/MFEs** follow a similar path [being finalized]

> **Why not GitHub's own approvals?** Deployment approvals are a GitHub Enterprise feature, and we're on the Team plan. The GitOps PR *is* the approval, and it's the audit trail too.

*Both get their own walkthrough and demo in a later session.*

**Speaker notes:** ⏱ 1 min. Decided: Lambdas are managed through AWS Controllers for Kubernetes (ACK), so a Lambda is a Kubernetes manifest like any service, and it goes through the same promotion flow. SPAs will be similar; that strategy is still being finalized. Don't go into detail here, because both get a dedicated session. Message to teams: don't build deploy steps into your GitHub Actions workflows.
