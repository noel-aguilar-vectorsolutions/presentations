What a site is

A site is a hostname-rooted static origin

  • A CloudFront distribution and an S3 bucket, with DNS, its own certificate and the publisher's identity: modules/site, per environment
  • A viewer-request function, plus a KeyValueStore for versioned: modules/site-function, once per account, attached by every environment's distribution
  • It doesn't care what the files are

A viewer-request function is a CloudFront Function: a few lines of JavaScript CloudFront runs on every request. A KeyValueStore is a small key-value table the function reads at the edge.

Delivered as a site today

  • ✓ An SPA
  • ✓ An MFE host shell whose MFEs ship in the same release (mfe-example)

Delivered another way

  • → A frontend that runs as a pod: as an EKS workload
  • → An independently released MFE: as a versioned asset on the shared CDN, loaded by its host site coming
⏱ 2 min. Four words, one line each. A frontend is what a team builds: browser code, however it's hosted. An SPA is a standalone frontend: it owns a hostname and users go to it directly. An MFE is loaded into an existing site at runtime and never has a hostname of its own. A site is where an SPA is published: a hostname-rooted static origin on S3 and CloudFront. Two modules make it: modules/site creates each environment's distribution, bucket, DNS records and certificate; modules/site-function creates the site's viewer-request function (and, for versioned, its KeyValueStore) once per account, and every environment's distribution in that account attaches it. Neither knows or cares whether the site holds an SPA, a Storybook or three HTML files. Today an SPA, or a shell whose MFEs ship in the same release, is delivered as a site: mfe-example is that shell, delivered the same way, and it stays on modules/site v1 until COREOPS-4759. A frontend that runs as a pod, like scheduling-frontend, is delivered like any EKS workload. Independently released MFEs will be supported, but not as sites: an MFE has no hostname, so it's published to the shared CDN as a versioned asset, and its host site's import map pins the version. That's a follow-on epic, not built yet; last content slide. Source: strategy §0, §4.0–4.2; how-to introduction.

The four phases

Four phases, in this order

The image is never run as a service: it holds the built files, and the Job copies them out.

⏱ 2 min. Left to right. Phase 1 creates the ECR repository, the site's function once for the account (the function unit), and the site in the lowest environment (the site unit); higher environments come later, with their first promotion. The site unit's outputs (the SSM prefix, the ServiceAccount, the hostnames) and, for versioned, the function's release_name fill in the chart in phase 2. Phase 3 turns the build into one release image. Phase 4 renders the chart with that image's tag and runs a Job in the cluster that publishes the files to the site. Two things that make a site different from an EKS workload: the image is never run as a service, and the same chart, ApplicationSet and Promotion Manager deliver both methods. The method is set twice and must match: routing in the function unit, and the values block in the chart. Source: how-to "The four phases".

Two methods

In-place replaces files; versioned moves a pointer

In-place: about a minute, one build for every hostname. Versioned: one key write per hostname, no invalidation; spa-example's reached the Job's edge in 6–31 s.

⏱ 2.5 min. In-place: the publisher Job replaces the files at the root of the bucket, in an order that keeps pages already open working: copy first, nothing deleted; then index.html and the files: entries, no-cache; then invalidate /* and wait; and only then sweep what the new build doesn't have; last it writes .release.json. About a minute end to end. Versioned never touches a published release: it adds releases/<pkg>/<version>/ (or finds it there already), writes each host's config, then moves each hostname's pointer in the KeyValueStore. Then it checks through CloudFront that the page names the new version, for up to 180 seconds; if a host doesn't, it puts the old keys back and the Job fails. If every host serves it, the Job writes current.json and releases/index.json and runs retention. The 6 to 31 seconds is what spa-example's releases took at the edge the Job reached; each edge gets the change separately, so others can take up to about a minute. Source: how-to "What a release does", "Reading the publisher Job's log".

Two methods

How a request is served

In both, a path whose last segment has no . is a client-side route and gets the page. Before the first release, in-place answers 404 (the bucket is empty) and versioned 503 site not released (the host has no key).

⏱ 1.5 min. In-place serves the one page at the root of the bucket. Versioned rewrites every path into the hostname's live release, and every hostname has its own key. That's how one function and one store serve all of a site's environments in an account: spa-example's develop and staging are two distributions on one function, and their two keys point at two different releases. Before the first release, an in-place site answers 404 (the bucket is empty) and a versioned one 503 "site not released" (the hostname has no key yet). Both are expected: they're the check that phase 1 worked. Source: how-to "How a request is served"; modules/site-function viewer-request-in-place.js and viewer-request-versioned.js.

Two methods

Which to choose

In-place

Your build stays as it is, served from the root, and you can live without instant rollback.

Versioned preferred

One build change, the version in your URLs, for instant rollback and a release per hostname.

Why preferred: rollback is one key write; the release check reverts itself; each hostname has its own release; old releases are kept; and it's the method proven on v2.

Choose once. Switching an existing site's method isn't supported: create a new site with the other method.

⏱ 1.5 min. The method is chosen once per site, with routing in the site's function unit; it's required and has no default, so every function unit states it. Why you can't switch: the bucket layout, the viewer-request function and the publisher's permissions all differ between the two. Switching means a new site with the other method, then moving the hostnames. It's a trade-off, not a capability: almost any modern build can put the version in its URLs with one setting (Vite base, webpack publicPath), set from RELEASE_VERSION as spa-example does with Vite's base. The version has to be in the URL because the function picks the live version only when a page loads; a tab still open on the old release keeps fetching its own chunks by their versioned URLs after a promotion or rollback. The publisher refuses a versioned image whose index.html doesn't reference /releases/<pkg>/<version>/. The rare build that really can't, say hard-coded root paths or a service worker that must control the whole site, goes in-place. Versioned is the preferred method for what it gives you. Rollback is one key write: the release folder is still there. The Job checks that each host serves the new version and puts the keys back if one doesn't, so a bad release undoes itself. Each hostname has its own release. Old releases stay, at least the last 10, so open pages keep working. And it's the method we've proven on v2: spa-example's promotion and rollback on develop and staging; in-place hasn't been run on v2 yet. The CloudFront Functions quota no longer decides it: under v2 both methods use one function per site per account (next slide). Source: how-to "Which to choose", "Side by side" and step 3; modules/site-function viewer-request-versioned.js; Noel, 2026-11-23.

Phase 1 · Infrastructure

Two units: the function, then the site

platform/<app>-site-function on modules/site-function site-function-v1.0.1, once per account, sets routing; application/<app>-site on modules/site site-v2.0.0, a leaf per environment, attaches it.

Why one function per account: CloudFront allows 100 functions per account by default (CORE nonprod had 13 on 2026-11-19); one per distribution would cost a site five in nonprod. Check: every hostname answers 503 site not released (versioned) or 404 (in-place).

⏱ 2.5 min. Follow "Create a site unit" in infrastructure-standards; it's linked from the how-to. A site is two units, created in this order. First the function unit, platform/<app>-site-function, with modules/site-function: the viewer-request function and, for versioned, the KeyValueStore, once per account, with the routing, the API prefixes and the redirect hosts set there, once. It's in platform/, so DevOps approves every change. Then the site unit, application/<app>-site, a leaf per environment on modules/site v2: each leaf reads the function through a dependency block and passes it on. spa-example's lines, by file: platform/spa-example-site-function/unit_tf/main.tf has source = "…//modules/site-function?ref=site-function-v1.0.1"; its leaf, environments/nonprod/terragrunt.hcl, has the input routing = "versioned" (or "in-place"; required, no default). application/spa-example-site/unit_tf/main.tf has source = "…//modules/site?ref=site-v2.0.0"; its leaf, environments/dev/terragrunt.hcl, has the inputs function = dependency.site_function.outputs.function, alias_hosts = ["spa-example.develop.vsp-nonprod.com"] and dns_zones = { "vsp-nonprod.com" = "Z…" }. Apply the function unit's nonprod leaf first, then the lowest environment's site leaf; the first apply waits a few minutes for the certificate, which the module issues for alias_hosts and validates in dns_zones. Every host in alias_hosts needs its zone there. Check the name is free first: a site's record takes over any host an Istio VirtualService already serves through the wildcard. Why one function per account: CloudFront Functions are a default quota of 100 per account, and whether AWS would raise it is unknown, so sites plan within 100. CORE nonprod had 13 on 2026-11-19. One per distribution would cost a site five in nonprod (develop, test1–3, staging), room for about 17 more sites; one per site per account leaves room for about 87, whatever the method. Prod has its own 100. The trade-offs, accepted: every environment's publisher can write every one of the site's keys, and a function change reaches all of the site's nonprod environments at once. The hand-off to the chart is still SSM: the Job reads the bucket and distribution id (and for versioned the KeyValueStore ARN and retention) at run time. The publisher's identity is IRSA (IAM roles for service accounts): an IAM role that only the <app>-site-publisher ServiceAccount in your namespace can assume. Note what phase 2 needs: the SSM prefix, the ServiceAccount name, the hostnames and, for versioned, release_name. The in-place 404 isn't confirmed on v2 yet. Source: how-to step 2; strategy §4.4.2 and 2026-11-21 decision; plan §1; AWS CloudFront quotas.

Phase 2 · App repository

The build fits the method; one values block says which

  • The image holds no environment values. Browser config goes in files:, and it's public: never a secret.
  • Versioned: the build writes /releases/<pkg>/<version>/ into its URLs, from RELEASE_VERSION. In-place: a plain build, index.html at the top.
  • helm/<app>/ depends on site-release, pinned to an exact version, with Chart.lock committed.
  • Versioned: each environment's site.hosts lists only its own hostnames. The store is shared, so this list keeps a develop release off staging's key.

⏱ 3 min. The release image is the contract between the app and the publisher. One rule for both: no environment value in the image; anything the browser reads at run time, like an API URL, goes in the chart's files:, which the Job writes and serves. spa-example's file is served at /config/spa-example-config.json (environment and apiBaseUrl). The in-place column is an illustration: spa-example is versioned, and this is what its develop values would be in place, with only keys site-release 0.4.1 accepts; no site runs in-place on v2 yet. In place, files: entries are written next to the build, so config.json is served at /config.json, no-cache. Versioned asks more of the build: URLs to the site's own files are host-relative, /releases/<pkg>/<version>/…, written by the build from RELEASE_VERSION (webpack publicPath or the import map, Vite base); app code never derives URLs from its own version. In-place takes a plain build with index.html at the top of sourcePath (default /release/dist); a fixed-name file such as a service worker goes in noCache. The values have exactly one block, site: or inPlace:, matching routing; the render fails with neither, both, or a key the block doesn't know. Both are merged values.yaml plus envs/values-<namespace>.yaml, trimmed. spa-example's values-staging.yaml is the same shape with staging's host and /terragrunt-demo/staging/site/spa-example. The hosts rule matters because the KeyValueStore is shared by all of the site's environments in the account, and its IAM can only name the whole store: develop's publisher could move staging's key, and what stops it is that develop's values list only develop's host. spa-example pins site-release 0.4.1. Source: how-to steps 3–4; proposed-standards 4.13; spa-example helm/spa-example; site-release 0.4.1's accepted inPlace keys (templates/_helpers.tpl).

Phase 3 · CI

Build the release image once, on main

  • Every environment releases the same image; nothing is rebuilt per environment.
  • Versioned takes only X.Y.Z, so a branch image can never be released. In-place takes any tag, a branch build included.
⏱ 1.5 min. Build once, on main. CI builds and checks the image first; only the publish step asks ECR whether the version is already there. ECR tags are mutable, so CI must never push over a release: the same tag from the same commit is a re-run, so skip the push; from another commit, fail the run. For versioned, RELEASE_VERSION is set for the release build only, so the build writes dist/<version>/ with versioned URLs; local builds and previews are unchanged. The base image needs sh, mkdir, cp, find, sort, sha256sum and cut, because the Job runs it as an init container that copies the files out: spa-example uses busybox 1.38.0, pinned by digest. References: spa-example's ci.yml for versioned (jobs Plan release, Build release image, Publish image, Tag release commit; it's an exception to cicd-standards' two CI paths until the library's site build can do this, COREOPS-4783 and 4784). There's no in-place reference on v2 yet. Source: how-to step 5.

Phase 4 · CD

Register once; every promotion publishes

  • Register once (DevOps, one argo-app-of-apps PR): the ApplicationSet, with retry.limit: 2, and the promotion config. Auto-deploy only on the lowest environment.
  • Promote the first release by hand: versions pushed before the config existed aren't deployed automatically.
  • Each higher environment adds a site leaf (DevOps approves), its values file and a promotion entry; it reuses the function.
⏱ 2 min. Same for both methods; only what the Job does differs. The Promotion Manager renders your chart with the image tag and commits the environment's manifests, a ConfigMap and a Job, to the rendered-manifests repo; ArgoCD syncs <env>-<app> and runs the <env>-<app>-site-release Job. Why retry.limit 2: a failed versioned attempt puts the failing release live for its check (up to 180 s) before reverting, and ArgoCD runs one operation per app at a time; two retries keep a failure to about 12 minutes, where ArgoCD's default of 5 took over 40. Higher environments are promoted by hand. A product's site uses its own Argo project and the rendered-k8s-manifests repository; spa-example is a POC and renders to poc-rendered-k8s-manifests, which needs a ruleset bypass for the Promotion Manager. Then check: the manifests commit, the Argo app, the Job log line "<host> serves <version> at edge …" (versioned) or "released <version>" (in-place), and the site. Staging, for spa-example: a staging site leaf pinned to the tag the first merge cut, the EKS locals in _env/staging.hcl, envs/values-staging.yaml, and a staging override in the promotion config without auto-deploy. Its plan added a distribution, not a function. Source: how-to steps 6–8.

After the first release

Rollback and failed releases

Rolling back

  • Roll back in the Promotion Manager: it restores that promotion's manifests, files: included
  • Versioned: the folder is still there, so only that environment's key changes
  • In-place: a full release of the earlier image: copy, invalidate, sweep

When a release fails

  • Versioned: no host serves it within 180 s? The Job puts every key back and fails. Nothing to clean up.
  • In-place: every step is safe to repeat; the next sync finishes the release

ArgoCD retries twice, about 12 minutes at most. A newer release waits; releases in between are skipped.

⏱ 2 min. This is what the demo just showed: a versioned rollback takes as long as the key takes to reach the edge. The recommended way is the Promotion Manager's Rollback: it commits "chore(rollback): revert app-manifests/<app>-appset/<cluster>/<env>/manifests.yaml to <version>", which restores that promotion's rendered manifests as they were, files: included, and ArgoCD's sync runs the Job. Promoting the earlier version also works, but it renders the chart from main, so the old image goes out with today's values. The flip side: a Rollback restores that render as it was, including the site-release chart version it used, so rolling back across a chart fix re-runs the older publisher. spa-example's develop rollback to 1.0.2 on 2026-11-23 (b39f2ab) went back to site-release 0.4.0, from before the 0.4.1 check fix. spa-example's staging went back from 1.0.3 to 1.0.2 that way on 2026-11-23: the folder was already uploaded, one key write, served 31 s later at the Job's edge, and develop's key stayed on 1.0.3. In-place rollback is a whole release with the old image, about a minute. Failures: versioned is self-healing; users see the old version again. In-place: a failure before the copy changes nothing; if the invalidation doesn't complete in time, the Job fails before the sweep, so the new build is already serving, the old files are still there, and the next sync finishes it. For both, the sync fails and ArgoCD retries it twice. While retries run, a newer release waits; when the failed operation ends, ArgoCD syncs the newest commit, so releases in between are skipped. To stop the retries at once, terminate the operation on <env>-<app> in ArgoCD. The Job itself never retries (backoffLimit 0): a second pod would put the failing release live again. Source: how-to "Rolling back", "When a release fails"; proposed-standards 7.12; poc-rendered-k8s-manifests commit 818f695; Noel, 2026-11-23 (the Promotion Manager's rollback is the recommendation).

After the first release · environments

Each environment is its own distribution

A test environment (test1–3) is one more site leaf: a distribution, not a function. The function and the store are shared, so a function change reaches every nonprod environment at once. Production has its own function and store (not yet covered). On 2026-11-23, before rehearsal, the keys were develop 1.0.3 and staging 1.0.2.

Alternative, versioned only: test hostnames as alias hosts on develop's distribution, each with its own key. For testing releases, never infrastructure.

⏱ 1.5 min. The default is one distribution per environment, test environments included. spa-example has develop and staging: two distributions, each with its own bucket and certificate, on one function and one store, with a key per host. On 2026-11-22/23, promoting 1.0.3 to staging and rolling it back to 1.0.2 changed only staging's key; develop stayed on 1.0.3. The versions in the caption are as of 2026-11-23 before rehearsal; they move with every promotion. A test environment is the same again: a site leaf with the same dependency on the function unit's nonprod leaf, its own values listing only its hostname, its own Argo app and promotion entry. It costs a distribution, not a function. spa-example has no test environments yet. What's shared, and accepted: every environment's publisher can write every one of the site's keys (the chart's hosts list is the guard), and a function change reaches every nonprod environment of the site at once. Production has its own function and store, and isn't covered yet. The alternative, versioned only: test hostnames on develop's distribution, each with its own key, so no extra distribution or bucket. It isn't the default: in-place can't do it, the test names become names on develop's leaf and certificate, and a test environment on develop's distribution can't try infrastructure changes or have its own WAF, headers or logs. Source: how-to step 8, "Optional: test environments"; strategy §4.4.2–4.4.3; TRACKER 2026-11-22/23.

After the first release · optional

An API through the site

/api/* on the site's own hostname: same origin, no CORS. The same for both methods.

  1. Infrastructure: the /api prefix is set once in the function unit (DevOps approves); each environment's site unit sets api, which adds the /api/* behavior
  2. The API's chart: a site VirtualService on the external gateway, listing the site's hostnames
  3. The API checks the origin-verify header, so only CloudFront reaches it (api.origin_verify; architecture-standards R206.1)
  4. Promote the API, so its chart renders the new VirtualService
  5. The site's config sets the API's base URL to /api

spa-example's /api/hello reaches the echo server in its own environment, on develop and staging.

⏱ 1 min. Optional; some apps need it, not all. The plan fails if the function unit has the prefix and a site leaf has no api, or the other way round. spa-example leaves origin_verify out on purpose, because its API is the echo server, which only shows the headers it gets; a real API must not copy that. The VirtualService matches only /api/ and lists that environment's site hostnames; poc_echo_server_node's templates/virtualservice-site.yaml is the example. The origin-verify check means the API refuses requests that didn't come through the site's CloudFront. A chart-only change builds no image, so re-promote the current version. Check it: /api/anything returns 200 with Host set to the site hostname, and x-cache is never a Hit. If /api/… returns 404 with server: istio-envoy, the API's site VirtualService isn't deployed: promote the API. Source: how-to "Optional: route an API through the site"; spa-example envs/values-*.yaml (apiBaseUrl /api).
