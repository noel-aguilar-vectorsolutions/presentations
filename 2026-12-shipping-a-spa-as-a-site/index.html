What a site is

A site is a hostname-rooted static origin

  • A CloudFront distribution, an S3 bucket and a viewer-request function, plus DNS and the publisher's identity
  • Created by modules/site for one app in one environment
  • It doesn't care what the files are

Delivered as a site today

  • ✓ An SPA
  • ✓ An MFE host shell whose MFEs ship in the same release (mfe-example)

Delivered another way

  • → A frontend that runs as a pod: as an EKS workload
  • → An independently released MFE: as a versioned asset on the shared CDN, loaded by its host site coming
⏱ 2 min. Four words, one line each. A frontend is what a team builds: browser code, however it's hosted. An SPA is a standalone frontend: it owns a hostname and users go to it directly. An MFE is loaded into an existing site at runtime and never has a hostname of its own. A site is where an SPA is published: a hostname-rooted static origin on S3 and CloudFront. The site module doesn't know or care whether it holds an SPA, a Storybook or three HTML files. Today an SPA, or a shell whose MFEs ship in the same release, like mfe-example, is delivered as a site. A frontend that runs as a pod, like scheduling-frontend, is delivered like any EKS workload. Independently released MFEs will be supported, but not as sites: an MFE has no hostname, so it's published to the shared CDN as a versioned asset, and its host site's import map pins the version. That's a follow-on epic, not built yet; last content slide. Source: strategy §4.0–4.2.

The four phases

Four phases, in this order

The image is never run as a service: it holds the built files, and the Job copies them out.

⏱ 2 min. Left to right. Phase 1 creates the site and the ECR repository; the unit's outputs (the SSM prefix, the ServiceAccount, the hostnames and, for versioned, release_name) fill in the chart in phase 2. Phase 3 turns the build into one release image. Phase 4 renders the chart with that image's tag and runs a Job in the cluster that publishes the files to the site. Two things that make a site different from an EKS workload: the image is never run as a service, and the same chart, ApplicationSet and Promotion Manager deliver both methods. The method is set twice and must match: routing in the Terraform, and the values block in the chart. Source: how-to "The four phases".

Two methods

In-place replaces files; versioned moves a pointer

In-place: about a minute, one build for every hostname. Versioned: one key write per hostname, 30–40 s to reach the edge, no invalidation.

⏱ 2.5 min. In-place: the publisher Job replaces the files at the root of the bucket, in an order that keeps pages already open working: copy first, nothing deleted; then index.html and the files: entries, no-cache; then invalidate /* and wait; and only then sweep what the new build doesn't have. About a minute end to end. Versioned never touches a published release: it adds releases/<pkg>/<version>/ (or finds it there already), writes each host's config, then moves each hostname's pointer in the KeyValueStore. Then it checks through CloudFront that the page names the new version, for up to 180 seconds; if a host doesn't, it puts the old keys back and the Job fails. The 30–40 seconds for a key to reach the edge is what we measured on develop. Source: how-to "What a release does".

Two methods

How a request is served

In both, a path whose last segment has no . is a client-side route and gets the page.

⏱ 1.5 min. In-place serves the one page at the root of the bucket. Versioned rewrites every path into the hostname's live release, so two hostnames on one distribution can serve two different releases; that's what makes test environments as alias hosts possible, later. Before the first release, an in-place site answers 404 (the bucket is empty) and a versioned one 503 "site not released" (the hostname has no key yet). Both are expected: they're the check that phase 1 worked. Source: how-to "How a request is served"; modules/site viewer-request-in-place.js and viewer-request-versioned.js.

Two methods

Which to choose

In-place

A plain build, and you don't need instant rollback. Or your build can't put the version in its URLs.

Versioned

Instant rollback, a release per hostname, or test environments sharing develop's distribution.

Choose once. Switching an existing site's method isn't supported: you'd stand up a new distribution.

⏱ 1.5 min. The method is chosen once per site, with routing on modules/site; it's required and has no default, so every unit states it. Why you can't switch: the bucket layout, the viewer-request function and the publisher's permissions all differ between the two. Switching means a new site with the other method, then moving the hostnames. If you're unsure: versioned costs a build change (versioned URLs from RELEASE_VERSION) and gives you one-write rollback and a release per hostname. Source: how-to "Which to choose"; modules/site variables.tf, routing.

Phase 1 · Infrastructure

The unit creates the site and hands off through SSM

source  = "…//modules/site?ref=site-v1.1.0"
routing = "versioned"   # or "in-place"; required, no default

Check: every hostname answers 404 (in-place) or 503 site not released (versioned).

⏱ 2.5 min. Follow "Create a site unit" in infrastructure-standards; it's linked from the how-to. Start with the lowest environment. The unit calls modules/site with the method you chose. Everything in the left box exists for both methods; the right box only for versioned. The hand-off to the chart is SSM: the publisher Job reads the bucket and distribution id (and for versioned the KeyValueStore ARN and retention) at run time, so no resource id is ever copied into Helm values. The publisher's identity is an IRSA role and its ServiceAccount in your namespace. Note what phase 2 needs: the SSM prefix, the ServiceAccount name, the hostnames and, for versioned, release_name. The snippet shows site-v1.1.0 for versioned; that tag is being finalized, and in-place uses site-v1.0.0 today (SDS does). Source: how-to step 2; modules/site README.

Phase 2 · App repository

The build fits the method; one values block says which

  • The image holds no environment values. Browser config goes in files:, and it's public: never a secret.
  • Versioned: the build writes /releases/<pkg>/<version>/ into its URLs, from RELEASE_VERSION. In-place: a plain build, index.html at the top.
  • helm/<app>/ depends on site-release, pinned to an exact version, with Chart.lock committed.

Versioned · mfe-example

siteRelease:
  serviceAccountName: mfe-example-site-publisher
  files:
    mfe-demo-config.js: { API_URL: /api }
  site:
    pkg: mfe-example
    hosts: [mfe-example.develop.vsp-nonprod.com]
    ssmPrefix: /terragrunt-demo/dev/site/mfe-example

In-place · SDS

siteRelease:
  serviceAccountName: sds-site-publisher
  files:
    config.json: { apiBase: "", … }
  inPlace:
    target: "."
    sourcePath: /release/site
    ssmPrefix: /sds/test1/site
    noCache: [sw.js]
⏱ 3 min. The release image is the contract between the app and the publisher. One rule for both: no environment value in the image; anything the browser reads at run time, like an API URL, goes in the chart's files:, which the Job writes and serves. mfe-example's file is served at /config/mfe-demo-config.js; SDS's at /config.json, no-cache. Versioned asks more of the build: URLs to the site's own files are host-relative, /releases/<pkg>/<version>/…, written by the build from RELEASE_VERSION (webpack publicPath or the import map, Vite base); app code never derives URLs from its own version. In-place takes a plain build with index.html at the top of sourcePath; SDS's is /release/site, and noCache lists its service worker, which has a fixed name. The values have exactly one block, site: or inPlace:, matching routing; the render fails with neither, both, or a key the block doesn't know. Both are merged values.yaml plus envs/values-<namespace>.yaml, trimmed. mfe-example pins site-release 0.3.1; SDS pins 0.3.0. Source: how-to steps 3–4; mfe-example helm/mfe-example; sds src/helm/sds-site.

Phase 3 · CI

Build the release image once, on main

  • Every environment releases the same image; nothing is rebuilt per environment.
  • Versioned takes only X.Y.Z, so a branch image can never be released. In-place takes any tag: SDS releases a build tag such as main-<run>, or a release version.
⏱ 1.5 min. Build once, on main. Skip a version already in ECR: ECR tags are mutable, so CI must never push over a release tag. For versioned, RELEASE_VERSION is set for the release build only, so the build writes dist/<version>/ with versioned URLs; local builds and previews are unchanged. The base image needs sh, cp, find, sort, sha256sum and cut, because the Job runs it as an init container that copies the files out: mfe-example uses busybox 1.38.0, pinned by digest. References: mfe-example's ci.yml, job "Build and publish image", for versioned; SDS's ci.yml for in-place. Source: how-to step 5.

Phase 4 · CD

Register once; every promotion publishes

  • Register once (DevOps, one argo-app-of-apps PR): the ApplicationSet, with retry.limit: 2, and the promotion config. Auto-deploy only on the lowest environment.
  • Promote the first release by hand: versions pushed before the config existed aren't deployed automatically.
⏱ 2 min. Same for both methods; only what the Job does differs. The Promotion Manager renders your chart with the image tag and commits the environment's manifests, a ConfigMap and a Job, to the rendered-manifests repo; ArgoCD syncs <env>-<app> and runs the <env>-<app>-site-release Job. Why retry.limit 2: a failed versioned attempt puts the failing release live for its check (up to 180 s) before reverting, and ArgoCD runs one operation per app at a time; two retries keep a failure to about 12 minutes, where ArgoCD's default of 5 took over 40. Higher environments are promoted by hand. The Promotion Manager's writer identity must be able to push to the manifests repo, or the first promotion fails at the push. Then check: the manifests commit, the Argo app, the Job log ending in "serves <version>" or "released <version>", and the site. Source: how-to steps 6–7.

After the first release

Rollback and failed releases

Rolling back

  • Promote the earlier version, or revert its manifests commit
  • Versioned: the folder is still there, so only the key changes
  • In-place: a full release of the earlier image: copy, invalidate, sweep

When a release fails

  • Versioned: no host serves it within 180 s? The Job puts every key back and fails. Nothing to clean up.
  • In-place: every step is safe to repeat; the next sync finishes the release

ArgoCD retries twice, about 12 minutes at most. A newer release waits; releases in between are skipped.

⏱ 2 min. This is what the demo just showed: a versioned rollback takes as long as the key takes to reach the edge. In-place rollback is a whole release with the old image, about a minute. Failures: versioned is self-healing; users see the old version again. In-place: a failure before the copy changes nothing; if the invalidation doesn't complete in time, the Job fails before the sweep, so the new build is already serving, the old files are still there, and the next sync finishes it. For both, the sync fails and ArgoCD retries it twice. While retries run, a newer release waits; when the failed operation ends, ArgoCD syncs the newest commit, so releases in between are skipped. To stop the retries at once, terminate the operation on <env>-<app> in ArgoCD. The Job itself never retries (backoffLimit 0): a second pod would put the failing release live again. Source: how-to "Rolling back", "When a release fails"; proposed-standards 7.12.

After the first release · versioned

Test environments as alias hosts being finalized

test1–3 are extra hostnames on develop's distribution, each with its own key. Waiting on *.test1-3 on the nonprod certificate.

⏱ 1 min. Illustrative: no test environment is set up this way yet. With versioned, test1–3 don't need distributions of their own: the develop unit lists their hostnames in alias_hosts and creates a publisher ServiceAccount per namespace; each test namespace's values list only its own hostname, with develop's ssmPrefix, and has its own Argo app and promotion entry. So test1 can stay on an older release while develop moves on, and retention never deletes a version any hostname points at. What's missing: the nonprod us-east-1 platform certificate covers *.develop and *.staging, not *.test1-3 yet. Give a test environment its own distribution instead if it must test infrastructure changes, or needs its own WAF, headers, logs or IAM: every namespace's publisher can write every key in the shared store. Source: how-to "Optional: test environments"; strategy §4.4.3.

After the first release · optional

An API through the site

/api/* on the site's own hostname: same origin, no CORS. The same for both methods.

  1. Infrastructure: the site unit's api input adds the /api/* behavior
  2. The API's chart: a site VirtualService on the external gateway, listing the site's hostnames
  3. The API checks requests came through CloudFront (architecture-standards §206)
  4. Promote the API, so its chart renders the new VirtualService
  5. The site's config sets API_URL: /api

mfe-example's /api/hello reaches its echo server this way; SDS sends /api and /admin to its API on test1.

⏱ 1 min. Optional; some apps need it, not all. The VirtualService matches only /api/ and lists that environment's site hostnames; poc_echo_server_node's templates/virtualservice-site.yaml is the example. The origin-verify check means the API refuses requests that didn't come through the site's CloudFront. A chart-only change builds no image, so re-promote the current version. Check it: /api/anything returns 200 with Host set to the site hostname, and x-cache is never a Hit. If /api/… returns 404 with server: istio-envoy, the API's site VirtualService isn't deployed: promote the API. Source: how-to "Optional: route an API through the site"; SDS test1 values (apiBase "" sends /api and /admin to the API).
