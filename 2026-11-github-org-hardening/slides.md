## 2. GitHub's settings now protect every pipeline

*Why now*

- **The Actions migration**: Every pipeline becomes a GitHub workflow, with our code, secrets and AWS roles.

- **Open defaults**: GitHub favours convenience. Ours were never tightened, across ~800 active repos.

- **A real attack**: March 2025: a moved `tj-actions` tag ran attacker code in thousands of pipelines.

> **No new licences.** Everything in this plan runs on the GitHub Team plan we already pay for.

**Speaker notes:** ⏱ 1.5 min. The point: once CI lives in GitHub Actions, a workflow can reach our source, our secrets and our AWS roles, so the organization's Actions settings are now part of our security perimeter. GitHub ships with permissive defaults, and nobody had tightened ours; with about 800 active repositories, configuring them one at a time has left uneven coverage. The tj-actions/changed-files compromise in March 2025 is the example to remember: an attacker moved a version tag to point at malicious code, and every pipeline that referenced the tag ran it. We don't use that action, but nothing in our current settings would stop the same thing happening with one we do use. Every control in this plan is available on the Team plan, so there's no licence cost; the cost is configuration time, plus small edits in some repos.

## 5. Control what runs in CI, and what it can touch

*Q4 2026 · secure the CI supply chain*

- **Pin every action**: An exact commit can't be moved. Teams get a report with the fix first. Announce: November 
Enable: December

- **Approved actions only**: Ours, GitHub's, and the 22 third-party actions in use today. New ones by request. November

- **Read-only token**: Read access unless a workflow asks for more; no PR approvals. 3 workflows need one line. Announce: November 
Enable: December

**Speaker notes:** ⏱ 2 min. These three close the tj-actions class of attack. Pinning: a tag like @v4 can be moved by whoever controls the action; a 40-character commit SHA can't. A report goes to the 46 affected repos with the exact replacement for every line, and Dependabot keeps pins current; DevOps adds its configuration when each repo moves to GitHub Actions, so teams don't add it themselves. Pinning is announced in November, with the report, and required org-wide in December, which gives the 46 repos a month to pin. Repos that are already fully pinned (55 of them) can get the requirement first, so they can't slip back. The approved-actions list lands in November. GitHub's rule covers its own actions too; reusable workflows are exempt. Approved actions: VectorLearning's own and GitHub-authored actions are allowed, plus a named list of 22 third-party actions, split between vendors (AWS, Docker, Microsoft, HashiCorp, Anthropic, Google, Astral, Veracode) and four individual maintainers. Four retiring actions stay allowed until 31 January 2027. No wildcards; we can loosen later. New actions are requested through a COREOPS ticket. Read-only token: announced in November with its report, switched on in December. 43 workflow files in 25 repos rely on the write default today, but only three actually write (release workflows in gateway-cli, document-auditor and survey-library); they add one permissions line. No workflow approves PRs today, so that part breaks nothing.

## 6. A baseline every repo gets automatically, and less surface to attack

*Q4 2026 · guardrails and cleanup*

- **PR required on `main`**: One org rule for every repo's default branch: changes go through a pull request, no force-push. Repos can add stricter rules. November

- **Dependabot everywhere**: Vulnerability alerts and fix PRs in all 771 active repos, with a named triage owner. November

- **Old cluster credentials gone**: Nine unused AWS and Kubernetes secrets removed: keys deactivated first, deleted after two quiet weeks. November

- **Unused features off**: Wikis, issues and projects off where nobody uses them: 568 wikis, 607 issue trackers. In-use ones untouched. November

- **Only owners create public repos**: Members still create private repos; a public one needs an org owner. November

- **App access narrowed**: Five third-party apps can reach every repo. Each is narrowed, or justified, with its owner. December

**Speaker notes:** ⏱ 1.5 min. Move quickly; leads can read the detail in the Jira stories. Org rule: today there are no org-level rules, so protection depends on each team remembering. One rule covers every repo's default branch, including new repos: pull request required, no force-push, no deletion. It's switched on directly in November, with no trial period, so teams with automation that pushes straight to main need to tell us before then. The existing break-glass path on the github-actions repo is kept. Dependabot is free on our plan; expect a burst of alerts at first, which is why a triage owner is named before it goes on. AWS keys: nothing uses them, but they're deactivated first because deleting can't be undone. Unused features: turning a feature off hides it but deletes nothing, and any repo with even one wiki page or issue is left alone. Apps: aws-connector-for-github, atlassian, microsoft-teams-for-github, claude-design-import and aws-devops-agent-read-only can reach every repository; this one is reviewed with each app's owner and goes last.

**Speaker notes:** ⏱ 1.5 min. Q1 is planned: these come from the security review's backlog and don't have an epic yet. 2FA is the one item that removes people, so it gets the most notice. GitHub's enforcement removes any member or outside collaborator without 2FA; they can be reinstated within three months, but it's disruptive. So starting in Q4, well ahead of the deadline, everyone, including outside collaborators (who aren't on our internal channels), is told the deadline with instructions for setting up 2FA, and a weekly list of who still hasn't is followed up until it's near zero. The rest: 16 people are org owners, who can bypass almost every control, so that comes down to about 10. The Claude review workflow in 16 repos reads instructions from the PR's own branch while holding write access; it'll read them from the base branch instead. 78 repos haven't been pushed to in two years. There are no self-hosted runners today, but the default runner group would expose the first one to every repo, so it gets locked down before anyone adds one.

## 11. Access through teams, on standard accounts

*What we propose [proposed · not yet planned]*

- **Standard accounts**: About 80 people rename in place and keep their history. 20 accounts that look personal are replaced. Contractors are marked `-ctr`.

- **One team pattern**: Per product: a dev team with write, and a maintainers team under it. Every team has a named owner, and every repo a CODEOWNERS file naming its team.

- **Access through teams**: 194 times, someone was added to a repo individually with access their team already gives them. Those go first, changing nothing. The rest move into product teams.

- **Repos start with an owner**: You request a repo through a self-service front door, and an App creates it with its teams, CODEOWNERS and the baseline.

- **Clean up**: Unused teams removed. Repos with no owner get an owning team, or are archived.

- **Outside collaborators sponsored**: Staff become members. The rest get a named sponsor and an end date. A monthly check flags new ones.

**Speaker notes:** ⏱ 1.5 min. This is the direction, not a commitment: no epic, no dates. Standard accounts: a GitHub username can be changed in place, so most people keep everything, including their commit history; the 20 accounts that look personal need a new company account instead. We call them personal from the username alone, since GitHub doesn't show us the email behind an account; a few may turn out to be company accounts with the wrong name, and those just rename. One team pattern: each product gets a dev team with write, and a maintainers team under it with maintain; no team gets admin, which is the next slide. Read for everyone else comes from the org-wide engineering team, kept read-only. Every team has a named owner managing its members, which 30 teams lack today. CODEOWNERS: only 175 of 776 active repos have one today, so most repos have no named owner for review; every repo gets one, naming its team. Access through teams: 194 times, someone was added to a repo individually with access their team already gives them; for instance, added with write to a repo their team already has write on. Removing those changes nothing, so they go first. The other personal grants move into the product teams. Repos start with an owner: today any member can create a repo and becomes its admin, which is where most of the personal admin grants come from. Instead, the person who needs a repo requests it through a self-service front door, and an App creates it with its teams, a CODEOWNERS file and the baseline already in place. Nobody creates repos by hand, DevOps included. It's proposed, not built, and it's what the next two slides depend on. Clean-up: the unused teams, and the 117 repos nobody owns. Outside collaborators: on our GitHub plan we can't stop repo admins inviting them, so the control is sponsorship plus a monthly read-only check. What it will ask of people: rename an account if asked, and leads naming a maintainer for each team. Questions about this part are welcome now, but it'll come back as its own plan.

## 12. Nobody gets repo admin, by default

*What we propose · the access model [proposed · not yet planned]*

#### Who gets what

| Who | On repos |
|---|---|
| Org owners (about 10) | **Admin** on every repo, through their org role |
| All engineers | Read, through the org-wide engineering team |
| A product's dev team | Write on its repos |
| Its maintainers team | Maintain |
| A product's admins team | Admin, only on repos that deploy from GitHub, and only if needed |
| GitOps and infrastructure repos | Every merge approved by the owning team and DevOps |
| Individuals | Nothing directly; access comes through a team |

#### Admin-only, done on request

- Granting access: people, teams, outside collaborators
- Branch protection and rulesets
- Deployment environments and their secrets
- Webhooks and deploy keys
- Visibility, archiving, deleting, transferring

> Maintainers keep the day-to-day: merging, releases, most settings, Actions secrets and deploys.

**Speaker notes:** ⏱ 1.5 min. The default is that no team and no person gets admin on a repo. Org owners already have admin everywhere through their role, and Q1 brings them down to about ten. We're not proposing an org-admin team: it would be a second, less visible owner group. Maintain is the highest role a team normally gets. It covers what leads do every day: merging, releases, repo settings like merge options and topics, and Actions secrets and deploys, which only need write. What it can't do is exactly what went wrong in the findings: it can't grant access, so a maintainer can't add an outside collaborator; it can't weaken branch protection or rulesets; and it can't delete, archive, transfer or change visibility. Those, plus webhooks and deploy keys, become a request. The exception is deployment environments, which need admin. Most of our deploys go through GitOps, not Actions; only the Windows, GovCloud and Azure deploys run from Actions. Where one of those needs a team to manage its environment, the product gets a small admins team: one to three named people, admin only on the repos that deploy, and reviewed each quarter. DevOps sets the environments up as part of migrating those repos. GitOps and infrastructure repos are different: a merge there is a deploy or an infrastructure change. Today the main GitOps repos already require a code-owner review, but about 312 people can write to them, so the CODEOWNERS file is the real gate, and every merge needs the owning team and DevOps. On our plan there's no in-between role: custom repository roles need Enterprise Cloud, so it's maintain or admin.

## 13. Three steps, so nobody is blocked

*What we propose · getting there [proposed · not yet planned]*

- **1. Admin moves into teams**: Personal grants fold into each product's teams. Maintainers keep admin for now, so nothing breaks.

- **2. Build the request paths**: One front door, signed in with Okta, for new repos and access changes. Every repo gets a CODEOWNERS file.

- **3. Drop to maintain**: Members can no longer create repos; only the App does. Maintainers drop to maintain; an admins team only where a deploy needs one.

> The repo-creation App is the dependency. Step 3 waits until it works.

**Speaker notes:** ⏱ 1.25 min. We don't take admin away first. Step one moves the roughly thousand admin grants on active repos, today spread across people and teams, into one maintainers team per product. Maintainers keep admin for now, so nobody loses the ability to do their job; the gain is that admin becomes a short, named list per product instead of a thousand scattered grants. Step two builds the request paths: one front door, an internal app behind AVA so people sign in with Okta, where you ask for a new repo or an access change. It doesn't change GitHub itself; it opens a pull request to the github-org-config repo, where our GitHub Apps are already managed, and after review a repo-creation App makes the change. That's also when every repo gets a CODEOWNERS file: the App adds one to every new repo, and existing repos get one through a pull request. Step three only happens once the App works: we turn off repo creation for members, which today makes every creator an admin, and maintainers drop to maintain. Products that deploy from Actions and need an environment get their small admins team then. While admin is still in place, a monthly read-only check flags new outside collaborators and new personal admin grants, so nothing grows back unseen. And the Q4 org rule already stops repo admins from removing the pull-request requirement on main.

## 14. Every GitHub account tied to an Okta identity

*What we propose · joining and leaving [proposed · not yet planned]*

#### One way in, one way out

- **Joining:** through the front door, signed in with Okta. It checks the username against the standard and records which Okta person owns which GitHub account.
- **Leaving:** when an Okta account is deactivated, the matching GitHub account is removed from the org.
- **A daily check:** flags anyone in GitHub with no Okta owner, and anyone whose Okta account is no longer active.

#### Not SSO, but most of the benefit

|  | SSO + SCIM<br>Enterprise Cloud | Front door<br>our Team plan |
|---|---|---|
| Each account tied to a person in Okta | ✓ | ✓ |
| Removed when someone leaves | Immediately | Within a day |
| Okta needed to sign in to GitHub | ✓ | ✗ GitHub login and 2FA |
| Extra licence cost | Yes | None |

> Leaving Okta means leaving GitHub: within a day, not the moment the account is deactivated.

**Speaker notes:** ⏱ 1.25 min. Today nothing removes a leaver from GitHub unless someone remembers; the security review rates that High. The usual fix is SSO plus SCIM. SSO makes you sign in to GitHub through Okta. SCIM is the standard way Okta creates and removes accounts in another system automatically: deactivate someone in Okta, and their account goes. On GitHub both need Enterprise Cloud, which isn't part of this plan. The front door gives us most of the SCIM half on the Team plan. Everyone joins through it, signed in with Okta, so we record which Okta person owns each GitHub account. When Okta deactivates someone, we know which GitHub account to remove. What it doesn't give us is the sign-in half: people still sign in to GitHub with their GitHub login and 2FA, so between deactivation and removal a leaver's account, tokens and SSH keys still work. A daily check keeps that to a day at first; an Okta hook can bring it down to minutes later. Two conditions make it hold. Everyone already in the org gets matched to their Okta identity once, which fits with the account renames. And the front door has to be the only way in: the daily check also flags anyone added another way, such as an owner inviting someone by hand or an admin adding an outside collaborator, and removing repo admin closes most of those paths.
