## 2. GitHub's settings now protect every pipeline

*Why now*

- **The Actions migration**: Every pipeline becomes a GitHub workflow, with our code, secrets and AWS roles.

- **Open defaults**: GitHub favours convenience. Ours were never tightened, across ~800 active repos.

- **A real attack**: March 2025: a moved `tj-actions` tag ran attacker code in thousands of pipelines.

> **No new licences.** Everything in this plan runs on the GitHub Team plan we already pay for.

**Speaker notes:** ⏱ 1.5 min. The point: once CI lives in GitHub Actions, a workflow can reach our source, our secrets and our AWS roles, so the organization's Actions settings are now part of our security perimeter. GitHub ships with permissive defaults, and nobody had tightened ours; with about 800 active repositories, configuring them one at a time has left uneven coverage. The tj-actions/changed-files compromise in March 2025 is the example to remember: an attacker moved a version tag to point at malicious code, and every pipeline that referenced the tag ran it. We don't use that action, but nothing in our current settings would stop the same thing happening with one we do use. Every control in this plan is available on the Team plan, so there's no licence cost; the cost is configuration time, plus small edits in some repos.

**Speaker notes:** ⏱ 2 min. All numbers are from the scan of 9 November 2026, the same scan the two team reports were built from. Walk the six quickly. Movable tags: 190 "uses:" lines point at tags like @v4 rather than a fixed commit, and the org allows any action from any author. Write token: unless a workflow says otherwise, its GITHUB_TOKEN can push code and edit releases, and Actions is allowed to approve pull requests, which defeats a "requires approval" rule. Their values in GitHub haven't changed since 2022–23 (production 2022-08-23, staging 2023-02-28, develop 2023-03-16). GitHub can't show a secret's value, so whether the keys were rotated or disabled in AWS itself is the first thing the cleanup checks. Every private repo's workflows can read them, and no workflow uses them. None of this is anyone's mistake; these are GitHub's defaults.

## 5. Control what runs in CI, and what it can touch

*Q4 2026 · secure the CI supply chain*

- **Pin every action**: An exact commit can't be moved. Teams get a report with the fix first. Announce: November 
Enable: December

- **Approved actions only**: Ours, GitHub's, and the 22 third-party actions in use today. New ones by request. November

- **Read-only token**: Read access unless a workflow asks for more; no PR approvals. 3 workflows need one line. Announce: November 
Enable: December

**Speaker notes:** ⏱ 2 min. These three close the tj-actions class of attack. Pinning: a tag like @v4 can be moved by whoever controls the action; a 40-character commit SHA can't. A report goes to the 46 affected repos with the exact replacement for every line, and Dependabot keeps pins current; DevOps adds its configuration when each repo moves to GitHub Actions, so teams don't add it themselves. Pinning is announced in November, with the report, and required org-wide in December, which gives the 46 repos a month to pin. Repos that are already fully pinned (55 of them) can get the requirement first, so they can't slip back. The approved-actions list lands in November. GitHub's rule covers its own actions too; reusable workflows are exempt. Approved actions: VectorLearning's own and GitHub-authored actions are allowed, plus a named list of 22 third-party actions, split between vendors (AWS, Docker, Microsoft, HashiCorp, Anthropic, Google, Astral, Veracode) and four individual maintainers. Four retiring actions stay allowed until 31 January 2027. No wildcards; we can loosen later. New actions are requested through a COREOPS ticket. Read-only token: announced in November with its report, switched on in December. 43 workflow files in 25 repos rely on the write default today, but only three actually write (release workflows in gateway-cli, document-auditor and survey-library); they add one permissions line. No workflow approves PRs today, so that part breaks nothing.

## 6. A baseline every repo gets automatically, and less surface to attack

*Q4 2026 · guardrails and cleanup*

- **PR required on `main`**: One org rule for every repo's default branch: changes go through a pull request, no force-push. Repos can add stricter rules. November

- **Dependabot everywhere**: Vulnerability alerts and fix PRs in all 771 active repos, with a named triage owner. November

- **Old cluster credentials gone**: Nine unused AWS and Kubernetes secrets removed: keys deactivated first, deleted after two quiet weeks. November

- **Unused features off**: Wikis, issues and projects off where nobody uses them: 568 wikis, 607 issue trackers. In-use ones untouched. November

- **Only owners create public repos**: Members still create private repos; a public one needs an org owner. November

- **App access narrowed**: Five third-party apps can reach every repo. Each is narrowed, or justified, with its owner. December

**Speaker notes:** ⏱ 1.5 min. Move quickly; leads can read the detail in the Jira stories. Org rule: today there are no org-level rules, so protection depends on each team remembering. One rule covers every repo's default branch, including new repos: pull request required, no force-push, no deletion. It's switched on directly in November, with no trial period, so teams with automation that pushes straight to main need to tell us before then. The existing break-glass path on the github-actions repo is kept. Dependabot is free on our plan; expect a burst of alerts at first, which is why a triage owner is named before it goes on. AWS keys: nothing uses them, but they're deactivated first because deleting can't be undone. Unused features: turning a feature off hides it but deletes nothing, and any repo with even one wiki page or issue is left alone. Apps: aws-connector-for-github, atlassian, microsoft-teams-for-github, claude-design-import and aws-devops-agent-read-only can reach every repository; this one is reviewed with each app's owner and goes last.

## 7. 2FA becomes mandatory at the end of January

*Q1 2027 · identity and access [planned]*

**2FA enforcement**

184 members

plus 9 outside collaborators have no 2FA today. Enforcement **removes them from the org**.

- Starting in Q4: everyone is told the deadline and how to set up 2FA; whoever still isn't set up is followed up weekly
- First, 4 bot accounts used by CI (Jenkins, CircleCI, the CI bot, Convergence) move to GitHub Apps; otherwise enforcement removes them and their pipelines break

#### Also in Q1

- Org owners: 16 → about 10
- Claude review workflow hardened in 16 repos
- 78 repos untouched for 2+ years archived, with owners consulted
- Runner groups locked down before the first self-hosted runner

**Speaker notes:** ⏱ 1.5 min. Q1 is planned: these come from the security review's backlog and don't have an epic yet. 2FA is the one item that removes people, so it gets the most notice. GitHub's enforcement removes any member or outside collaborator without 2FA; they can be reinstated within three months, but it's disruptive. So starting in Q4, well ahead of the deadline, everyone, including outside collaborators (who aren't on our internal channels), is told the deadline with instructions for setting up 2FA, and a weekly list of who still hasn't is followed up until it's near zero. Four of the accounts without 2FA are machines (targetsolutions-jenkins, vectorcibot, vectorehs-circlecimachine and ConvergenceServiceAccount); they move to GitHub Apps or other non-password auth before enforcement, otherwise their pipelines fail the moment it's switched on. The rest: 16 people are org owners, who can bypass almost every control, so that comes down to about 10. The Claude review workflow in 16 repos reads instructions from the PR's own branch while holding write access; it'll read them from the base branch instead. 78 repos haven't been pushed to in two years. There are no self-hosted runners today, but the default runner group would expose the first one to every repo, so it gets locked down before anyone adds one.

## 8. Most teams do nothing; a few make small changes

*What it asks of teams*

#### Who needs to act

- **Everyone:** turn on 2FA before the end of January
- **46 repos:** pin actions before December, using the report's exact SHAs
- **3 repos:** add one `permissions:` line to a release workflow (report)
- **3 repos:** replace 4 retiring actions by 31 January
- **Automation that pushes to `main`:** tell us before the rule is switched on

#### How we'll know it worked

| Measure | Today | Target |
|---|---|---|
| Unpinned action references | 190 | 0 |
| Repos without branch protection | 425 | 0 |
| Repos with Dependabot | 34 | 771 |
| Unused AWS and Kubernetes secrets | 9 | 0 |
| Members without 2FA | 184 | 0 |

**Speaker notes:** ⏱ 1.5 min. For leads: the only thing every person must do is set up 2FA. The rest is a short list of named repos, and each gets a report with the exact change. The 46 pinning repos and the 3 permissions repos are listed in the two team reports on Confluence, linked on this slide and on slide 5. The retiring actions are in survey-library, devsec and document-auditor. If a bot or job in your repo pushes straight to main (version bumps, generated files), tell us before the rule is switched on in November so we can move it to a PR or let its GitHub App through. A written announcement with the details goes out to teams. For leadership: these five numbers are what we'll report against; they come from the same scan we'll re-run after each change, so progress is measured, not assumed.
