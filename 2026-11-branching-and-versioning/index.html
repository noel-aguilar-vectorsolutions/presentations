Why the choice matters

One strategy per repository, and it rarely changes

A module is a folder versioned and released as one unit: one version, one line of tags. By default it's the whole repository; a monorepo has several. A repository uses one strategy for all its modules, and none is the default.

1

Is every merge a release candidate, or do you collect features and plan a release?

Every merge: Continuous versioning. Collect and plan: release-please.

2

release-please: do you keep merging to main while a version is in regression?

Yes: release branches.

3

release-please: must you hotfix production without shipping unreleased work?

Often: release branches. Rarely: plain.

Cut release branches today? That's release-please with release branches. Continuous versioning has none.

⏱ 1.25 min. Source: cicd-standards docs/ci/versioning.md, "Which versioning strategy should a repository use?" and "What is a module?". A module is a folder of the repository versioned and released as one unit: one version, one line of tags (v1.2.0, or echo@v1.2.0 in a monorepo). It may produce several images; it is not an image, a .NET project or a Helm chart. With no configuration, the module is the whole repository. The first question splits the two models: Continuous versioning makes every build on main a release candidate as it lands; release-please collects features or epics in a release PR and someone decides when to cut. Questions 2 and 3 only apply under release-please, and choose between its two strategies. A team that cuts release branches by hand today lands on release-please with release branches; Continuous versioning never has release branches. A repository MUST use exactly one strategy, for all its modules. Between plain release-please and release branches, switching is one PR (the caller workflow and config files), once live release or hotfix branches are finished or deleted. Between Continuous versioning and release-please, the tags are compatible by design, but no repository has made that move yet. So in practice teams rarely switch once they've started. That's why it's worth deciding deliberately now. Keep these questions in mind: every strategy slide comes back to them, and the decision flow after the scenarios turns them into a choice. Ask the room to think about how their team handles regression today.

Recap

Squash merge: one PR, one commit, one title

  • Branch commits (wip, fix typo) never reach main
  • The PR title becomes the commit's title on main
  • Every strategy reads its versions from those titles
⏱ 1 min. A refresher from October, but it matters more than it looked then: everything in this session depends on it. With a merge commit, every commit on the branch lands on main, and a tool reading titles would see "wip" and "fix typo". With squash, main gets one commit per PR, titled by the PR. The repository setting is squash only, with the PR title and description as the commit message, so footers in the description (BREAKING CHANGE:, Release-As:) reach main too. Your branch commits can be as messy as you like.

⏱ 1.75 min. Source: cicd-standards versioning.md, "How must pull request titles be written?" and "Which types should a title use?". The rule is a MUST: pull request titles MUST be Conventional Commits, and a required pull request title check MUST enforce it (PR / Lint PR title, from the pr-title.yml template). Why it's a must: squash merge makes the PR title the commit on main (slide 4), and every strategy computes the version from those titles. Format: type, an optional scope in brackets, an optional ! for a breaking change, a colon and a space, then the summary. Four types are recommended so nobody has to remember the rest: feat, fix, chore, docs. The check accepts every Conventional Commit type, but use chore: in place of build:, ci:, test:, refactor: and style:, and fix: for perf:. A scope is free text; teams often put the Jira key in the summary or scope. Claude Code (or any assistant) writes a good title from the diff in seconds if someone is unsure. Then the table, what each type does to the version. Source: versioning.md, "Which types should a title use?". The question is: does the change alter what the service does for the people who use it? A dependency bump is chore(deps):, or fix(deps): when it fixes a CVE, even when it's only a version number, so it releases and the changelog lists it. Retitle a Dependabot security PR fix(deps): before merging. The "none under release-please" column is a preview: under Continuous versioning, a chore: that changes a module's files still ships a patch. Once a title is a commit on a protected branch it can't be edited; retitling a merged PR changes nothing.

Recap

Not merged = not shipped

  • Anything merged to main is in the next version: the very next one under Continuous versioning, the next release PR under release-please
  • Work that isn't ready stays unmerged, or is merged behind a feature flag that's off
  • A merged change only comes out with a revert: PR

This is what a hotfix runs into: whatever is on main ships with it, unless the strategy gives you another branch.

⏱ 1 min. Source: versioning.md, "What must not be merged to main?". This is the rule the rest of the session builds on. A revert takes the code out, but it doesn't cancel the original commit's effect on the version, or, with release-please, its line in the changelog. The callout sets up the second of our two questions: if main has unreleased work and production needs a fix today, the strategy decides whether you can ship the fix alone.

⏱ 1.75 min. The core slide. Sources: versioning.md's comparison table; versioning-release-please.md, "Why does main never release a patch version?", "What if a feature lands on a release branch?" and "How is a breaking change released?". Release branches come on slide 26: each minor version gets a branch, release/X.Y.x, that cuts its patches; this slide previews their rules. Walk it column by column. Continuous versioning and plain release-please bump by type, the textbook way. With release branches, main uses always-bump-minor, a release-please setting: even a release holding only fixes is the next minor (why: slide 27). Each release branch uses always-bump-patch, so anything merged there, even a feat:, ships as the next patch; a job comments on the PR to warn, but doesn't block it. The cost of always-bump-minor is that a breaking change no longer becomes a major by itself: it needs Release-As: X.0.0, a footer line in a PR description that sets the next version, on a PR to main. The release PR version check, a required check on every release PR (release-please / release-pr-version-check), fails main's release PR until it's there. That check applies from 1.0.0 on; below 1.0 a minor is the right bump for a breaking change. A plain release-please team may choose always-bump-minor too, and then gets the same rule.

Continuous versioning

A patch means "a build shipped", not "a bug was fixed".

release-please

The type decides whether a change releases. Release-As: X.Y.Z forces a version, e.g. to ship a chore: alone.

⏱ 1.25 min. Sources: versioning.md, "Which types should a title use?"; versioning-continuous.md, "In the SemVer format"; versioning-release-please.md, "When may the proposed version be overridden?"; the how-to, "How do I release a docs or chore change on its own?". Continuous versioning: every build on main that ships changes what's deployed, so it needs a new version, even when the commits don't call for one. "The module's files" are its folder and its extra-paths (other folders it's built from, listed in version-config.json), minus Markdown, docs/ and .github/, so a docs-only change builds nothing and cuts nothing. release-please: docs: and chore: wait for the next feat: or fix:. When one must reach production first (a CVE bump merged as chore(deps): by mistake, say), put "Release-As: 1.4.3" (the next patch) on its own line at the end of a PR description; release-please proposes that version. Release-As is the only correction after a merge. With release branches, main never releases a patch: put the footer on the release branch the production version came from, release/1.4.x, and merge its forward-port. On main, Release-As must be higher than every version tag in the repository, and, with release branches, a new minor or major. With plain release-please and unreleased work on main, the change goes on a hotfix branch.

⏱ 0.75 min. Sources: versioning-continuous.md, "Where does the version live?"; versioning-release-please.md, "Which release type should I use?" and the caution in "What happens when the release PR merges?". Continuous versioning: the version lives in git tags only; nothing reads a version from files in the repository or writes one to them, and a committed <Version> in a .csproj from an earlier pipeline MUST be deleted. release-please: every service MUST use release-type simple, whatever its language, which writes only the manifest, CHANGELOG.md and an existing version.txt; a language type (node, maven) only for a service that opts in to its stack's workspace plugin, and that file is then one release behind the image. Why files can't be trusted: under release-please the image is built from the merged commit before the release PR merges and re-tagged at release, never rebuilt; under Continuous versioning the build doesn't stamp it. So an application MUST NOT take its version from a file in the image (package.json, pyproject.toml, the POM, a .csproj, version.txt). One that reports a version, in a health endpoint, logs or an error tracker, gets it from the deployment, for example an environment variable set from the image tag in the GitOps manifest; how exactly is for the CI → GitOps Handoff standard (Planned). The commit SHA is known at build time and may be baked in. Python is the same case as every other stack: a service declares no version in pyproject.toml. How to remove it without breaking the package manager (uv: dynamic version and package = false; Poetry: package-mode = false) is in cicd-standards #36. If a team wants the version visible in source, release-please's extra-files can write it, keeping release-type simple. Libraries are the exception because the version is part of the artifact: node writes package.json; .NET passes it to dotnet pack; a Python library carries it in pyproject.toml.

Strategy 1 of 3

Continuous versioning

Every merge to main that builds is a release candidate, tagged as it lands.

No release PR and no release branches: main is the only long-lived branch.

⏱ 0.25 min. Section opener. Say the one line, then move on: the next slides show how it works, then the live demo.

Continuous versioning

main only: every merge that builds is a version

  • Topic branches build <branch>-<run> images, never a version
  • On main: compute the version, push image 1.4.0, then tag v1.4.0
  • Only changed modules build; a docs-only change builds nothing
⏱ 1.25 min. Source: versioning-continuous.md, "How does Continuous versioning work, end to end?". One workflow, ci.yml, calling app-ci. Its first job, Plan builds, runs compute-versions: which modules did this push change, and, on main, what's each one's next version, from the PR titles merged since that module's last tag. Each changed module is built once, tested and scanned as built, and only then pushed; on main, the git tag is created last, so a tag never points at a version whose images are missing or untested. A change that touches no module (docs, workflows, a chart outside the module folder) builds nothing. Main builds run one at a time, so versions are cut in order.

Continuous versioning

Git tags are the whole record

You get

  • A version per merge, computed from the titles
  • Only changed modules built and tagged
  • One version line per module in a monorepo

You don't get

  • A release PR to batch changes
  • CHANGELOG.md or a GitHub Release
  • A branch to hotfix production on

Hotfix while main has unreleased work: not covered. The fix ships with everything merged before it.

⏱ 1.25 min. Source: versioning-continuous.md, "Known limitations". No changelog or GitHub Release is generated: the git tags are the record of versions, and the Promotion Manager the record of what was released. The hotfix gap follows from "not merged = not shipped": every merge to main is the next version, so a fix can't skip work already merged. A team that needs that uses release-please with release branches. In practice this works for a team that keeps main releasable: small PRs, feature flags for unfinished work. Also a limitation: version tag creation isn't restricted (they're created with GITHUB_TOKEN), only moving and deleting them is blocked.

Continuous versioning

Fits a team that ships each change as it lands

It fits

  • Each merged change goes to staging on its own
  • main is kept releasable: small PRs, feature flags
  • A service monorepo whose modules share files or code directly (extra-paths)

The files

  • version-config.json: the modules, their format (semver), extra paths
  • build-config.json: what each module builds
  • ci.yml: calls app-ci, copied as-is
⏱ 1.25 min. Sources: versioning.md, "Which model for a repository with several modules"; versioning-continuous.md, "What must a repository have?". The monorepo point matters: under Continuous versioning, a module lists whatever else it builds from in extra-paths (a shared entrypoint.sh, a library referenced directly), and a change to it cuts a version of every module that lists it. release-please can't do that (see the gotchas). Files only named, never opened: the set-up how-to (docs/how-to/set-up-continuous-versioning.md) walks through them. The pilot, poc_echo_server_dotnet, is what demo 1 uses.

Strategy 2 of 3

Plain release-please

Merges collect in a release PR; merging it cuts the version.

main is the only long-lived branch; a hotfix/X.Y.x appears only when production needs one.

⏱ 0.25 min. Section opener. Say the one line, then move on: the next slides show how it works, then the live demo.

Plain release-please

Merging the release PR cuts the version

  • Feature branches come off main; each merge builds main-<run>, no version
  • Merging the release PR tags vX.Y.Z and writes a GitHub Release
  • Hotfix button: hotfix/X.Y.x from the production tag, only if main moved on; fix branches come off it
⏱ 1.25 min. Source: versioning-release-please.md, "How does plain release-please work?" and "Hotfix branches". After every releasable merge (feat:, fix:, a breaking change), release-please updates one standing release PR with the next version and its changelog. Nothing is cut until a person merges it: anyone with merge rights merges main's release PR, since it goes to staging first. A hotfix branch is rare: if nothing has merged to main since the production version was cut, the hotfix goes on main like any fix. Only when main has unreleased work does the Technical Owner (the project lead, or whoever decides for the repository) press the hotfix button, Actions → release-please → Run workflow, with the production tag; the workflow creates hotfix/X.Y.x from it. The fix branch is cut from hotfix/X.Y.x, not from main, and goes back into it by PR, squash-merged like every other change. Seconds after the fix merges, the forward-port job opens its port back to main: a forward-port is a PR that carries the same change to main. Only the Technical Owner merges the branch's release PR, which cuts the next patch, because it goes to production. While the hotfix branch exists, main can't release on its line: the version check blocks it, so main's next release is a minor (with only fixes on main, the check asks for a Release-As).

Plain release-please

The tested image gets the version: no rebuild

Re-tag

The release adds 1.4.0 to the image main already built and tested, main-412: same digest.

Changelog

CHANGELOG.md and a GitHub Release, written from the PR titles.

You decide when

Nothing is cut until a person merges the release PR.

Build once, promote many: what regression tested is byte for byte what ships.

⏱ 1.25 min. Source: versioning-release-please.md, "What happens when the release PR merges?". The release commit (chore(main): release 1.4.0) only changes the manifest and CHANGELOG.md, so it builds nothing. The retag job walks back to the commit before it that built (normally its parent), waits for that build to finish, checks each image's org.opencontainers.image.revision label is that commit's SHA, and only then adds 1.4.0 to the same digest. It never falls back to "the newest image". The Promotion Manager sees 1.4.0 appear as a push and can promote it. The changelog is the benefit people remember: QA, support and product can read what's in a version without asking a developer.

Plain release-please

Fits a team that batches changes, and can hold merges

When regression fails

  • Fix it on main
  • Hold other merges, so the next version stays small
  • The next release PR replaces the failed version in staging

The files

  • release-please-config.json: release type, excluded paths
  • .release-please-manifest.json: the last version
  • release-please.yml: calls app-release-please.yml, which is the choice
⏱ 1.25 min. It fits a team that ships several changes together, on a schedule or after a round of regression, can hold merges while a version is in regression, and rarely patches an older version. Sources: versioning.md, "Which versioning strategy should a repository use?"; the how-to, "How do I fix a failed regression with plain release-please?". The next version after a failed 1.4.0 is 1.4.1, or 1.5.0 if a feature merged meanwhile, which is why you hold merges. The strategy is chosen by which reusable workflow the caller workflow, .github/workflows/release-please.yml, calls: app-release-please.yml for plain, app-release-please-release-branches.yml for release branches. release-please itself knows nothing about release branches. A service uses release-type simple, which writes only the manifest, CHANGELOG.md and version.txt if it exists. The repository settings and rulesets come from cicd-standards templates/release-please/, applied once during setup.

Plain release-please, plus a release/X.Y.x branch for every minor version.

release-please with release branches

Every minor version gets its own release/X.Y.x

  • Cutting X.Y.0 on main creates release/X.Y.x from its tag (the x is literal)
  • Fixes go on the release branch as patches; it's never merged back
  • Several can be live: production on 1.0.2, 1.1.0 in regression
⏱ 1 min. Source: versioning-release-please.md, "How do release branches work?". The x is literal: one branch per minor version, release/1.0.x holds 1.0.1, 1.0.2 and so on. The workflow (app-release-please-release-branches.yml) creates it, as the release App, right after main's release PR cuts X.Y.0: the release commit plus one commit with the branch's own config. Nobody creates one by hand. The release branch first stabilizes the version while it's in regression, then maintains it with hotfixes once it's in production, so there's no separate hotfix branch under this strategy. It's never merged into main: each fix reaches main by its own forward-port PR. Anyone with merge rights merges main's release PR; only the Technical Owner merges a release branch's release PR, because a patch can be a production hotfix. The Technical Owner deletes the branch once production runs a later minor. In industry terms: trunk-based development with branch-for-release. Teams that cut release/1.0.0 branches by hand today land here.

release-please with release branches

Forward-ports open themselves

A forward-port is an ordinary PR that carries one change from a release branch to main, reviewed and squash-merged like any other. Not a cherry-pick pushed straight to main, and never a merge of the release branch back.

  • Any PR merged into a release or hotfix branch: the release App opens a PR with the same title to main, and to each newer release branch
  • The developer merges each, or closes it saying why
  • A release PR is blocked while a port into its branch is missing
  • A change to a workflow file is labelled forward-port-needed and ported by hand
⏱ 0.75 min. Source: versioning-release-please.md, "What is a forward-port?". It copies the change, not the branch: nothing else on the release branch comes with it. Because it's a normal PR, it gets the same checks, review and squash merge as any other, and its title lands in main's changelog. Under the hood the action builds the port's branch with git cherry-pick, so if someone asks: yes, but the result is a PR that a developer reviews and merges, not a commit pushed onto main. Correction to the October deck, which said forward-ports were opened by hand until an action existed (COREOPS-4416). Now both release-please workflows run a forward-port job on every push to a release/** or hotfix/** branch (github-actions app-release-please-release-branches.yml and app-release-please.yml, release/forward-port). It cherry-picks the change onto a branch named forward-port/<source>/<pr>/<target> cut from the target, opens the PR as the release App with the original's title, labels it forward-port and asks the original author for a review. One change per PR, never bundled. Where it can't (a conflict, or a file under .github/workflows/, which the App has no permission to push), it labels the original forward-port-needed and its comment names the branch to use for the hand-made port. The release PR version check holds the target's release PR until every port is merged or closed. Demo 3 shows one, already open: it opened seconds after the fix merged into release/1.0.x, not when the release PR merged.

This answers our first question: can you keep merging to main while a version is in regression? Say 1.0.0 is in staging and fails. Continuous versioning: the fix merges to main, but whatever merged since goes along: feat: C already cut 1.1.0, so the fix is 1.1.1, with feat: C in it. Plain: the team held merges, so the next release PR is just the fix: 1.0.1 (or 1.1.0 if a feature slipped in). Release branches: the developer branches from release/1.0.x, fixes, merges back, and the forward-port to main opens itself seconds later; the Technical Owner merges that branch's release PR, 1.0.1, re-tested in staging. Meanwhile main merged two features and nobody waited. In all three, production goes straight from the version it runs to the version that passes.

Choosing

Three steps pick the strategy

None is the default. It's your team's call: switching later is doable, but it's work, so choose on purpose.

⏱ 1.25 min. Walk the flow left to right. Step (1) Is every merge a release candidate? Continuous versioning. If not, you collect features or epics and plan a release, so it is release-please, unless (2) the shape of the repository rules it out. Two boxes, not one question: a monorepo whose modules use shared code directly, from a folder in the repository, and deploy separately goes to Continuous versioning, because release-please releases a module only for changes inside its own folder, so a change to the shared code alone would release nothing. Everything else carries on to step 3: one module; a monorepo whose shared code is a published, versioned package; or a monorepo whose modules share code directly but deploy as one, one linked-versions group (slide 33). A team routed to Continuous versioning by step 2 gives up the hotfix path, so it keeps main releasable. (3) Must you keep merging to main while a version is in regression, or hotfix production without shipping unreleased work, often? Release branches; otherwise plain release-please. Ask the room: which box does your team land in? If a lead isn't sure between plain and release branches, the deciding question is how often the team needs to keep merging during regression. On switching: between plain and release branches it's one PR once live release or hotfix branches are finished; between Continuous versioning and release-please the tags are compatible by design, but no repository has made that move yet, so it's planned work, not a setting.

Epics that ship together

Integration branches: one commit per feature coming

  • Each feature branch is cut from integration/<EPIC> and squash-merged back into it, not into main
  • Ships with Rebase and merge: each feature keeps its own Conventional Commit, version bump and changelog line
  • The only PR into main that isn't squash-merged; needs ruleset changes first
⏱ 0.75 min. Source: the presenter's draft, "Integration Branch Workflow" (not yet a standard). Say up front: this is the direction we're heading, not a rule yet. The problem: some teams work on several epics at once, and an epic's features are incomplete without each other, so they can't merge one by one to main (anything merged to main ships in the next version). Squashing the whole epic into main would collapse every feature into one commit: one changelog entry, one bump, lost history. The idea: integration/PROJ-123, cut from the latest main. Each feature branch (feat/PROJ-201 and so on) is cut from the integration branch, and its PR targets the integration branch and is squash-merged back into it, each with a Conventional Commit title, so each feature is one commit. The branch is kept current by rebasing on main (Update branch → Update with rebase, or git rebase origin/main and git push --force-with-lease), never by merging main in, so its history stays linear. When the epic is ready: a final rebase, check the PR's commit list is one Conventional Commit per feature and no merge commits, then Rebase and merge, not squash; delete the branch. release-please then lists each feature separately and bumps by the highest. If someone squash-merges it by mistake, put a BEGIN_COMMIT_OVERRIDE … END_COMMIT_OVERRIDE block in the merged PR's description, one line per change, before the release PR merges: release-please uses those lines instead. Under Continuous versioning it works too, but gains less: the rebase-merge pushes the commits together, main builds once at the head and cuts one version, with the highest bump. What it needs before it's a standard: main allowing rebase merge (today every repository is squash-only, in the templates and the branch rulesets) and linear history; a ruleset for integration/** that is squash-only, linear, and allows force push for the rebase; and the PR-title check on PRs into integration/**. GitHub can't restrict a merge method to one PR, so once rebase is allowed on main, keeping it to integration PRs is discipline, or a required check that wants a rebase-merge label as a deliberate pause. Rebase and merge creates new commits, so rebuild from main; never promote an image built on the integration branch (build once, promote many still holds, from main). Not a release branch: a release branch stabilizes a version already cut; an integration branch holds work that hasn't reached main. Until this lands, the options are keeping the PRs unmerged or merging behind a feature flag that's off.

Rulesets and squash merge

Squash only: versions come from titles people reviewed

  • Continuous versioning (SemVer format): a merge commit in a module's range fails the build
  • release-please requires it, or wip and fix typo land in the changelog and can change the bump
⏱ 0.5 min. Sources: versioning-continuous.md, "What must a repository have?"; versioning-release-please.md, "Repository settings". How squash works was slide 4; this is why each strategy needs it. It's a repository setting, from templates/*/repository-settings.json: squash merging only, merge commits and rebase merging off, default commit message "Pull request title and description". The one exception is Continuous versioning's legacy four-part format, which may keep merge commits (slide 45). The templates also turn on "Automatically delete head branches".

Rulesets and squash merge

What the rulesets protect

  • Branches: PR and checks required, up to date, no direct or force pushes
  • Creating release/** and hotfix/**: the release App; a Technical Owner creates hotfix/** only when the button can't
  • Version tags: nobody moves or deletes them; under release-please only the App creates them
⏱ 1.5 min. Source: versioning-release-please.md, "What must a repository have?" (Repository settings); versioning-continuous.md for the CV differences. release-please: one branch ruleset template covers main, release/** and hotfix/**: pull request required; the PR-title check (PR / Lint PR title), the build (CI / CI result) and the release PR version check (release-please / release-pr-version-check) required, accepted only from GitHub Actions; branches up to date before merging; no direct or force pushes; nobody bypasses. Only the release App creates release/** (through the workflow); the App or a Technical Owner creates hotfix/** (a Technical Owner only when the hotfix button can't); only Technical Owners delete either. Tag rulesets on v* and *@v*: only the App creates version tags, and nobody updates or deletes them. Why tags matter so much: release-please finds its last release by the tag named in the manifest, so a moved or hand-made tag breaks the next version. Continuous versioning differs: its branch ruleset is on main only (it has no release or hotfix branches), and it creates tags with the workflow's GITHUB_TOKEN, so its tag ruleset blocks only updating and deleting.

Rulesets and squash merge

A person approves every PR, the release PR included

  • Code owner approval is required. The release App can approve a PR, but its approval never counts: the App is never a code owner
  • Technical Owners are named in CODEOWNERS, and in the ruleset that lets them delete release/** and hotfix/**

You don't write rulesets: cicd-standards templates/ has them, and the setup how-tos apply them.

⏱ 0.75 min. Sources: versioning-release-please.md, "Repository settings"; versioning-continuous.md, "What must a repository have?". Every repository on these strategies has a CODEOWNERS file naming its Technical Owners, and every PR needs a code owner's approval, the release PR included. A plain required approval isn't enough: the App can approve a PR, and that approval would count, and any workflow on any branch can mint the App's token, so anyone with write access could have their PR approve itself. Requiring a code owner closes that: the App is never one, so a person always approves. New commits dismiss earlier approvals; Update branch keeps them. Templates: templates/continuous-versioning/ and templates/release-please/, applied by docs/how-to/set-up-continuous-versioning.md and set-up-release-please.md. The demo repos have one approver, so approvals are off there; that is a demo shortcut, not the rule.

Gotchas

Merging under the up-to-date rule

  • After any merge, every other open PR needs Update branch
  • On a release PR, Update branch only after docs: or chore: merges; after a feat: or fix:, wait a minute for release-please
  • Never Update with rebase on a release PR
  • Blocked with every check green? The version check was cancelled: re-run it
⏱ 1.25 min. Sources: versioning-release-please.md, "Repository settings" and "Known limitations"; the how-to, "What if a release PR is blocked with every check green?". The up-to-date rule exists for the release PR (so it can only merge once it describes everything on the branch), but a ruleset can't single one PR out, so it applies to every PR into main, release/** and hotfix/**. That's the cost; the benefit is that every PR's checks ran against the exact code it merges into. After a feat: or fix:, release-please rewrites its PR, usually within a minute; Update branch before then makes the release PR mergeable with a version and changelog that leave the new change out (the version check catches it). After docs: or chore:, release-please leaves its PR alone, so Update branch is the way to unblock it. Update with rebase rewrites release-please's commit and the check fails it. The cancelled check: release-please pushes twice within a second, and GitHub sometimes cancels the newer run; open the cancelled release-please run for the release PR's branch and Re-run all jobs. The workflow fix is COREOPS-4698.

Gotchas

Versions you didn't expect

  • A fix: that changes only files the build skips cuts a version with no image: title it docs: or chore:
  • A revert is a new version under Continuous versioning, and stays in release-please's changelog
⏱ 0.75 min. Sources: versioning-release-please.md, "Known limitations"; versioning-continuous.md, "How is a revert versioned?". (1) The build ignores docs/, .github/, .circleci/, Markdown anywhere, LICENSE, build-config.json and release-please's own files; release-please only skips the folders in its exclude-paths. The template lists docs, .github and .circleci, so the common gap is a fix: touching only, say, a root README.md or build-config.json: release-please cuts a version, no build made an image, and the retag job fails. (2) A revert under Continuous versioning bumps like a chore: a patch. GitHub's own "Revert …" title isn't a Conventional Commit: retitle it revert:.

Gotchas

Branches, Releases and running images

  • Each live release or hotfix branch runs its own caller workflow: a library pin bump is a PR into each
  • The release App can't touch .github/workflows/: those changes are ported by hand, and the hotfix button refuses an older tag whose workflow files differ
  • GitHub's "Latest" release is the one created last, maybe a patch on an older line: use the environment's version
  • release-please monorepos: modules that share code directly must be one linked-versions group, and release together
⏱ 1.25 min. Source: versioning-release-please.md, "Known limitations". (1) A push to release/1.0.x runs release-please.yml as it is on that branch, so when the library pin moves on main, open a chore: PR into each live branch too. (2) The release App has no Workflows permission, on purpose, so it can't push anything under .github/workflows/: the forward-port job labels such a change forward-port-needed (slide 28), and GitHub refuses the hotfix job a branch at a commit whose workflow files differ from today's, which is usual for an older release; a Technical Owner then pushes the branch with the same config commit (the how-to has the steps). (3) The Releases API marks every new release Latest, and release-please can't turn it off. (4) release-please releases a module only for commits in its own folder, so a change only to shared code releases nothing; the build's shared-code guard fails such a reference. That shape fits Continuous versioning.

Legacy

The four-part format: don't start new ones legacy

What it is

  • X.Y.Z.N, e.g. 1.4.0.7284, from dynamo-config
  • Merge commits allowed
  • Not SemVer: npm can't publish it
  • N is the run number plus run-number-offset: renaming ci.yml breaks it

Moving to SemVer

  • Squash only
  • version-format: semver
  • initial-version above the last X.Y.Z: after v1.4.2.2087, 1.4.3 or 1.5.0

Shown, not demoed: poc_echo_server_dotnet_legacy's tags, such as v1.3.1.2019

⏱ 1.5 min. Say up front: this matters only if your repo came from dynamo-config; everyone else can relax for a minute. Source: versioning-continuous.md, "When may a repository use the four-part format?" and "How does a module move to SemVer?". It's Continuous versioning's build-metadata format, kept for repositories migrating from dynamo-config. The standard says it's legacy, not recommended, and will be deprecated in the future; no date is set, so don't promise one. A new repository should not use it; one that does states why in its README. X.Y.Z moves only for feat, fix, perf and breaking changes; anything else gets a new N. Why 1.4.3 and not 1.4.2: SemVer ranks 1.4.2 below 1.4.2.2087, so the first SemVer build fails without an initial-version above it. Remove initial-version once that first tag exists, and remove run-number-offset once no module uses the four-part format. If time allows, open poc_echo_server_dotnet_legacy's tags page.
