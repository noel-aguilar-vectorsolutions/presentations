## 3. One strategy per repository, and it rarely changes

*Why the choice matters*

A **module** is a folder versioned and released as one unit: one version, one line of tags. By default it's the whole repository; a monorepo has several. A repository uses **one strategy for all its modules**, and none is the default.

- **Is every merge a release candidate, or do you collect features and plan a release?**: Every merge: **Continuous versioning**. Collect and plan: **release-please**.

- **release-please: do you keep merging to `main` while a version is in regression?**: Yes: **release branches**.

- **release-please: must you hotfix production without shipping unreleased work?**: Often: **release branches**. Rarely: **plain**.

> Cut release branches today? That's release-please with release branches. Continuous versioning has none.

**Speaker notes:** ⏱ 1.25 min. Source: cicd-standards docs/ci/versioning.md, "Which versioning strategy should a repository use?" and "What is a module?". A module is a folder of the repository versioned and released as one unit: one version, one line of tags (v1.2.0, or echo@v1.2.0 in a monorepo). It may produce several images; it is not an image, a .NET project or a Helm chart. With no configuration, the module is the whole repository. The first question splits the two models: Continuous versioning makes every build on main a release candidate as it lands; release-please collects features or epics in a release PR and someone decides when to cut. Questions 2 and 3 only apply under release-please, and choose between its two strategies. A team that cuts release branches by hand today lands on release-please with release branches; Continuous versioning never has release branches. A repository MUST use exactly one strategy, for all its modules. Between plain release-please and release branches, switching is one PR (the caller workflow and config files), once live release or hotfix branches are finished or deleted. Between Continuous versioning and release-please, the tags are compatible by design, but no repository has made that move yet. So in practice teams rarely switch once they've started. That's why it's worth deciding deliberately now. Keep these questions in mind: every strategy slide comes back to them, and the decision flow after the scenarios turns them into a choice. Ask the room to think about how their team handles regression today.

## 4. Squash merge: one PR, one commit, one title

*Recap*

*Diagram:* A pull request branch, feat/DAR-102-search, has three messy commits: wip, fix typo and address review. Squash merge turns them into one commit on main, titled with the PR title, feat(search): add clear button (DAR-102) (#123), which makes the next version a minor one.

*Diagram labels:* main · feat/DAR-102-search · wip · fix typo · address review · squash merge · feat(search): add clear button (DAR-102) (#123) · one commit on main; its message is the PR title · next minor

- Branch commits (`wip`, `fix typo`) never reach `main`
- The PR title becomes the commit's title on `main`
- Every strategy reads its versions from those titles

**Speaker notes:** ⏱ 1 min. A refresher from October, but it matters more than it looked then: everything in this session depends on it. With a merge commit, every commit on the branch lands on main, and a tool reading titles would see "wip" and "fix typo". With squash, main gets one commit per PR, titled by the PR. The repository setting is squash only, with the PR title and description as the commit message, so footers in the description (BREAKING CHANGE:, Release-As:) reach main too. Your branch commits can be as messy as you like.

## 5. The PR title sets the version

*Recap*

| Title | Use it for | Bump |
|---|---|---|
| `feat:` | Something new for the people who use the service | minor |
| `fix:` | A correction, a performance fix, a CVE bump: `fix(deps):` | patch |
| `docs:` | Documentation only | none under release-please |
| `chore:` | Everything else: build, CI, tests, refactors, a routine `chore(deps):` | none under release-please |
| `feat!:`, or a `BREAKING CHANGE:` footer | A change callers must adapt to | major |

> A merged title can't be changed. **The PR-title check is the only cheap place to catch a wrong version.**

**Speaker notes:** ⏱ 1.5 min. Source: versioning.md, "Which types should a title use?". Any Conventional Commit type is allowed and the check accepts them all, but four are recommended so nobody has to remember the rest. The question is: does the change alter what the service does for the people who use it? Use chore: in place of build:, ci:, test:, refactor: and style:, and fix: for perf:. revert: stays the type for taking a merged change out. A dependency bump is chore(deps):, or fix(deps): when it fixes a CVE, even when it's only a version number, so it releases and the changelog lists it. Retitle a Dependabot security PR fix(deps): before merging. The "none under release-please" column is a preview: under Continuous versioning, a chore: that changes a module's files still ships a patch. Once a title is a commit on a protected branch it can't be edited; retitling a merged PR changes nothing.

## 6. A version tag marks a release candidate, not a release

*Recap*

- **Cut: a candidate**: The git tag `v1.4.0` is created. That build is now a release candidate, on its way to `staging`. Nothing is in production yet.

- **Released: in production**: The ArgoCD Promotion Manager promotes that same candidate to `production`.

> `1.4.0` fails regression, `1.4.1` passes, and production goes straight to `1.4.1`. Normal, in every strategy.

**Speaker notes:** ⏱ 0.75 min. Source: versioning.md, "When is a version cut, and when is it released?". This holds for all three strategies. Continuous versioning is not continuous deployment: every version it cuts is still only a release candidate. The Promotion Manager, not the tag list, is the record of what was released. A package published to CodeArtifact is the one exception (cut and released are the same event), but that's out of scope today.

## 7. Every image gets a build tag; only a version gets a git tag

*Recap*

| What was built | Image tag | Git tag |
|---|---|---|
| Branch `feat/DAR-102-search`, run 107 | `feat-DAR-102-search-107` | none |
| A version, `1.4.0` | `1.4.0` | `v1.4.0` |
| Moving tags | never: no `latest`, no `main` | never moved or deleted |

*A branch build's tag, `<branch>-<run>`, is on the image in the registry only. Which build gets the version differs by strategy: coming up.*

**Speaker notes:** ⏱ 0.75 min. Source: versioning.md, "How are builds tagged?" and "What do versions and version tags look like?". The branch name with each / replaced by -, then the workflow run number. Version tags are vX.Y.Z in git (the git convention, and release-please's default) and bare X.Y.Z on images and packages. A monorepo module's git tag carries its component: echo@v1.4.0. The difference by strategy, for later: under Continuous versioning, the build on main is tagged with the version it cuts. Under release-please, every build is branch-run, main included (main-412), and the version is added to that image at release.

## 8. Not merged = not shipped

*Recap*

- Anything merged to `main` is in the next version: the very next one under Continuous versioning, the next release PR under release-please
- Work that isn't ready stays unmerged, or is merged behind a feature flag that's off
- A merged change only comes out with a `revert:` PR

> This is what a hotfix runs into: whatever is on `main` ships with it, unless the strategy gives you another branch.

**Speaker notes:** ⏱ 1 min. Source: versioning.md, "What must not be merged to main?". This is the rule the rest of the session builds on. A revert takes the code out, but it doesn't cancel the original commit's effect on the version, or, with release-please, its line in the changelog. The callout sets up the second of our two questions: if main has unreleased work and production needs a fix today, the strategy decides whether you can ship the fix alone.

## 9. `MAJOR.MINOR.PATCH`: breaking, feature, fix

*SemVer*

- **MAJOR 2.0.0**: A breaking change: callers must change something

- **MINOR 1.5.0**: A new feature; nothing breaks

- **PATCH 1.4.1**: A fix; nothing new

> A monorepo has one version line per module, tagged `<component>@v1.4.0`.

**Speaker notes:** ⏱ 0.75 min. Source: versioning.md, "What do versions and version tags look like?". Starting from 1.4.0 in the examples. Tags are protected by rulesets so nobody can move or delete one (slide 38). Monorepo: under Continuous versioning, each module gets its own line, component@vX.Y.Z; under release-please, each package does, and a repository with several packages must use component tags. A single-module release-please repository uses plain vX.Y.Z by default, or may choose component tags: demo 2 uses echo@v…, demo 3 plain v…, so you'll see both.

## 10. Same PR title, different version

*SemVer, three ways*

| Title | Continuous versioning | Plain release-please | Release branches: `main` | Release branches: `release/X.Y.x` |
|---|---|---|---|---|
| `fix:` | patch | patch | **minor** (`always-bump-minor`) | patch (`always-bump-patch`) |
| `feat:` | minor | minor | minor | **patch**, with a warning on the PR: revert it (the default) or keep it on purpose |
| `feat!:` | major | major, unless the team sets `always-bump-minor` | needs `Release-As: X.0.0`; the version check fails without it | still a patch, with a stronger warning: majors come from `main` |

> Release branches change the rules on purpose: `main` cuts minors, each release branch cuts patches.

**Speaker notes:** ⏱ 1.75 min. The core slide. Sources: versioning.md's comparison table; versioning-release-please.md, "Why does main never release a patch version?", "What if a feature lands on a release branch?" and "How is a breaking change released?". Release branches come on slide 25: each minor version gets a branch, release/X.Y.x, that cuts its patches; this slide previews their rules. Walk it column by column. Continuous versioning and plain release-please bump by type, the textbook way. With release branches, main uses always-bump-minor, a release-please setting: even a release holding only fixes is the next minor (why: slide 26). Each release branch uses always-bump-patch, so anything merged there, even a feat:, ships as the next patch; a job comments on the PR to warn, but doesn't block it. The cost of always-bump-minor is that a breaking change no longer becomes a major by itself: it needs Release-As: X.0.0, a footer line in a PR description that sets the next version, on a PR to main. The release PR version check, a required check on every release PR (release-please / release-pr-version-check), fails main's release PR until it's there. That check applies from 1.0.0 on; below 1.0 a minor is the right bump for a breaking change. A plain release-please team may choose always-bump-minor too, and then gets the same rule.

## 11. The type decides how much, or whether

*SemVer, three ways*

| Title | Continuous versioning | Plain release-please | Release branches: `main` | Release branches: `release/X.Y.x` |
|---|---|---|---|---|
| `chore:` / `docs:` | **patch**, if it changes the module's files | **no release** | no release | no release |

- **Continuous versioning**: A patch means "a build shipped", not "a bug was fixed".

- **release-please**: The type decides **whether** a change releases. `Release-As: X.Y.Z` forces a version, e.g. to ship a `chore:` alone.

**Speaker notes:** ⏱ 1.25 min. Sources: versioning.md, "Which types should a title use?"; versioning-continuous.md, "In the SemVer format"; versioning-release-please.md, "When may the proposed version be overridden?"; the how-to, "How do I release a docs or chore change on its own?". Continuous versioning: every build on main that ships changes what's deployed, so it needs a new version, even when the commits don't call for one. "The module's files" are its folder and its extra-paths (other folders it's built from, listed in version-config.json), minus Markdown, docs/ and .github/, so a docs-only change builds nothing and cuts nothing. release-please: docs: and chore: wait for the next feat: or fix:. When one must reach production first (a CVE bump merged as chore(deps): by mistake, say), put "Release-As: 1.4.3" (the next patch) on its own line at the end of a PR description; release-please proposes that version. Release-As is the only correction after a merge. With release branches, main never releases a patch: put the footer on the release branch the production version came from, release/1.4.x, and merge its forward-port. On main, Release-As must be higher than every version tag in the repository, and, with release branches, a new minor or major. With plain release-please and unreleased work on main, the change goes on a hotfix branch.

## 13. `main` only: every merge that builds is a version

*Continuous versioning*

*Diagram:* Continuous versioning uses main only. Topic branches feat/DAR-102-search and fix/DAR-103-retry each build an image named after the branch and run, such as feat-DAR-102-search-107 and fix-DAR-103-retry-112, with no version. Each squash merge to main cuts a version at once: v1.4.0 for the feat, v1.4.1 for the fix, v1.4.2 for a chore, which is still a patch. A docs-only merge builds nothing and gets no version.

*Diagram labels:* main · v1.3.0 · feat/DAR-102-search · feat-DAR-102-search-107 · image, no version · v1.4.0 · feat: a minor · fix/DAR-103-retry · fix-DAR-103-retry-112 · v1.4.1 · fix: a patch · v1.4.2 · chore: still a patch · no tag · docs: builds nothing

- Topic branches build `<branch>-<run>` images, never a version
- On `main`: compute the version, push image `1.4.0`, then tag `v1.4.0`
- Only changed modules build; a docs-only change builds nothing

**Speaker notes:** ⏱ 1.25 min. Source: versioning-continuous.md, "How does Continuous versioning work, end to end?". One workflow, ci.yml, calling app-ci. Its first job, Plan builds, runs compute-versions: which modules did this push change, and, on main, what's each one's next version, from the PR titles merged since that module's last tag. Each changed module is built once, tested and scanned as built, and only then pushed; on main, the git tag is created last, so a tag never points at a version whose images are missing or untested. A change that touches no module (docs, workflows, a chart outside the module folder) builds nothing. Main builds run one at a time, so versions are cut in order.

## 14. Git tags are the whole record

*Continuous versioning*

#### You get

- A version per merge, computed from the titles
- Only changed modules built and tagged
- One version line per module in a monorepo

#### You don't get

- A release PR to batch changes
- `CHANGELOG.md` or a GitHub Release
- A branch to hotfix production on

> Hotfix while `main` has unreleased work: **not covered**. The fix ships with everything merged before it.

**Speaker notes:** ⏱ 1.25 min. Source: versioning-continuous.md, "Known limitations". No changelog or GitHub Release is generated: the git tags are the record of versions, and the Promotion Manager the record of what was released. The hotfix gap follows from "not merged = not shipped": every merge to main is the next version, so a fix can't skip work already merged. A team that needs that uses release-please with release branches. In practice this works for a team that keeps main releasable: small PRs, feature flags for unfinished work. Also a limitation: version tag creation isn't restricted (they're created with GITHUB_TOKEN), only moving and deleting them is blocked.

## 15. Fits a team that ships each change as it lands

*Continuous versioning*

**It fits**

- Each merged change goes to `staging` on its own
- `main` is kept releasable: small PRs, feature flags
- A service monorepo whose modules share files or code directly (`extra-paths`)

**The files**

- `version-config.json`: the modules, their format (`semver`), extra paths
- `build-config.json`: what each module builds
- `ci.yml`: calls `app-ci`, copied as-is

**Speaker notes:** ⏱ 1.25 min. Sources: versioning.md, "Which model for a repository with several modules"; versioning-continuous.md, "What must a repository have?". The monorepo point matters: under Continuous versioning, a module lists whatever else it builds from in extra-paths (a shared entrypoint.sh, a library referenced directly), and a change to it cuts a version of every module that lists it. release-please can't do that (see the gotchas). Files only named, never opened: the set-up how-to (docs/how-to/set-up-continuous-versioning.md) walks through them. The pilot, poc_echo_server_dotnet, is what demo 1 uses.

## 19. Merging the release PR cuts the version

*Plain release-please*

*Diagram:* Plain release-please. Each merge to main builds an image tagged main-10, main-11 and so on, and a release PR collects them. Merging it cuts v1.0.0 and re-tags the tested main-11 image. Production is on 1.0.x and needs a hotfix while main holds unreleased work, so the hotfix button creates hotfix/1.0.x from the production tag v1.0.0. A fix there releases v1.0.1 and is forward-ported to main, and the next release PR cuts v1.1.0.

*Diagram labels:* release PR · next release PR · main · main-10 · main-11 · v1.0.0 · re-tags main-11 · main-12 · feat: B, unreleased · main-13 · v1.1.0 · re-tags main-13 · main-14 · hotfix/1.0.x · fix: X · v1.0.1 · created by the hotfix button from v1.0.0, the production tag · forward-port

- `main` builds `main-<run>` images, with no version yet
- Merging the release PR tags `vX.Y.Z` and writes a GitHub Release
- The hotfix button cuts `hotfix/X.Y.x` from the production tag, **only** when `main` has moved on

**Speaker notes:** ⏱ 1.25 min. Source: versioning-release-please.md, "How does plain release-please work?" and "Hotfix branches". After every releasable merge (feat:, fix:, a breaking change), release-please updates one standing release PR with the next version and its changelog. Nothing is cut until a person merges it: anyone with merge rights merges main's release PR, since it goes to staging first. A hotfix branch is rare: if nothing has merged to main since the production version was cut, the hotfix goes on main like any fix. Only when main has unreleased work does the Technical Owner (the project lead, or whoever decides for the repository) press the hotfix button, Actions → release-please → Run workflow, with the production tag; the workflow creates hotfix/X.Y.x from it, and the fix goes in by PR. Seconds after the fix merges, the forward-port job opens its port back to main: a forward-port is a PR that carries the same change to main. Only the Technical Owner merges the branch's release PR, which cuts the next patch, because it goes to production. While the hotfix branch exists, main can't release on its line: the version check blocks it, so main's next release is a minor (with only fixes on main, the check asks for a Release-As).

## 20. The tested image gets the version: no rebuild

*Plain release-please*

- **Re-tag**: The release adds `1.4.0` to the image `main` already built and tested, `main-412`: same digest.

- **Changelog**: `CHANGELOG.md` and a GitHub Release, written from the PR titles.

- **You decide when**: Nothing is cut until a person merges the release PR.

> Build once, promote many: what regression tested is byte for byte what ships.

**Speaker notes:** ⏱ 1.25 min. Source: versioning-release-please.md, "What happens when the release PR merges?". The release commit (chore(main): release 1.4.0) only changes the manifest and CHANGELOG.md, so it builds nothing. The retag job walks back to the commit before it that built (normally its parent), waits for that build to finish, checks each image's org.opencontainers.image.revision label is that commit's SHA, and only then adds 1.4.0 to the same digest. It never falls back to "the newest image". The Promotion Manager sees 1.4.0 appear as a push and can promote it. The changelog is the benefit people remember: QA, support and product can read what's in a version without asking a developer.

## 21. Fits a team that batches changes, and can hold merges

*Plain release-please*

**When regression fails**

- Fix it on `main`
- **Hold other merges**, so the next version stays small
- The next release PR replaces the failed version in `staging`

**The files**

- `release-please-config.json`: release type, excluded paths
- `.release-please-manifest.json`: the last version
- `release-please.yml`: calls `app-release-please.yml`, which *is* the choice

**Speaker notes:** ⏱ 1.25 min. It fits a team that ships several changes together, on a schedule or after a round of regression, can hold merges while a version is in regression, and rarely patches an older version. Sources: versioning.md, "Which versioning strategy should a repository use?"; the how-to, "How do I fix a failed regression with plain release-please?". The next version after a failed 1.4.0 is 1.4.1, or 1.5.0 if a feature merged meanwhile, which is why you hold merges. The strategy is chosen by which reusable workflow the caller workflow, .github/workflows/release-please.yml, calls: app-release-please.yml for plain, app-release-please-release-branches.yml for release branches. release-please itself knows nothing about release branches. ## 26. `main` never releases a patch

*release-please with release branches*

- `always-bump-minor` on `main`: every release is the next minor, whatever the titles say
- `always-bump-patch` on each release branch: every release is the next patch

| After `v1.1.0`, merged | Branch | release-please's default | With the setting |
|---|---|---|---|
| only `fix:` PRs (forward-ports) | `main` | `1.1.1`: clashes with `release/1.1.x` | `1.2.0` |
| a `fix:` | `release/1.1.x` | `1.1.1` | `1.1.1` |
| a `feat:` (by mistake) | `release/1.1.x` | `1.2.0`: clashes with `main` | `1.1.1`, with a warning |
| a `feat!:` | `main` | `2.0.0` | `1.2.0`: add `Release-As: 2.0.0` |

> Each version line owns its numbers: `main` the minors, `release/1.1.x` the `1.1.*` patches.

**Speaker notes:** ⏱ 1 min. Source: versioning-release-please.md, "Why does main never release a patch version?" and "What if a feature lands on a release branch?". Walk the table top to bottom. Row 1: after 1.1.0 is cut, release/1.1.x exists and owns 1.1.1, 1.1.2 and so on. If main has only merged fixes, typically the forward-ports of fixes from the release branch, release-please's default would propose 1.1.1 for main too. always-bump-minor makes it 1.2.0. Row 2: the release branch's own fixes release as 1.1.1, as expected. Row 3: a feat: merged into a release branch by mistake would by default become 1.2.0, the version main will cut; always-bump-patch keeps it a patch, and the workflow warns on the PR so the Technical Owner can revert it. Row 4: the price, a breaking change on main still proposes a minor, so a major needs Release-As; the version check fails the release PR until it's there. release-please computes main's version from main alone and can't see release branches. Without always-bump-minor, main would propose 1.1.1 after 1.1.0, the very version release/1.1.x releases next; whichever merged second would find its tag taken, and that branch's changelog goes wrong. The workflow fails if main's config lacks always-bump-minor. The price, majors by Release-As (slide 10), is small: a major is a deliberate, rare event anyway.

## 27. Forward-ports open themselves

*release-please with release branches*

A **forward-port** is an ordinary PR that carries **one** change from a release branch to `main`, reviewed and squash-merged like any other. Not a cherry-pick pushed straight to `main`, and never a merge of the release branch back.

- Any PR merged into a release or hotfix branch: the release App opens a PR with the same title to `main`, and to each newer release branch
- The developer merges each, or closes it saying why
- A release PR is blocked while a port into its branch is missing
- A change to a workflow file is labelled `forward-port-needed` and ported by hand

**Speaker notes:** ⏱ 0.75 min. Source: versioning-release-please.md, "What is a forward-port?". It copies the change, not the branch: nothing else on the release branch comes with it. Because it's a normal PR, it gets the same checks, review and squash merge as any other, and its title lands in main's changelog. Under the hood the action builds the port's branch with git cherry-pick, so if someone asks: yes, but the result is a PR that a developer reviews and merges, not a commit pushed onto main. Correction to the October deck, which said forward-ports were opened by hand until an action existed (COREOPS-4416). Now both release-please workflows run a forward-port job on every push to a release/** or hotfix/** branch (github-actions app-release-please-release-branches.yml and app-release-please.yml, release/forward-port). It cherry-picks the change onto a branch named forward-port/\<source>/\<pr>/\<target> cut from the target, opens the PR as the release App with the original's title, labels it forward-port and asks the original author for a review. One change per PR, never bundled. Where it can't (a conflict, or a file under .github/workflows/, which the App has no permission to push), it labels the original forward-port-needed and its comment names the branch to use for the hand-made port. The release PR version check holds the target's release PR until every port is merged or closed. Demo 3 shows one, already open: it opened seconds after the fix merged into release/1.0.x, not when the release PR merged.

## 32. Monorepos work in both: shared code decides

*Side by side*

| Modules share code… | Continuous versioning | release-please (either strategy) |
|---|---|---|
| Not at all | ✓ | ✓ |
| As a published, versioned package | ✓ | ✓ a consumer bumps the version in its own folder, which releases it |
| Directly, released together | ✓ `extra-paths` | ✓ one `linked-versions` group: the modules and the shared folder share one version |
| Directly, released on their own schedules | ✓ `extra-paths` | ✗ a change only to the shared code releases nothing |

> Proven on `release-please-monorepo-demo`: a change in `src/Shared` released alpha, beta and shared as `1.1.0` together.

**Speaker notes:** ⏱ 0.75 min. Source: versioning.md, "Which model for a repository with several modules (i.e. monorepo)?"; versioning-release-please.md, "How may modules share code?". Why the last row fails: release-please releases a module only for commits that touch files inside its own folder, and has no way to say another folder belongs to it (upstream additional-paths, googleapis/release-please#2534, is unmerged). So a fix only in src/Shared changes what alpha and beta do but releases neither. The linked-versions row works under three conditions: the shared folder is itself a package of the group (a folder no package owns doesn't work, even inside a group); every module that references it is in the group, so they all share one version and release and deploy together; and each referencing module lists the shared folder in extra-paths in version-config.json, so a change there rebuilds it and the re-tag finds an image with the change. The guard release/check-module-references fails the build if any of the three is missing. The trade-off is losing independent releases inside the group: every release bumps every member. Node and Maven workspaces are a narrow exception (node-workspace, maven-workspace plugins release the dependent when its dependency releases). Proof: COREOPS-4612 on release-please-monorepo-demo, release PR #8 proposed alpha, beta and shared 1.1.0, three tags, alpha and beta re-tagged.

Continuous versioning: there's no branch to fix on; the fix becomes the next version, 1.1.1, with the feature in it. Teams on CV avoid this by keeping main releasable (feature flags). Plain: the Technical Owner runs Actions → release-please → Run workflow with tag v1.0.0; it creates hotfix/1.0.x; the fix goes in by PR, and the forward-port job opens its port to main as soon as it merges; the Technical Owner merges the branch's release PR, 1.0.1. While hotfix/1.0.x exists, main can't release a 1.0.z (the version check blocks it), so main's next release is 1.1.0 (with only fixes on main, the check asks for a Release-As: 1.1.0); the Technical Owner deletes the hotfix branch once production runs a version from main. Release branches: release/1.0.x already exists; same fix, same patch, same forward-port, no button. If release/1.0.x already holds an unreleased fix, the hotfix releases with it.

## 35. A breaking change ships

*Scenario 3*

*Diagram:* A breaking change, feat!:, under each strategy. Continuous versioning: merging it moves v1.4.0 to v2.0.0 automatically. Plain release-please: the release PR proposes 2.0.0 by default; if main sets always-bump-minor, it needs a Release-As: 2.0.0 footer. Release branches: the release PR proposes 1.5.0 and the version check fails; a PR with Release-As: 2.0.0 makes it v2.0.0, which creates release/2.0.x.

*Diagram labels:* Continuous · versioning · main · v1.4.0 · v2.0.0 · feat!: drop v1 API · a major, automatically, when it merges · Plain · release-please · main · v1.4.0 · feat!: drop v1 API · release PR proposes 2.0.0 · v2.0.0 · if main sets always-bump-minor, it needs Release-As: 2.0.0 · Release · branches · main · v1.4.0 · feat!: drop v1 API · release PR: 1.5.0, check fails ✗ · Release-As: 2.0.0 · v2.0.0 · release/2.0.x

**Continuous versioning**`feat!:` merges: the next major, automatically

**Plain release-please**The release PR proposes the next major, unless `always-bump-minor` is set

**Release branches**`Release-As: X.0.0` on `main`, enforced; it creates `release/X.0.x`

**Speaker notes:** ⏱ 1.25 min. Source: versioning-release-please.md, "How is a breaking change released?". In every strategy, the breaking change merges with an honest title, feat!: or a BREAKING CHANGE: footer, so the changelog lists it under Breaking Changes. Continuous versioning: the merge itself cuts 2.0.0. Plain: release-please proposes 2.0.0 by itself, unless the team chose always-bump-minor. Release branches: release-please proposes only 1.5.0, and the release PR version check fails it, naming the footer to use; put "Release-As: 2.0.0" in the description of that PR or the next one to main; merging the release PR cuts 2.0.0 and creates release/2.0.x. A feat!: that wasn't really breaking is confirmed as a minor with Release-As: 1.5.0, which also passes the check.

## 36. Three steps pick the strategy

*Choosing*

*Diagram:* Choosing a strategy. Step 1: is every merge a release candidate? Yes: Continuous versioning. No: step 2, how the modules share code. A monorepo whose modules use shared code directly and deploy separately: Continuous versioning. One module, or a monorepo whose shared code is a published package or whose modules deploy as one: go on to step 3. Step 3: must you keep merging to main during regression, or hotfix production without shipping unreleased work, often? Yes: release-please with release branches. No: plain release-please.

*Diagram labels:* Every merge a · release candidate? · no · One module, or a monorepo · whose shared code is a · package, or deploys as one · Monorepo: modules use · shared code directly and · deploy separately · Keep merging to main during · regression, or hotfix production · without shipping unreleased work, often? · yes · yes · no · Continuous versioning · release-please with · release branches · plain · release-please

> None is the default. It's your team's call: switching later is doable, but it's work, so choose on purpose.

**Speaker notes:** ⏱ 1.25 min. Walk the flow left to right. Step (1) Is every merge a release candidate? Continuous versioning. If not, you collect features or epics and plan a release, so it is release-please, unless (2) the shape of the repository rules it out. Two boxes, not one question: a monorepo whose modules use shared code directly, from a folder in the repository, and deploy separately goes to Continuous versioning, because release-please releases a module only for changes inside its own folder, so a change to the shared code alone would release nothing. Everything else carries on to step 3: one module; a monorepo whose shared code is a published, versioned package; or a monorepo whose modules share code directly but deploy as one, one linked-versions group (slide 32). A team routed to Continuous versioning by step 2 gives up the hotfix path, so it keeps main releasable. (3) Must you keep merging to main while a version is in regression, or hotfix production without shipping unreleased work, often? Release branches; otherwise plain release-please. Ask the room: which box does your team land in? If a lead isn't sure between plain and release branches, the deciding question is how often the team needs to keep merging during regression. On switching: between plain and release branches it's one PR once live release or hotfix branches are finished; between Continuous versioning and release-please the tags are compatible by design, but no repository has made that move yet, so it's planned work, not a setting.

## 37. Squash only: versions come from titles people reviewed

*Rulesets and squash merge*

- Continuous versioning (SemVer format): a merge commit in a module's range fails the build
- release-please requires it, or `wip` and `fix typo` land in the changelog and can change the bump

**Speaker notes:** ⏱ 0.5 min. Sources: versioning-continuous.md, "What must a repository have?"; versioning-release-please.md, "Repository settings". How squash works was slide 4; this is why each strategy needs it. It's a repository setting, from templates/*/repository-settings.json: squash merging only, merge commits and rebase merging off, default commit message "Pull request title and description". The one exception is Continuous versioning's legacy four-part format, which may keep merge commits (slide 43). The templates also turn on "Automatically delete head branches".

## 38. What the rulesets protect

*Rulesets and squash merge*

*Diagram:* What the rulesets allow. main already exists and is never deleted; it changes only by PR: squash merge, checks green, up to date, code owner approval, and no direct or force push. release/** branches are created only by the release App, change only by PR under the same rules, and are deleted only by Technical Owners. hotfix/** branches are created by the release App's hotfix button, or by a Technical Owner only when the button can't, change only by PR, and are deleted only by Technical Owners. Version tags, v* and *@v*, are created only by the release App and are never updated or deleted. Continuous versioning differs: its branch ruleset covers main only, and the build's own token creates tags, so only updating and deleting them is blocked.

*Diagram labels:* main · release/** · hotfix/** · v* and *@v* tags · Create · Change · Delete · — · exists from the start · release App only · automatic, at each X.Y.0 · release App · (the hotfix button) · or a Technical Owner, · when the button can't · release App only * · when a version is cut · Only by PR · squash merge · checks green, up to date · code owner approves · no direct or force push · Only by PR · same rules as main · Only by PR · same rules as main · Never · release-please finds its · last release by its tag · Never · Technical Owners · Technical Owners · Never · * Continuous versioning: a branch ruleset on main only, and the build's own token creates tags, · so only updating and deleting them is blocked.

- **Branches:** PR and checks required, up to date, no direct or force pushes
- **Creating `release/**` and `hotfix/**`:** the release App; a Technical Owner creates `hotfix/**` only when the button can't
- **Version tags:** nobody moves or deletes them; under release-please only the App creates them

**Speaker notes:** ⏱ 1.5 min. Source: versioning-release-please.md, "What must a repository have?" (Repository settings); versioning-continuous.md for the CV differences. release-please: one branch ruleset template covers main, release/** and hotfix/**: pull request required; the PR-title check (PR / Lint PR title), the build (CI / CI result) and the release PR version check (release-please / release-pr-version-check) required, accepted only from GitHub Actions; branches up to date before merging; no direct or force pushes; nobody bypasses. Only the release App creates release/** (through the workflow); the App or a Technical Owner creates hotfix/** (a Technical Owner only when the hotfix button can't); only Technical Owners delete either. Tag rulesets on v* and *@v*: only the App creates version tags, and nobody updates or deletes them. Why tags matter so much: release-please finds its last release by the tag named in the manifest, so a moved or hand-made tag breaks the next version. Continuous versioning differs: its branch ruleset is on main only (it has no release or hotfix branches), and it creates tags with the workflow's GITHUB_TOKEN, so its tag ruleset blocks only updating and deleting.

## 39. A person approves every PR, the release PR included

*Rulesets and squash merge*

- Code owner approval is required. The release App can approve a PR, but its approval never counts: the App is never a code owner
- Technical Owners are named in `CODEOWNERS`, and in the ruleset that lets them delete `release/**` and `hotfix/**`

> You don't write rulesets: cicd-standards `templates/` has them, and the setup how-tos apply them.

**Speaker notes:** ⏱ 0.75 min. Sources: versioning-release-please.md, "Repository settings"; versioning-continuous.md, "What must a repository have?". Every repository on these strategies has a CODEOWNERS file naming its Technical Owners, and every PR needs a code owner's approval, the release PR included. A plain required approval isn't enough: the App can approve a PR, and that approval would count, and any workflow on any branch can mint the App's token, so anyone with write access could have their PR approve itself. Requiring a code owner closes that: the App is never one, so a person always approves. New commits dismiss earlier approvals; Update branch keeps them. Templates: templates/continuous-versioning/ and templates/release-please/, applied by docs/how-to/set-up-continuous-versioning.md and set-up-release-please.md. The demo repos have one approver, so approvals are off there; that is a demo shortcut, not the rule.

## 40. Merging under the up-to-date rule

*Gotchas*

- After any merge, every other open PR needs **Update branch**
- On a release PR, **Update branch** only after `docs:` or `chore:` merges; after a `feat:` or `fix:`, wait a minute for release-please
- Never **Update with rebase** on a release PR
- Blocked with every check green? The version check was cancelled: re-run it

**Speaker notes:** ⏱ 1.25 min. Sources: versioning-release-please.md, "Repository settings" and "Known limitations"; the how-to, "What if a release PR is blocked with every check green?". The up-to-date rule exists for the release PR (so it can only merge once it describes everything on the branch), but a ruleset can't single one PR out, so it applies to every PR into main, release/** and hotfix/**. That's the cost; the benefit is that every PR's checks ran against the exact code it merges into. After a feat: or fix:, release-please rewrites its PR, usually within a minute; Update branch before then makes the release PR mergeable with a version and changelog that leave the new change out (the version check catches it). After docs: or chore:, release-please leaves its PR alone, so Update branch is the way to unblock it. Update with rebase rewrites release-please's commit and the check fails it. The cancelled check: release-please pushes twice within a second, and GitHub sometimes cancels the newer run; open the cancelled release-please run for the release PR's branch and Re-run all jobs. The workflow fix is COREOPS-4698.

## 41. Versions you didn't expect

*Gotchas*

- A `fix:` that changes only files the build skips cuts a version with no image: title it `docs:` or `chore:`
- A revert is a new version under Continuous versioning, and stays in release-please's changelog

**Speaker notes:** ⏱ 0.75 min. Sources: versioning-release-please.md, "Known limitations"; versioning-continuous.md, "How is a revert versioned?". (1) The build ignores docs/, .github/, .circleci/, Markdown anywhere, LICENSE, build-config.json and release-please's own files; release-please only skips the folders in its exclude-paths. The template lists docs, .github and .circleci, so the common gap is a fix: touching only, say, a root README.md or build-config.json: release-please cuts a version, no build made an image, and the retag job fails. (2) A revert under Continuous versioning bumps like a chore: a patch. GitHub's own "Revert …" title isn't a Conventional Commit: retitle it revert:.

## 42. Branches, Releases and running images

*Gotchas*

- Each live release or hotfix branch runs its own caller workflow: a library pin bump is a PR into each
- The release App can't touch `.github/workflows/`: those changes are ported by hand, and the hotfix button refuses an older tag whose workflow files differ
- GitHub's "Latest" release is the one created last, maybe a patch on an older line: use the environment's version
- Under release-please the running image doesn't know its version: inject it at deploy time
- release-please monorepos: modules that share code *directly* must be one `linked-versions` group, and release together

**Speaker notes:** ⏱ 1.5 min. Source: versioning-release-please.md, "Known limitations". (1) A push to release/1.0.x runs release-please.yml as it is on that branch, so when the library pin moves on main, open a chore: PR into each live branch too. (2) The release App has no Workflows permission, on purpose, so it can't push anything under .github/workflows/: the forward-port job labels such a change forward-port-needed (slide 27), and GitHub refuses the hotfix job a branch at a commit whose workflow files differ from today's, which is usual for an older release; a Technical Owner then pushes the branch with the same config commit (the how-to has the steps). (3) The Releases API marks every new release Latest, and release-please can't turn it off. (4) The image was built as main-412 and re-tagged, never rebuilt, so a version file inside it (package.json, version.txt) holds the previous version: an app that reports its version gets it from the deployment; how is not standardized yet (the CI → GitOps Handoff standard, Planned, will say). (5) release-please releases a module only for commits in its own folder, so a change only to shared code releases nothing; the build's shared-code guard fails such a reference. That shape fits Continuous versioning.

## 43. The four-part format: don't start new ones [legacy]

*Legacy*

#### What it is

- `X.Y.Z.N`, e.g. `1.4.0.7284`, from dynamo-config
- Merge commits allowed
- Not SemVer: npm can't publish it
- `N` is the run number plus `run-number-offset`: renaming `ci.yml` breaks it

#### Moving to SemVer

- Squash only
- `version-format: semver`
- `initial-version` above the last `X.Y.Z`: after `v1.4.2.2087`, `1.4.3` or `1.5.0`

*Shown, not demoed: `poc_echo_server_dotnet_legacy`'s tags, such as `v1.3.1.2019`*

**Speaker notes:** ⏱ 1.5 min. Say up front: this matters only if your repo came from dynamo-config; everyone else can relax for a minute. Source: versioning-continuous.md, "When may a repository use the four-part format?" and "How does a module move to SemVer?". It's Continuous versioning's build-metadata format, kept for repositories migrating from dynamo-config. The standard says it's legacy, not recommended, and will be deprecated in the future; no date is set, so don't promise one. A new repository should not use it; one that does states why in its README. X.Y.Z moves only for feat, fix, perf and breaking changes; anything else gets a new N. Why 1.4.3 and not 1.4.2: SemVer ranks 1.4.2 below 1.4.2.2087, so the first SemVer build fails without an initial-version above it. Remove initial-version once that first tag exists, and remove run-number-offset once no module uses the four-part format. If time allows, open poc_echo_server_dotnet_legacy's tags page.

## 44. Three strategies on one page

*Cheat sheet*

|  | Continuous versioning | Plain release-please | release-please with release branches |
|---|---|---|---|
| Branches | `main` only | `main`; `hotfix/X.Y.x` only when needed | `main`, plus `release/X.Y.x` per minor, created automatically |
| A version is cut | Every merge to `main` that builds | Merging the release PR | Merging a release PR, on `main` or a release branch |
| `fix:` · `feat:` · `feat!:` | patch · minor · major | patch · minor · major (minor with `always-bump-minor`) | `main`: minor · minor · `Release-As`. Release branch: always a patch |
| `chore:` · `docs:` | patch, if the module changed | no release | no release |
| Image from `main` | Tagged with its version, `1.4.0` | `main-412`, re-tagged `1.4.0` at release | As plain; `release-1.4.x-57` on the branch |
| Regression fails | Fix on `main` | Fix on `main`, hold merges | Fix on `release/X.Y.x`, forward-port |
| Production hotfix | Ships with whatever `main` holds | Hotfix button, patch, forward-port | Fix on `release/X.Y.x`, patch, forward-port |
| Chosen by | `version-config.json` | `app-release-please.yml` | `app-release-please-release-branches.yml` |

*Every strategy: squash merge, Conventional Commit PR titles, `vX.Y.Z` tags that never move, and cut is not released.*
