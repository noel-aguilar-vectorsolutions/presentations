## 3. One strategy per repository, and it rarely changes

*Why the choice matters*

- A repository uses exactly one strategy, for all its modules
- None is the default: it depends on how your team works

*Two questions decide most of it:*

- **Do you keep merging to `main` while a version is in regression?**

- **Must you hotfix production without shipping unreleased work?**

**Speaker notes:** ⏱ 1.25 min. Source: cicd-standards docs/ci/versioning.md, "Which versioning strategy should a repository use?". A repository MUST use exactly one strategy, for all its modules. Switching is possible (one PR that changes the caller workflow and config files), but a release-please repository must finish or delete its live release or hotfix branches first, so in practice teams rarely switch once they've started. That's why it's worth deciding deliberately now. Keep the two questions in mind: every strategy slide comes back to them, and the decision flow at the end starts from them. Ask the room to think about how their team handles regression today.

## 4. Squash merge: one PR, one commit, one title

*Recap*

*Diagram:* A pull request branch, feat/DAR-102-search, has three messy commits: wip, fix typo and address review. Squash merge turns them into one commit on main, titled with the PR title, feat(search): add clear button (DAR-102) (#123), which makes the next version a minor one.

*Diagram labels:* main · feat/DAR-102-search · wip · fix typo · address review · squash merge · feat(search): add clear button (DAR-102) (#123) · one commit on main; its message is the PR title · next minor

- Branch commits (`wip`, `fix typo`) never reach `main`
- The PR title becomes the commit's title on `main`
- Every strategy reads its versions from those titles

**Speaker notes:** ⏱ 1 min. A refresher from October, but it matters more than it looked then: everything in this session depends on it. With a merge commit, every commit on the branch lands on main, and a tool reading titles would see "wip" and "fix typo". With squash, main gets one commit per PR, titled by the PR. The repository setting is squash only, with the PR title and description as the commit message, so footers in the description (BREAKING CHANGE:, Release-As:) reach main too. Your branch commits can be as messy as you like.

## 5. The PR title sets the version

*Recap*

| Title | Use it for | Bump |
|---|---|---|
| `feat:` | Something new for the people who use the service | minor |
| `fix:` | A correction, a performance fix, a CVE bump: `fix(deps):` | patch |
| `docs:` | Documentation only | none under release-please |
| `chore:` | Everything else: build, CI, tests, refactors, a routine `chore(deps):` | none under release-please |
| `feat!:`, or a `BREAKING CHANGE:` footer | A change callers must adapt to | major |

> A merged title can't be changed. **The PR-title check is the only cheap place to catch a wrong version.**

**Speaker notes:** ⏱ 1.5 min. Source: versioning.md, "Which types should a title use?". Any Conventional Commit type is allowed and the check accepts them all, but four are recommended so nobody has to remember the rest. The question is: does the change alter what the service does for the people who use it? Use chore: in place of build:, ci:, test:, refactor: and style:, and fix: for perf:. revert: stays the type for taking a merged change out. A dependency bump is chore(deps):, or fix(deps): when it fixes a CVE, even when it's only a version number, so it releases and the changelog lists it. Retitle a Dependabot security PR fix(deps): before merging. The "none under release-please" column is a preview: under Continuous versioning, a chore: that changes a module's files still ships a patch. Once a title is a commit on a protected branch it can't be edited; retitling a merged PR changes nothing.

## 6. Cut is not released

*Recap*

- **Cut**: The git tag is created, `v1.4.0`. A release candidate, on its way to `staging`.

- **Released**: The ArgoCD Promotion Manager promotes that version to `production`.

> `1.4.0` fails regression, `1.4.1` passes, and production goes straight to `1.4.1`. Normal, in every strategy.

**Speaker notes:** ⏱ 0.75 min. Source: versioning.md, "When is a version cut, and when is it released?". This holds for all three strategies. Continuous versioning is not continuous deployment: every version it cuts is still only a release candidate. The Promotion Manager, not the tag list, is the record of what was released. A package published to CodeArtifact is the one exception (cut and released are the same event), but that's out of scope today.

## 7. One tag names one build, and never moves

*Recap*

| What | Tag |
|---|---|
| A build of `feat/DAR-102-search`, run 107 | `feat-DAR-102-search-107`: `<branch>-<run>` |
| A version | git tag `v1.4.0`, image `1.4.0` |
| Moving tags | None: no `latest`, no `main` |

*Which build gets the version tag differs by strategy: coming up.*

**Speaker notes:** ⏱ 0.75 min. Source: versioning.md, "How are builds tagged?" and "What do versions and version tags look like?". The branch name with each / replaced by -, then the workflow run number. Version tags are vX.Y.Z in git (the git convention, and release-please's default) and bare X.Y.Z on images and packages. A monorepo module's git tag carries its component: echo@v1.4.0. The difference by strategy, for later: under Continuous versioning, the build on main is tagged with the version it cuts. Under release-please, every build is branch-run, main included (main-412), and the version is added to that image at release.

## 8. Not merged = not shipped

*Recap*

- Anything merged to `main` is in the next version: the very next one under Continuous versioning, the next release PR under release-please
- Work that isn't ready stays unmerged, or is merged behind a feature flag that's off
- A merged change only comes out with a `revert:` PR

> This is what a hotfix runs into: whatever is on `main` ships with it, unless the strategy gives you another branch.

**Speaker notes:** ⏱ 1 min. Source: versioning.md, "What must not be merged to main?". This is the rule the rest of the session builds on. A revert takes the code out, but it doesn't cancel the original commit's effect on the version, or, with release-please, its line in the changelog. The callout sets up the second of our two questions: if main has unreleased work and production needs a fix today, the strategy decides whether you can ship the fix alone.

## 9. `MAJOR.MINOR.PATCH`: breaking, feature, fix

*SemVer*

- **MAJOR 2.0.0**: A breaking change: callers must change something

- **MINOR 1.5.0**: A new feature; nothing breaks

- **PATCH 1.4.1**: A fix; nothing new

> One version, one tag, never moved. A monorepo has one version line per module, tagged `<component>@v1.4.0`.

**Speaker notes:** ⏱ 0.75 min. Source: versioning.md, "What do versions and version tags look like?". Starting from 1.4.0 in the examples. Tags are protected by rulesets so nobody can move or delete one (section 8). Monorepo: under Continuous versioning, each module gets its own line, component@vX.Y.Z; under release-please, each package does, and a repository with several packages must use component tags. A single-module release-please repository uses plain vX.Y.Z by default, or may choose component tags: demo 2 uses echo@v…, demo 3 plain v…, so you'll see both.

## 10. Same PR title, different version

*SemVer, three ways*

| Title | Continuous versioning | Plain release-please | Release branches: `main` | Release branches: `release/X.Y.x` |
|---|---|---|---|---|
| `fix:` | patch | patch | **minor** (`always-bump-minor`) | patch (`always-bump-patch`) |
| `feat:` | minor | minor | minor | **patch**, with a warning on the PR: revert it (the default) or keep it on purpose |
| `feat!:` | major | major, unless the team sets `always-bump-minor` | needs `Release-As: X.0.0`; the version check fails without it | still a patch, with a stronger warning: majors come from `main` |

> Release branches change the rules on purpose: `main` cuts minors, each release branch cuts patches.

**Speaker notes:** ⏱ 1.75 min. The core slide. Sources: versioning.md's comparison table; versioning-release-please.md, "Why does main never release a patch version?", "What if a feature lands on a release branch?" and "How is a breaking change released?". Walk it column by column. Continuous versioning and plain release-please bump by type, the textbook way. With release branches, main is set to always-bump-minor so it can never take a patch number that a release branch owns: even a release holding only fixes is the next minor. Each release branch is set to always-bump-patch, so anything merged there, even a feat:, ships as the next patch; a job comments on the PR to warn, but doesn't block it. The cost of always-bump-minor is that a breaking change no longer becomes a major by itself: it needs a Release-As: X.0.0 footer on a PR to main, and the release PR version check (release-please / release-pr-version-check) fails main's release PR until it's there. That check applies from 1.0.0 on; below 1.0 a minor is the right bump for a breaking change. A plain release-please team may choose always-bump-minor too, and then gets the same rule.

## 11. The type decides how much, or whether

*SemVer, three ways*

| Title | Continuous versioning | Plain release-please | Release branches: `main` | Release branches: `release/X.Y.x` |
|---|---|---|---|---|
| `chore:` / `docs:` | **patch**, if it changes the module's files | **no release** | no release | no release |
| When it's cut | Every merge to `main` that builds | When someone merges the release PR | When someone merges the release PR | When the Technical Owner merges that branch's release PR |

- **Continuous versioning**: A patch means "a build shipped", not "a bug was fixed".

- **release-please**: The type decides **whether** a change releases. `Release-As: X.Y.Z` forces a version, e.g. to ship a `chore:` alone.

**Speaker notes:** ⏱ 1.5 min. Sources: versioning.md, "Which types should a title use?"; versioning-continuous.md, "In the SemVer format"; versioning-release-please.md, "When may the proposed version be overridden?". Continuous versioning: every build on main that ships changes what's deployed, so it needs a new version, even when the commits don't call for one. "The module's files" are its folder and extra-paths, minus Markdown, docs/ and .github/, so a docs-only change builds nothing and cuts nothing. release-please: docs: and chore: wait for the next feat: or fix:. When one must reach production first (a CVE bump merged as chore(deps): by mistake, say), put "Release-As: 1.4.3" (the next patch) on its own line at the end of a PR description; release-please proposes that version. Release-As is the only correction after a merge. On main it must name a version higher than every version tag in the repository. Who merges: anyone with merge rights merges main's release PR (it goes to staging first); only the Technical Owner merges a release or hotfix branch's release PR, because a patch can be a production hotfix.

## 12. `main` only: every merge that builds is a version

*Continuous versioning*

*Diagram:* Continuous versioning uses main only. Topic branches feat/DAR-102-search and fix/DAR-103-retry each build an image named after the branch and run, such as feat-DAR-102-search-107 and fix-DAR-103-retry-112, with no version. Each squash merge to main cuts a version at once: v1.4.0 for the feat, v1.4.1 for the fix, v1.4.2 for a chore, which is still a patch. A docs-only merge builds nothing and gets no version.

*Diagram labels:* main · v1.3.0 · feat/DAR-102-search · feat-DAR-102-search-107 · image, no version · v1.4.0 · feat: a minor · fix/DAR-103-retry · fix-DAR-103-retry-112 · v1.4.1 · fix: a patch · v1.4.2 · chore: still a patch · no tag · docs: builds nothing

- Topic branches build `<branch>-<run>` images, never a version
- On `main`: compute the version, push image `1.4.0`, then tag `v1.4.0`
- Only changed modules build; a docs-only change builds nothing

**Speaker notes:** ⏱ 1.5 min. Source: versioning-continuous.md, "How does Continuous versioning work, end to end?". One workflow, ci.yml, calling app-ci. Its first job, Plan builds, runs compute-versions: which modules did this push change, and, on main, what's each one's next version, from the PR titles merged since that module's last tag. Each changed module is built once, tested and scanned as built, and only then pushed; on main, the git tag is created last, so a tag never points at a version whose images are missing or untested. A change that touches no module (docs, workflows, a chart outside the module folder) builds nothing. Main builds run one at a time, so versions are cut in order.

## 13. Git tags are the whole record

*Continuous versioning*

#### You get

- A version per merge, computed from the titles
- Only changed modules built and tagged
- One version line per module in a monorepo

#### You don't get

- A release PR to batch changes
- `CHANGELOG.md` or a GitHub Release
- A branch to hotfix production on

> Hotfix while `main` has unreleased work: **not covered**. The fix ships with everything merged before it.

**Speaker notes:** ⏱ 1.25 min. Source: versioning-continuous.md, "Known limitations". No changelog or GitHub Release is generated: the git tags are the record of versions, and the Promotion Manager the record of what was released. The hotfix gap follows from "not merged = not shipped": every merge to main is the next version, so a fix can't skip work already merged. A team that needs that uses release-please with release branches. In practice this works for a team that keeps main releasable: small PRs, feature flags for unfinished work. Also a limitation: version tag creation isn't restricted (they're created with GITHUB_TOKEN), only moving and deleting them is blocked.

## 14. Fits a team that ships each change as it lands

*Continuous versioning*

**It fits**

- Each merged change goes to `staging` on its own
- `main` is kept releasable: small PRs, feature flags
- A service monorepo whose modules share files or code (`extra-paths`)

**The files**

- `version-config.json`: the modules, their format (`semver`), extra paths
- `build-config.json`: what each module builds
- `ci.yml`: calls `app-ci`, copied as-is

**Speaker notes:** ⏱ 1.25 min. Sources: versioning.md, "Which model for a repository with several modules"; versioning-continuous.md, "What must a repository have?". The monorepo point matters: under Continuous versioning, a module lists whatever else it builds from in extra-paths (a shared entrypoint.sh, a library referenced directly), and a change to it cuts a version of every module that lists it. release-please can't do that (see the gotchas). Files only named, never opened: the set-up how-to (docs/how-to/set-up-continuous-versioning.md) walks through them. The pilot, poc_echo_server_dotnet, is what demo 1 uses.

## 17. Merging the release PR cuts the version

*Plain release-please*

*Diagram:* Plain release-please. Each merge to main builds an image tagged main-10, main-11 and so on, and a release PR collects them. Merging it cuts v1.0.0 and re-tags the tested main-11 image. Production is on 1.0.x and needs a hotfix while main holds unreleased work, so the hotfix button creates hotfix/1.0.x from the production tag v1.0.0. A fix there releases v1.0.1 and is forward-ported to main, and the next release PR cuts v1.1.0.

*Diagram labels:* release PR · next release PR · main · main-10 · main-11 · v1.0.0 · re-tags main-11 · main-12 · feat: B, unreleased · main-13 · v1.1.0 · re-tags main-13 · main-14 · hotfix/1.0.x · fix: X · v1.0.1 · created by the hotfix button from v1.0.0, the production tag · forward-port

- `main` builds `main-<run>` images, with no version yet
- Merging the release PR tags `vX.Y.Z` and writes a GitHub Release
- `hotfix/X.Y.x`, from the production tag, **only** when `main` has moved on

**Speaker notes:** ⏱ 1.5 min. Source: versioning-release-please.md, "How does plain release-please work?" and "Hotfix branches". After every releasable merge (feat:, fix:, a breaking change), release-please updates one standing release PR with the next version and its changelog. Nothing is cut until a person merges it. A hotfix branch is rare: if nothing has merged to main since the production version was cut, the hotfix goes on main like any fix. Only when main has unreleased work does the Technical Owner press Actions → release-please → Run workflow with the production tag; the workflow creates hotfix/X.Y.x from it, the fix goes in by PR, the branch's release PR cuts the next patch, and the forward-port job opens the port of the fix back to main. While the hotfix branch exists, main can't release on its line: the version check blocks it, so main's next release is a minor.

## 18. The tested image gets the version: no rebuild

*Plain release-please*

- **Re-tag**: The release adds `1.4.0` to the image `main` already built and tested, `main-412`: same digest.

- **Changelog**: `CHANGELOG.md` and a GitHub Release, written from the PR titles.

- **You decide when**: Nothing is cut until a person merges the release PR.

> Build once, promote many: what regression tested is byte for byte what ships.

**Speaker notes:** ⏱ 1.25 min. Source: versioning-release-please.md, "What happens when the release PR merges?". The release commit (chore(main): release 1.4.0) only changes the manifest and CHANGELOG.md, so it builds nothing. The retag job walks back to the commit before it that built (normally its parent), waits for that build to finish, checks each image's org.opencontainers.image.revision label is that commit's SHA, and only then adds 1.4.0 to the same digest. It never falls back to "the newest image". The Promotion Manager sees 1.4.0 appear as a push and can promote it. The changelog is the benefit people remember: QA, support and product can read what's in a version without asking a developer.

## 19. Fits a team that batches changes, and can hold merges

*Plain release-please*

**When regression fails**

- Fix it on `main`
- **Hold other merges**, so the next version stays small
- The next release PR replaces the failed version in `staging`

**The files**

- `release-please-config.json`: release type, excluded paths
- `.release-please-manifest.json`: the last version
- `release-please.yml`: calls `app-release-please.yml`, which *is* the choice

**Speaker notes:** ⏱ 1.25 min. It fits a team that ships several changes together, on a schedule or after a round of regression, can hold merges while a version is in regression, and rarely patches an older version. Sources: versioning.md, "Which versioning strategy should a repository use?"; the how-to, "How do I fix a failed regression with plain release-please?". The next version after a failed 1.4.0 is 1.4.1, or 1.5.0 if a feature merged meanwhile, which is why you hold merges. The strategy is chosen by which reusable workflow the caller workflow, .github/workflows/release-please.yml, calls: app-release-please.yml for plain, app-release-please-release-branches.yml for release branches. release-please itself knows nothing about release branches. A service uses release-type simple, which writes only the manifest, CHANGELOG.md and version.txt if it exists. The repository settings and rulesets come from cicd-standards templates/release-please/, applied once during setup.

## 22. Every minor version gets its own `release/X.Y.x`

*release-please with release branches*

*Diagram:* release-please with release branches. main merges feat: A and feat: B, and merging the release PR cuts v1.0.0, which creates release/1.0.x automatically. main keeps merging feat: C toward v1.1.0. - Cutting `X.Y.0` on `main` creates `release/X.Y.x` from its tag
- Fixes go on the release branch as patches; it's never merged back
- Several can be live: production on `1.0.2`, `1.1.0` in regression

**Speaker notes:** ⏱ 1.25 min. Source: versioning-release-please.md, "How do release branches work?". The x is literal: one branch per minor version, release/1.0.x holds 1.0.1, 1.0.2 and so on. The workflow (app-release-please-release-branches.yml) creates it, as the release App, right after main's release PR cuts X.Y.0: the release commit plus one commit with the branch's own config. Nobody creates one by hand. The release branch first stabilizes the version while it's in regression, then maintains it with hotfixes once it's in production, so there's no separate hotfix branch under this strategy. It's never merged into main: each fix reaches main by its own forward-port PR. The Technical Owner deletes it once production runs a later minor. In industry terms: trunk-based development with branch-for-release. Teams that cut release/1.0.0 branches by hand today land here.

## 23. `main` never releases a patch

*release-please with release branches*

- `main` uses `always-bump-minor`: even a release of only fixes is the next minor
- Each release branch uses `always-bump-patch`: every release from it is the next patch
- A major needs `Release-As: X.0.0` on `main`; the version check fails a breaking change without it

> Regression fails? Fix it on `release/X.Y.x` while `main` keeps moving.

**Speaker notes:** ⏱ 1 min. Source: versioning-release-please.md, "Why does main never release a patch version?". release-please computes main's version from main alone and can't see release branches. ## 35. Merging under the up-to-date rule

*Gotchas*

- After any merge, every other open PR needs **Update branch**
- On a release PR, **Update branch** only after `docs:` or `chore:` merges; after a `feat:` or `fix:`, wait a minute for release-please
- Never **Update with rebase** on a release PR
- Blocked with every check green? The version check was cancelled: re-run it

**Speaker notes:** ⏱ 1.25 min. Sources: versioning-release-please.md, "Repository settings" and "Known limitations"; the how-to, "What if a release PR is blocked with every check green?". The up-to-date rule exists for the release PR (so it can only merge once it describes everything on the branch), but a ruleset can't single one PR out, so it applies to every PR into main, release/** and hotfix/**. That's the cost; the benefit is that every PR's checks ran against the exact code it merges into. After a feat: or fix:, release-please rewrites its PR, usually within a minute; Update branch before then makes the release PR mergeable with a version and changelog that leave the new change out (the version check catches it). After docs: or chore:, release-please leaves its PR alone, so Update branch is the way to unblock it. Update with rebase rewrites release-please's commit and the check fails it. The cancelled check: release-please pushes twice within a second, and GitHub sometimes cancels the newer run; open the cancelled release-please run for the release PR's branch and Re-run all jobs. The workflow fix is COREOPS-4698.

## 36. Versions you didn't expect

*Gotchas*

- `always-bump-minor` hides majors: `feat!:` is a minor without `Release-As` (the check catches it)
- A `fix:` that changes only files the build skips cuts a version with no image: title it `docs:` or `chore:`
- A `feat:` merged into a release branch ships in a patch: warned, not blocked
- A revert is a new version under Continuous versioning, and stays in release-please's changelog

**Speaker notes:** ⏱ 1.25 min. Sources: versioning-release-please.md, "How is a breaking change released?", "Known limitations", "What if a feature lands on a release branch?"; versioning-continuous.md, "How is a revert versioned?". (1) The version check fails main's release PR for a breaking change without a major, from 1.0.0 on. (2) The build ignores docs/, .github/, .circleci/, Markdown anywhere, LICENSE, build-config.json and release-please's own files; release-please only skips the folders in its exclude-paths. (3) A job comments on any PR into release/** whose title marks a feature or breaking change; the Technical Owner reverts it (the default) or keeps it on purpose; it never fails the check. (4) A revert under Continuous versioning bumps like a chore: a patch. GitHub's own "Revert …" title isn't a Conventional Commit: retitle it revert:.

## 37. Branches, Releases and running images

*Gotchas*

- Each live release or hotfix branch runs its own caller workflow: a library pin bump is a PR into each
- A change to a workflow file is forward-ported by hand
- The hotfix button can't branch from an older tag whose workflow files differ: a Technical Owner does it by hand
- GitHub's "Latest" release is the one created last, maybe a patch on an older line: use the environment's version
- Under release-please the running image doesn't know its version: inject it at deploy time
- release-please monorepos: modules can't share code outside one `linked-versions` group

**Speaker notes:** ⏱ 1.5 min. Source: versioning-release-please.md, "Known limitations". (1) A push to release/1.0.x runs release-please.yml as it is on that branch, so when the library pin moves on main, open a ci: PR into each live branch too. (2) and (3) The release App has no Workflows permission, on purpose, so it can't push anything under .github/workflows/: the forward-port job labels such a change forward-port-needed, and GitHub refuses the hotfix job a branch at a commit whose workflow files differ from today's, which is usual for an older release; a Technical Owner then pushes the branch with the same config commit (the how-to has the steps). (4) The Releases API marks every new release Latest, and release-please can't turn it off. (5) The image was built as main-412 and re-tagged, never rebuilt, so a version file inside it (package.json, a .csproj, version.txt) holds the previous version: an app that reports its version gets it from the deployment, e.g. an environment variable from the image tag. (6) release-please releases a module only for commits in its own folder, so a change only to shared code releases nothing; the build's shared-code guard fails such a reference. That shape fits Continuous versioning.

## 38. The four-part format: don't start new ones [legacy]

*Legacy*

#### What it is

- `X.Y.Z.N`, e.g. `1.4.0.7284`, from dynamo-config
- Merge commits allowed
- Not SemVer: npm can't publish it
- `N` is the run number plus `run-number-offset`: renaming `ci.yml` breaks it

#### Moving to SemVer

- Squash only
- `version-format: semver`
- `initial-version` above the last `X.Y.Z`: after `v1.4.2.2087`, `1.4.3` or `1.5.0`

*Shown, not demoed: `poc_echo_server_dotnet_legacy`'s tags, such as `v1.3.1.2019`*

**Speaker notes:** ⏱ 1.5 min. Source: versioning-continuous.md, "When may a repository use the four-part format?" and "How does a module move to SemVer?". It's Continuous versioning's build-metadata format, kept for repositories migrating from dynamo-config. The standard says it's legacy, not recommended, and will be deprecated in the future; no date is set, so don't promise one. A new repository should not use it; one that does states why in its README. X.Y.Z moves only for feat, fix, perf and breaking changes; anything else gets a new N. Why 1.4.3 and not 1.4.2: SemVer ranks 1.4.2 below 1.4.2.2087, so the first SemVer build fails without an initial-version above it. Remove initial-version once that first tag exists, and remove run-number-offset once no module uses the four-part format. If time allows, open poc_echo_server_dotnet_legacy's tags page.
